The proxy and its setup page #

Contents: What it listens on · The setup page · Settings you may want (caching, fallbacks, guards, budgets, limits) · Using it from another machine · Other useful commands

maple-proxy is the program that holds your sign-ins and talks to the models. The agent uses it, and so can any other tool that speaks the OpenAI or Anthropic API. Start it with:

maple-proxy serve

It stays in the foreground. Add --logs=true to watch requests, --logs=/path/to.log to keep a record, or --logs=stdout when something else (systemd, launchd) is capturing output. To keep it running in the background, see Running as a service.

What it listens on #

AddressWhat it isWho may use it
127.0.0.1:11539The setup pageThis machine only. It refuses to listen anywhere else
127.0.0.1:11535OpenAI-compatible API (/v1)This machine; other machines only with an access token
127.0.0.1:11537Anthropic-compatible APIThis machine; other machines only with an access token

The addresses and ports are in the server: section of config.yaml. The proxy picks up changes to its providers and settings without a restart.

The setup page #

Open http://127.0.0.1:11539 on the machine running the proxy. From there you can:

  • Sign in to GitHub Copilot (a browser flow) or save an Anthropic API key. See Signing in.
  • Add model servers: pick the type (Ollama, LM Studio, oMLX, Lemonade, Unsloth, or any OpenAI-compatible server), press Detect models, and save. See Connect a model server.
  • See your Copilot allowance: the plan, how many chats are left, and when they reset.
  • Manage remote access: switch remote control on, pair a phone with a short code or a link, choose what each device may do, choose the folders a phone may start sessions in, and revoke a device at any time. See Remote control.
  • Read recent activity: sign-ins, token changes and remote switches.

Keys and sign-ins you enter here are stored in your system keyring, not in the configuration file.

Settings you may want #

Everything below is a card under Proxy settings on the setup page. Each control has a one-line explanation and a link back here. You do not need to edit any file.

When you change something, nothing is written yet. Press Review changes to see exactly what will change in config.yaml, then Save settings, or Revert to throw the edits away. The page checks every value with the same rules the proxy uses when it starts, and points at the field that is wrong. Saved settings apply to the very next request, with no restart, except the ones marked restart required.

Prompt caching #

Long conversations resend the same beginning on every turn. With caching on, backends that support it charge much less for that repeated part. It is a switch per provider; it appears only for backends where it can be controlled (Claude through the Anthropic API or through Copilot). Other backends cache on their own, or not at all, and the page says so. The default is on. In the file: prompt_cache: auto or off on a provider.

Fallbacks #

A fallback tells the proxy what to try when a model cannot answer: its account is out of chats or credit, the backend is overloaded, or it is unreachable. Pick the model, then add the fallbacks in the order to try them; move them with the arrows. A model cannot fall back to itself, and a name can be listed once.

A fallback happens only before any output has been sent, and only for failures another backend could fix. Bad credentials and malformed requests are never retried elsewhere, and a fallback's own fallbacks are not followed. Nothing falls back unless you add a rule. Responses from a fallback carry an X-Maple-Served-By header naming what answered. In the file: model_fallbacks.

A fallback whose context window is known to be too small for the request is passed over, and the next one is tried; the reason is listed in the X-Maple-Fallback-From header. A fallback whose window is not known is still tried. When no model on the list can take the request, the proxy answers with an error that says so, instead of sending it somewhere it cannot fit. The model you asked for is always tried, whatever its size.

Most tools that talk to a model connect to one fixed account or endpoint: when it runs out, the run stops until you fix it by hand. A fallback here means the proxy can try another one automatically, mid-task, with nothing for the client to do differently — list a second account or a second model and it takes over on its own. See adding a second GitHub Copilot or Anthropic account to set one up.

Auto mode at the proxy #

model_aliases and model_fallbacks together give you a name that is not a real model — request it and the proxy decides what actually answers, today and after you change your mind later, with no change needed on whatever asked for it:

model_aliases:
  auto-heavy: gpt-6-sol
  auto-medium: gpt-6-sol-mini
  auto-light: gpt-5-mini
model_fallbacks:
  auto-heavy: [claude-opus-5-5]
  auto-medium: [claude-sonnet-5]

Any client that speaks the proxy's OpenAI- or Anthropic-compatible surface can now ask for auto-heavy, auto-medium or auto-light and get whichever model you have named for it right now — change the alias and every client picks it up without being reconfigured. The name needs a model_aliases entry to mean anything at all; model_fallbacks on top of that reroutes it the same way a real model name would fall back, on the same terms described above.

Maple Harness's own /model auto picks a model itself by default (harness.auto_model_resolution: client). Setting it to proxy instead keeps the harness's own judgement of how much a turn is worth, but asks for it by name — auto-heavy, auto-medium or auto-light, or your own names via harness.auto_model_map — and leaves the proxy's model_aliases/model_fallbacks to decide what that means. This is the one case where auto mode works with a model that publishes no ranking of its own, since nothing here depends on one. maple-harness doctor checks that the proxy actually serves the names it would ask for.

Guards #

  • Context guard: for tools that do not know a model's window. Off sends the request as is, Truncate drops the oldest turns until it fits, and Refuse rejects it with a plain error. In the file: context_guard.
  • Repeat guard: stops a reply that has collapsed into repeating itself. Off by default. In the file: degenerate_guard.

Keeping the cache useful #

Two more settings, both on the same Guards card, help a provider's prompt cache do its job on long conversations:

  • Prefix stabiliser (prefix_stabilizer, on by default). Some tools resend their tool list in a different order, or put the current time in the system prompt, which stops the provider from reusing what it already read. The proxy puts the tools back in their first order and moves a changing line such as the time to the end of the last message. It never removes or rewrites a tool, and it leaves alone any tool that manages its own caching.
  • Trim old tool results (context_trim, off by default). Once a conversation is long, the content of old, large tool results is replaced by a short note ("ask again if needed"), a batch at a time, so the provider does not have to read the same output on every turn. Recent turns, your messages and the system prompt are never touched. The card lets you set when it starts, how many recent turns it spares, and the smallest result it replaces. Turn it on for long runs with large tool output; leave it off for short sessions.

Responses say what was done in the X-Maple-Prefix-Stabilized and X-Maple-Tool-Results-Trimmed headers.

Seeing how the cache is doing #

A provider that caches prompts charges a small fraction of the price for the part of a request it has already seen, and the full price, more for storing it, the first time. On a Copilot business seat, one request measured 1.573 AI units the first time and 0.132 when repeated unchanged. So when a bill looks wrong, the first question is whether the cache was used, and where it stopped being used.

The setup page has a Cache card that answers it:

  • the hit rate today, as a gauge, with the tokens read from and written to the cache and the AI units spent;
  • a table per model and per client (the token's label, or local (claude-code) for a tool on this machine);
  • the latest times the cache was lost, with the reason: tools or system prompt changed, an early message changed, model switched, or cache expired (a provider forgets after about five minutes without use).

maple-proxy cache prints the same summary in a terminal (--recent lists the last requests, --json gives the raw figures). Each response that is not streamed also carries X-Maple-Cache (hit, partial, miss or lost) and X-Maple-Cache-Read and X-Maple-Cache-Write token counts.

Only counts and labels are kept. The Cache, Sessions and Savings figures are saved to disk every few minutes and on a clean stop, so a restart does not lose them; a crash between two saves loses only the activity in that gap. No prompt, answer or file content is recorded. A provider that reports no cache figures at all (most local servers) shows as not applicable rather than as a miss.

Seeing cost per session #

Below the Cache card, the Sessions card groups AI units, tokens and requests by an opaque id a client sends on its own requests as X-Maple-Session — Maple Harness sends it automatically for every session, generated once and kept for the life of that conversation (including across --continue/--resume). A subagent it delegates to sends the same id as its parent, so a subagent's spend counts toward the session that started it, not a total that quietly leaves it out. The id is random and carries no content: never a session's name, never anything said in it — only the id and numbers appear on the card.

Any other OpenAI- or Anthropic-compatible client can send this header too, to appear here the same way. A client that doesn't send it is simply not grouped into any session, exactly as before this existed — nothing about a request without the header changes.

GET /api/cache/sessions returns the same list as JSON, most recently active first.

Seeing what it saves #

Below the Cache card, the Savings card shows what the proxy's techniques have saved and what they cost, today and in the last hour, across every session on this proxy, not just yours — a different scope from the Sessions card above it, which is one session's own measured spend. Every figure here is tagged measured (a count of tokens or requests, or the total AI units the provider actually billed) or estimated (a value in AI units, which comes from prices the proxy learns from your own requests), and an estimate says what it rests on. The card's own summary sentence always states what you actually spent (measured) right next to what the techniques are estimated to have avoided, so the two are never read apart from each other, and the estimated figure is capped so it can never claim more was avoided than the window actually spent. Costs are counted too, so the net can be negative, and the card then says so and shows which technique lost. The proxy always takes the reading that reports less saving, and it does not value anything until it has seen enough of your requests to know what a token costs. The net itself is deliberately narrow: it only ever totals the two techniques with a basis solid enough to trust in one number (the prompt cache and trimming). One or two others are shown fully computed on their own line, but held out of that total until their own estimate can be checked against a real bill — the line itself says which and why, and there is no setting that widens the net back out; it is a fixed choice, not a preference. maple-proxy savings prints the same in a terminal, and /savings in the harness shows what the harness itself did in a session.

Daily budgets #

For each provider you can set a limit on requests per day, on the AI units a day, or both; leave a box empty for no limit on that measure. Days are UTC, and today's use is shown next to each limit. When a provider reaches its limit, requests for it are refused, or handed to its fallback if you set one. In the file: budgets.

Limits and hosts (restart required) #

These are read when the proxy starts, so after saving, stop and start maple-proxy for them to apply.

  • Rate limit: how many requests one client may make. The default is off for this machine and on, conservatively, for other machines. You can force it on or off and set the requests per minute, the burst, how many may run at once, and whether clients are counted per token or per address.
  • Allowed hosts: extra names the proxy answers to, one per line, for example a Tailscale name such as box.tailnet-name.ts.net. Names only: no https://, no path.
  • Usage log: a file that gets one line per request. Budget counts (not the Cache, Sessions or Savings cards, which now survive a restart on their own) come from it, so set it if you use budgets and want their counts to survive a restart too. It rotates to a new file for each UTC day (usage-2026-09-28.jsonl next to the path you set), so it never grows into one unbounded file — nothing is ever deleted on its own. The Usage data card further down the page shows what the log holds, downloads it as CSV or Parquet, and removes old days after you confirm the list; see Query and export your usage data for the same from a terminal (maple-proxy usage export, usage prune) and how to point DuckDB or Grafana straight at it.

If you prefer files, all of this lives in config.yaml (usually ~/.config/maple-harness/config.yaml):

model_fallbacks:
  cloud: [local]            # cloud and local are model aliases (see Connect a model server)
context_guard: truncate     # off | truncate | error
degenerate_guard: true
budgets:
  - provider: anthropic
    max_requests_per_day: 150
    max_ai_units_per_day: 20
server:
  allowed_hosts: [box.tailnet-name.ts.net]
  rate_limit:
    requests_per_minute: 120
    burst: 20
    max_concurrent: 4
  usage_ledger: /home/you/.config/maple-harness/usage.jsonl

Saving from the setup page rewrites config.yaml in its standard form, so comments you added by hand are not kept. Keys are never in it: they stay in your system keyring, and the file holds only a reference.

Using it from another machine #

By default only this machine can reach the model APIs. To let another machine on your network use them, set the listen address and create an access token with the proxy scope on the setup page:

server:
  openai_compat: 0.0.0.0:11535
  anthropic_compat: 0.0.0.0:11537
  allowed_hosts: [my-box.local]     # the name other machines use to reach it

The proxy refuses to start on a non-loopback address until such a token exists, and callers send it as Authorization: Bearer <token>. Requests from other machines are rate-limited. The setup page itself never listens beyond this machine.

Check the cache yourself #

Providers cache the start of a request that they have seen recently, and reading from that cache costs a fraction of processing it again. Whether that is working for your account and your model is easy to see:

maple-proxy cache probe --model gpt-5-mini --yes

It sends the same small request twice, a few seconds apart, through the running proxy, and prints what each call reported: prompt tokens, tokens read from the cache, tokens written to it, and AI units. It says so plainly when a model reports no cache figures, in which case the cache may not be visible from here. Without --yes it sends nothing and only says what it would send (two requests of about 6,000 tokens, which may spend a few AI units). --tokens changes the size (1,500 to 50,000) and --wait the pause between the two calls. Nothing it prints contains a key.

Other useful commands #

maple-proxy auth status         # what is signed in
maple-proxy secrets status      # where each secret is stored (never its value)
maple-proxy audit tail          # who did what: token changes, refused requests
maple-proxy update              # install a newer release
