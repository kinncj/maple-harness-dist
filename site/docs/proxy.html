The proxy and its setup page #

Contents: What it listens on · The setup page · Settings you may want (caching, fallbacks, guards, budgets, limits) · Using it from another machine · Other useful commands

maple-proxy is the program that holds your sign-ins and talks to the models. The agent uses it, and so can any other tool that speaks the OpenAI or Anthropic API. Start it with:

maple-proxy serve

It stays in the foreground. Add --logs=true to watch requests, --logs=/path/to.log to keep a record, or --logs=stdout when something else (systemd, launchd) is capturing output. To keep it running in the background, see Running as a service.

What it listens on #

AddressWhat it isWho may use it
127.0.0.1:11539The setup pageThis machine only. It refuses to listen anywhere else
127.0.0.1:11535OpenAI-compatible API (/v1)This machine; other machines only with an access token
127.0.0.1:11537Anthropic-compatible APIThis machine; other machines only with an access token

The addresses and ports are in the server: section of config.yaml. The proxy picks up changes to its providers and settings without a restart.

The setup page #

Open http://127.0.0.1:11539 on the machine running the proxy. From there you can:

  • Sign in to GitHub Copilot (a browser flow) or save an Anthropic API key. See Signing in.
  • Add model servers: pick the type (Ollama, LM Studio, oMLX, Lemonade, Unsloth, or any OpenAI-compatible server), press Detect models, and save. See Connect a model server.
  • See your Copilot allowance: the plan, how many chats are left, and when they reset.
  • Manage remote access: switch remote control on, pair a phone with a short code or a link, choose what each device may do, choose the folders a phone may start sessions in, and revoke a device at any time. See Remote control.
  • Read recent activity: sign-ins, token changes and remote switches.

Keys and sign-ins you enter here are stored in your system keyring, not in the configuration file.

Settings you may want #

Everything below is a card under Proxy settings on the setup page. Each control has a one-line explanation and a link back here. You do not need to edit any file.

When you change something, nothing is written yet. Press Review changes to see exactly what will change in config.yaml, then Save settings, or Revert to throw the edits away. The page checks every value with the same rules the proxy uses when it starts, and points at the field that is wrong. Saved settings apply to the very next request, with no restart, except the ones marked restart required.

Prompt caching #

Long conversations resend the same beginning on every turn. With caching on, backends that support it charge much less for that repeated part. It is a switch per provider; it appears only for backends where it can be controlled (Claude through the Anthropic API or through Copilot). Other backends cache on their own, or not at all, and the page says so. The default is on. In the file: prompt_cache: auto or off on a provider.

Fallbacks #

A fallback tells the proxy what to try when a model cannot answer: its account is out of chats or credit, the backend is overloaded, or it is unreachable. Pick the model, then add the fallbacks in the order to try them; move them with the arrows. A model cannot fall back to itself, and a name can be listed once.

A fallback happens only before any output has been sent, and only for failures another backend could fix. Bad credentials and malformed requests are never retried elsewhere, and a fallback's own fallbacks are not followed. Nothing falls back unless you add a rule. Responses from a fallback carry an X-Maple-Served-By header naming what answered. In the file: model_fallbacks.

Guards #

  • Context guard: for tools that do not know a model's window. Off sends the request as is, Truncate drops the oldest turns until it fits, and Refuse rejects it with a plain error. In the file: context_guard.
  • Repeat guard: stops a reply that has collapsed into repeating itself. Off by default. In the file: degenerate_guard.

Keeping the cache useful #

Two more settings, both on the same Guards card, help a provider's prompt cache do its job on long conversations:

  • Prefix stabiliser (prefix_stabilizer, on by default). Some tools resend their tool list in a different order, or put the current time in the system prompt, which stops the provider from reusing what it already read. The proxy puts the tools back in their first order and moves a changing line such as the time to the end of the last message. It never removes or rewrites a tool, and it leaves alone any tool that manages its own caching.
  • Trim old tool results (context_trim, off by default). Once a conversation is long, the content of old, large tool results is replaced by a short note ("ask again if needed"), a batch at a time, so the provider does not have to read the same output on every turn. Recent turns, your messages and the system prompt are never touched. The card lets you set when it starts, how many recent turns it spares, and the smallest result it replaces. Turn it on for long runs with large tool output; leave it off for short sessions.

Responses say what was done in the X-Maple-Prefix-Stabilized and X-Maple-Tool-Results-Trimmed headers.

Daily budgets #

For each provider you can set a limit on requests per day, on the AI units a day, or both; leave a box empty for no limit on that measure. Days are UTC, and today's use is shown next to each limit. When a provider reaches its limit, requests for it are refused, or handed to its fallback if you set one. In the file: budgets.

Limits and hosts (restart required) #

These are read when the proxy starts, so after saving, stop and start maple-proxy for them to apply.

  • Rate limit: how many requests one client may make. The default is off for this machine and on, conservatively, for other machines. You can force it on or off and set the requests per minute, the burst, how many may run at once, and whether clients are counted per token or per address.
  • Allowed hosts: extra names the proxy answers to, one per line, for example a Tailscale name such as box.tailnet-name.ts.net. Names only: no https://, no path.
  • Usage log: a file that gets one line per request. Budgets are counted from it, so set it if you use budgets and want the counts to survive a restart.

If you prefer files, all of this lives in config.yaml (usually ~/.config/maple-harness/config.yaml):

model_fallbacks:
  cloud: [local]            # cloud and local are model aliases (see Connect a model server)
context_guard: truncate     # off | truncate | error
degenerate_guard: true
budgets:
  - provider: anthropic
    max_requests_per_day: 150
    max_ai_units_per_day: 20
server:
  allowed_hosts: [box.tailnet-name.ts.net]
  rate_limit:
    requests_per_minute: 120
    burst: 20
    max_concurrent: 4
  usage_ledger: /home/you/.config/maple-harness/usage.jsonl

Saving from the setup page rewrites config.yaml in its standard form, so comments you added by hand are not kept. Keys are never in it: they stay in your system keyring, and the file holds only a reference.

Using it from another machine #

By default only this machine can reach the model APIs. To let another machine on your network use them, set the listen address and create an access token with the proxy scope on the setup page:

server:
  openai_compat: 0.0.0.0:11535
  anthropic_compat: 0.0.0.0:11537
  allowed_hosts: [my-box.local]     # the name other machines use to reach it

The proxy refuses to start on a non-loopback address until such a token exists, and callers send it as Authorization: Bearer <token>. Requests from other machines are rate-limited. The setup page itself never listens beyond this machine.

Other useful commands #

maple-proxy auth status         # what is signed in
maple-proxy secrets status      # where each secret is stored (never its value)
maple-proxy audit tail          # who did what: token changes, refused requests
maple-proxy update              # install a newer release
