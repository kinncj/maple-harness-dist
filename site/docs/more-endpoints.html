More API routes: rerank, images, audio, files and pass-through #

Besides chat, the proxy's OpenAI-compatible address serves the other routes tools ask for: reranking, moderation, images, audio, files and batches. It can also pass a provider's own API through, for a tool that speaks Anthropic's, Gemini's or OpenAI's native API. Each one goes to a provider that offers it, with the same access tokens, model lists, budgets and usage log as chat.

Nothing to switch on, except pass-through

Nothing changes for a setup that does not use them: chat works exactly as before, and pass-through routes are off until you add one, on the setup page (Providers, Pass-through routes) or in config.yaml.

The short version

In plain words #

  • What it is. More of the OpenAI API at the proxy's address (http://127.0.0.1:11535/v1): /v1/rerank, /v1/moderations, /v1/images/..., /v1/audio/..., /v1/files and /v1/batches, and Anthropic's /v1/messages/batches. Each goes to the provider that serves the model you name. Reranking also works with the built-in search-by-meaning model, on your machine.
  • Why you want it. A tool that needs them (a RAG app that reranks, a script that makes images or transcribes audio) points at the proxy like a chat tool does, and its calls show up in the usage log, count against budgets and follow each person's model list.
  • The clicks. None. Use a model name the proxy lists, from a provider that offers the route. Pass-through routes are the one part you set up, on the setup page or in config.yaml (below).

Which providers #

A route is sent to the provider that serves the model asked for, at that provider's own address and with its key:

Provider typeThese routes
openai-compatible and the local servers (vLLM, llama.cpp, LM Studio, Ollama and others), openrouter, xai, gemini, litellm, a Maple hub (maple)Yes, for whatever the server itself offers (a server that has no /rerank answers with its own error)
anthropic with an API keyPass-through routes
bedrock, vertexPass-through routes only (one model's calls, below)
GitHub Copilot, Azure, Apple's on-device modelNo. The proxy answers 400 route_not_offered

If the model asked for is on a provider that does not offer the route, its fallbacks are tried, as for chat.

Rerank #

POST /v1/rerank (also /v2/rerank) takes the Cohere and Jina request shape and answers in it:

Shell
curl http://127.0.0.1:11535/v1/rerank -H 'Content-Type: application/json' -d '{
  "model": "builtin",
  "query": "how do I reset my password",
  "documents": ["Billing and invoices", "Resetting a forgotten password", "Two-factor sign-in"],
  "top_n": 2
}'
  • model: "builtin", the built-in model's own name, or no model ranks with the model set up for search by meaning, on your machine. Its score is how close each document is to the query in meaning: good for ordering, not a probability. It is not a dedicated reranking model.
  • Any other name goes to the provider serving it (Jina, Cohere, a vLLM or llama.cpp server with a reranker loaded, a LiteLLM gateway), and its answer comes back as that provider gives it.
  • documents may be strings or objects with text; at most 1,000 per request (256 with the built-in model).

Moderations, images and audio #

RouteBodyNotes
POST /v1/moderationsJSONNo model means omni-moderation-latest, which must then be a name the proxy serves. The built-in model and local classifiers answer on your machine (below)
POST /v1/images/generationsJSON
POST /v1/images/edits, /v1/images/variationsform uploadUp to 64 MB
POST /v1/audio/speechJSONThe audio is streamed back as it arrives
POST /v1/audio/transcriptions, /v1/audio/translationsform uploadUp to 64 MB

Every request must name a model the proxy serves (an id, an alias, a model group). The proxy sends the provider the model's own id.

Moderation on your machine #

/v1/moderations can also be answered without sending the text to a cloud service: by the proxy's built-in guardrails, or by a classification model you run yourself. Off until you set it up, on the setup page (Guards & limits, fold Moderation on this machine, which needs a page password) or with moderations: in config.yaml; without it, every moderation request goes to a provider as above.

YAML
guardrails:
  - name: no-secrets
    type: secrets
    default_on: false        # used only by the moderation model below, not on every chat request
  - name: no-pii
    type: pii
    default_on: false
moderations:
  builtin: [no-secrets, no-pii]   # the model "builtin": these guardrails, run on this machine
  classifiers:
    - name: local-toxicity        # the model name callers use
      provider: local-vllm        # a configured provider whose server runs the classifier
      model: unitary/toxic-bert   # the server's own model id (the name when left out)
      flag: [toxic]               # the model's labels that flag an input
      threshold: 0.5              # the score from which a flag label counts (0.5 when left out)
  • model: "builtin" runs the guardrails builtin names (built-in types only: secrets, pii, banned_terms, regex, size, prompt_injection) on each input. An input is flagged when one of them finds something; each guardrail is a category of the answer, with a score of 1 or 0. Nothing leaves the proxy, it costs nothing and, like the built-in rerank, writes no usage line. It finds what those guardrails look for (keys, personal data, your words and patterns), not harm categories such as hate or violence: for those, use a classifier or a provider's model. Anyone who may use the proxy can ask it, and its answer says which of those guardrails found something: name only guardrails whose findings you are happy for callers to see.
  • A classifier is a classification model on a server you run: vLLM's /classify (api: classify, the default) or Hugging Face Text Embeddings Inference's /predict (api: predict). The proxy sends the texts to that provider's server, at the root of its address (not under its /v1), with the provider's key, and answers in the moderation shape: each flag label is a category, flagged at or above threshold. Set path when the server serves its API elsewhere (it must end in /classify or /predict). It is asked like any request to that provider: model lists, budgets and a usage line (surface moderations).
  • Text only. The built-in model and classifiers check strings and {"type": "text"} parts; an image input is refused with 400. At most 256 inputs per request.
  • A guardrail can use any of these as its check: see the moderation type in Guardrails.

Prices for images and audio. These answers state no price, so a request costs nothing in the usage log until you give the model a price per unit, on the setup page (Providers, Model details and cloud accounts) or in config.yaml. The proxy then counts what the request used and records the cost as an estimate (list_cost_usd, price basis unit_price), which dollar budgets count:

YAML
providers:
  - id: openai
    type: openai-compatible
    base_url: https://api.openai.com/v1
    api_key: ${secret:openai}
    models:
      - id: dall-e-3
        unit_price: {per_image_usd: 0.04}          # each image the answer holds
      - id: tts-1
        unit_price: {per_million_chars_usd: 15}     # the characters of the text made into speech
      - id: whisper-1
        unit_price: {per_minute_usd: 0.006}        # the minutes of audio the answer says it transcribed

The prices are yours to set: take them from your provider's price page, and check its bill for what you were charged. Images are counted from the answer (the images it holds; a streamed answer counts the n asked for); speech from the request's input, in characters; transcriptions and translations from the duration the answer states (usage.seconds, or duration with response_format: verbose_json). An answer in another format states no duration and is not priced. A price the answer states itself (token usage the proxy can price) wins over unit_price, and a failed request is not priced.

Keys in lower case. A JSON body whose top-level object has two keys that differ only in case, or model, input_file_id or body written in another case ("Model"), is refused with 400: the proxy and the provider must read the same model. The same holds for each line of a batch file and its body.

Form uploads need an API key header. A form upload (multipart/form-data) is accepted only with an Authorization or x-api-key header, so a web page cannot send one on its own. The OpenAI SDKs always send one; with curl, add -H 'Authorization: Bearer maple' (any value on this machine, an access token from another machine).

Files and batches #

/v1/files and /v1/batches work as OpenAI's do, on a provider account you name, for example an OpenAI account with id: openai:

Shell
curl http://127.0.0.1:11535/v1/files?provider=openai -H 'Authorization: Bearer maple' \
  -F purpose=batch -F file=@requests.jsonl
curl http://127.0.0.1:11535/v1/batches -H 'Content-Type: application/json' \
  -d '{"input_file_id": "file-...", "endpoint": "/v1/chat/completions", "completion_window": "24h"}'
  • Name the account with ?provider=<id>, the X-Maple-Provider header, or a provider field in the upload form. Calls about a file or batch you made (read, download, delete, cancel, create a batch from a file) find the account by themselves.
  • Each caller sees only its own. The proxy remembers who uploaded each file and created each batch (an access token, and the person when people are set up). A list shows only yours; someone else's id answers 404.
  • Batch files are checked. Every model a batch file names must be one the caller may use, when the file is uploaded and again when the batch is created. A file of up to 200 MB is accepted.
  • Results. A completed batch's output and error files are its creator's, readable at /v1/files/<id>/content once the batch has been read as completed.
  • Usage. An upload and a batch's creation are lines in the usage log. When a batch is read and has ended (completed, or expired or cancelled with some requests finished), its token usage is recorded once, marked as the batch service tier, on the batch's first model. Reading a file's or a batch's details is not recorded, so polling adds nothing.
  • Budgets hold a batch's cost while it runs. With a dollar budget (an account's, a person's or a team's), a batch's estimated cost at the batch price is held from its creation: every request's input and its output limit (max_tokens, or the same bound as a chat request without one), priced as a chat request's hold is. A batch is admitted only when that estimate fits in what is left of the budget. Other requests see the budget as if it were spent, until the batch has ended and its usage is recorded. The proxy keeps the hold: it stays through a restart, and with several replicas it counts on all of them. When replicas share a usage store that refuses a batch's usage, the usage is kept and tried again, the batch stays held, and after 10 minutes an alert says so. About 10,000 batches are held at once, about 1,000 for one caller; another is answered 429 too_many_batches.
  • A batch the proxy cannot price is refused under a dollar budget. When a dollar budget applies and the proxy has no price for a model the batch names yet (no published list price, no request seen for it), the batch is refused with 400 batch_unpriced: its cost could not be held against the budget. Send a few of its requests on their own first, or run it without a dollar budget.
  • A batch whose usage is never read is still counted. When a batch's results or usage have not been read a day after its creation (25 hours), or it is deleted unread, its estimate is recorded in their place, labelled an estimate (price basis batch_estimate), and counts against the budgets; reading it later adds nothing. A batch that ran without a dollar budget on a model the proxy cannot price gets a line with no figure, so the usage log still shows it ran.

Anthropic's Message Batches #

/v1/messages/batches works as Anthropic's does, on an Anthropic account with an API key, at both the OpenAI-compatible address and the Anthropic-compatible one (http://127.0.0.1:11537), so the Anthropic SDKs' messages.batches work pointed at the proxy:

Shell
curl http://127.0.0.1:11537/v1/messages/batches -H 'Content-Type: application/json' -H 'anthropic-version: 2023-06-01' -d '{
  "requests": [
    {"custom_id": "q1", "params": {"model": "claude-sonnet-5", "max_tokens": 1024, "messages": [{"role": "user", "content": "Hello"}]}}
  ]}'
  • Which account. The one serving the requests' models (a model name the proxy serves, an alias; each is sent as the account's own id), which must be one Anthropic account for the whole batch. Or name it with ?provider=<id> or the X-Maple-Provider header, and use that account's own model ids. A list (GET /v1/messages/batches) needs the account named.
  • Each caller sees only its own, as for OpenAI's batches: someone else's batch answers 404, a list shows only yours. Every model the requests name must be on the caller's model list.
  • Results through the proxy. A batch's results_url is answered as the proxy's own path (/v1/messages/batches/<id>/results), so the results are read through the proxy with your proxy token.
  • Usage, once. When the results are read to the end, each model's usage is recorded once, as a line of its own (surface batches, the batch service tier), priced at Anthropic's batch price, an estimate. Requests that errored, were cancelled or expired cost nothing and are not counted.
  • Limits. A batch of up to 32 MB and 100,000 requests through the proxy (Anthropic takes up to 256 MB); at most 2 batches created at once, and 32 models in one batch.

Pass-through routes #

A pass-through route serves a provider's own API at /passthrough/<name>/ on the proxy's OpenAI-compatible address. A tool that speaks Anthropic's Messages API, Gemini's generateContent or another native API reaches the provider through the proxy: the proxy checks the caller, adds the provider's key, and records what the answer says it used. Off until you add one. A body that names an MCP server or connector for the provider to reach is refused, here and on the batch routes, unless you allow it (see Providers' own MCP connectors). A body that is not plain JSON the proxy can read in full is refused when the caller has a model list, since its model cannot be checked.

YAML
passthrough:
  - provider: anthropic           # a configured provider's id
    paths: ["/v1/messages"]       # required: only these paths (and the paths under them)
  - name: gemini-native           # optional: the route's name; the provider's id when left out
    provider: gemini
    paths: ["/v1beta/models"]
    cost_per_request_usd: 0.002   # optional: an estimated price for an answer that states no usage

With that, http://127.0.0.1:11535/passthrough/anthropic/v1/messages is Anthropic's /v1/messages. The version in the path (/v1, /v1beta) is matched against the provider's base_url, so it is not repeated.

Guardrails do not check these routes

Pass-through routes, like rerank, moderations, images, audio, files and batches, are passed to the provider as they are: guardrails check chat requests and MCP tool calls only. List only the paths a tool needs.

Bedrock and Vertex #

A route on a bedrock or vertex provider reaches one model's calls, signed with that provider's own cloud credentials, exactly as its chat requests are: the proxy signs a Bedrock request with AWS's SigV4 (or sends the provider's Bedrock API key), and gives a Vertex request a Google token. A tool that speaks the cloud's own API, or an SDK pointed at the route, needs no cloud credentials of its own.

YAML
passthrough:
  - provider: bedrock-us       # a type: bedrock provider
    paths: ["/model"]
  - provider: vertex-us        # a type: vertex provider
    paths: ["/publishers"]
Route onPaths it forwardsExample
bedrock/model/<model id>/ and one of invoke, invoke-with-response-stream, converse, converse-stream, count-tokens/passthrough/bedrock-us/model/us.anthropic.claude-sonnet-4-5-20250929-v1:0/converse
vertex/publishers/<publisher>/models/<model>: and one of generateContent, streamGenerateContent, countTokens, computeTokens, rawPredict, streamRawPredict, predict; or the same under /v1/projects/<project>/locations/<location>//passthrough/vertex-us/publishers/google/models/gemini-2.5-pro:generateContent

  • This provider's account only. A Bedrock route reaches the provider's region with its credentials. A Vertex route reaches the provider's own project and location: the short form /publishers/... is put there, and a whole path that names another project or location is refused.

  • Nothing else of the cloud's API. Asynchronous invocations, guardrails, endpoints, batch prediction jobs, cached contents, tuning and datasets are refused (400), whatever the route's paths say, and so is any method but POST. A Bedrock model is named by its id or inference profile id; an ARN (which holds /) cannot be used in the path.

  • The model is in the path, so a person's model list is checked against it, as bedrock-us/<model id>. A : in the id may be sent as is or encoded (%3A, as AWS's SDKs send it).

  • Usage. Converse and InvokeModel answers are read for their tokens, streamed or not (Bedrock's own stream framing included), and priced as the provider's chat requests are: Claude models at Anthropic's list price, an estimate. A stream that ends before Bedrock reports its usage counts what its events said so far; a Converse stream with none is estimated from the text it streamed and the request's size (price basis stream_estimate). Vertex answers are read in Gemini's and Anthropic's shapes. A Vertex stream is read with or without ?alt=sse; alt is the only query parameter sent on.

  • The key is the proxy's. The caller's own Authorization, x-api-key, cookies and forwarding headers are never sent on; only the content type, Accept, anthropic-version, anthropic-beta and OpenAI-Beta are. Query parameters that carry a key (key, api_key and the like) are dropped.

  • Only the paths you list. A route forwards only the paths in its paths, and the paths under them.

  • Account administration and kept state are never passed. Paths under organization, organizations or admin are refused, whatever the key can do. So are the routes where an account keeps things for whoever made them (files, batches, stored responses, vector stores, fine-tunes, assistants and threads, stored chat completions): every caller of the route would see everyone's. Use the proxy's own /v1/files and /v1/batches, which keep each caller's apart, and its own /v1/chat/completions and /v1/responses for chat.

  • The same rules as chat. A request that spends (POST, PUT, PATCH) from someone with a model list must name a model on it, in the body's model or in a Gemini path (/models/<model>:...); a person limited to their accounts reaches only those. Budgets and rate limits hold as for chat.

  • Cost. Usage the provider reports (Anthropic, OpenAI and Gemini shapes, streamed or not) is recorded and priced as for chat. cost_per_request_usd counts an estimate, labelled as one, against dollar budgets for an answer that states no price.

For the curious

Technical details #

  • Checks, in order: the surface's guards (address, token, same-origin, rate limit), the person's and team's model list and accounts, their rate limits and budgets, then the provider's daily and dollar budgets, exactly as for a chat request for the same model. A request is held to the provider it is admitted for.
  • Size limits: JSON bodies 16 MB (pass-through 32 MB, a Message Batch 32 MB), form uploads 64 MB, file uploads 200 MB (spooled to a temporary file and removed after); at most 16 JSON and pass-through requests, 2 Message Batches being created and 4 uploads of each kind at once per proxy (more are answered 429 with Retry-After); an upload sent with an Idempotency-Key is limited to 64 MB; an answer read whole to find its usage is capped at 64 MB. Streams and file downloads are passed through as they arrive.
  • Answer headers: only Content-Type, Content-Disposition, Retry-After and the provider's request id are passed back.
  • Usage log: each line's surface is rerank, moderations, images, audio, files, batches or passthrough (new values of an existing column; no new columns). Rerank and moderation with the built-in model, like /v1/embeddings, write no line: they run on your machine and cost nothing.
  • Where files and batches are remembered: files.json in the proxy's config folder, or, with several replicas (storage mode central), the shared store every replica reads, encrypted with the storage key. Records are kept for 60 days.
  • Paths: a pass-through path must be plain: no .. or . segment, no empty segment, no encoded characters, no backslash. Anything else is refused before it is sent.
