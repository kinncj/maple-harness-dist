    Several people can share one proxy, each with their own access token. The proxy then knows who sent every request, can give each person or team their own provider accounts, model list and budget, and lets each person see their own usage.

    If you use Maple on your own machine, you need none of this. Nothing on this page is on until you add it to config.yaml. A proxy without people:, teams: or default_accounts: routes, refuses and records requests exactly as before.

    Set up a team in four steps #

    1. Make a token for each person. On the proxy's setup page, open Remote access, add a device for each person with the proxy scope, and give each person their token. A token is shown once; treat it like a password.

    2. Add the people. Name each person, put them in a team if you like, and tie their token to them by its id (the setup page and maple-proxy people list show ids; config.yaml never holds a token itself):

      maple-proxy people add alice --team platform
maple-proxy people tie-token alice <token-id>

    3. Set budgets and rules (all optional):

      maple-proxy people budget alice --daily 40 --monthly 600
maple-proxy teams budget platform --monthly 2000
maple-proxy people models bob --allow coder-default,gpt-5

    4. Check the People card on the setup page: each person, their tokens by label, their budget used and left, and what they spent in the range you choose.

    The same in config.yaml:

    people:
  - id: alice
    team: platform
    tokens: [3f9c2a1b7d4e]          # token ids, never tokens
    budget: {daily_ai_units: 40, monthly_ai_units: 600}
    models:
      allow: [coder-default, "copilot/*"]
      fallbacks: {claude-opus-5: [claude-sonnet-5]}
    accounts: [copilot-work]
teams:
  - id: platform
    budget: {monthly_ai_units: 2000}
    accounts: [copilot-team]
default_accounts: [copilot-main]
people_self_view: "off"

    The People card and the maple-proxy people commands write the same keys and keep your comments. A change made on the setup page applies to the next request; one made with the command applies when the running proxy reloads its configuration or restarts.

    Who a request belongs to #

    • A request with a token belongs to the person that token is tied to. A proxy token tied to nobody still works; its requests are counted as unattributed and no person's rules apply to them. maple-proxy people list lists such tokens, so you can tie or revoke them.
    • On a proxy that listens only on this machine, a token is not required. A request that carries one anyway is checked, and refused if it is not valid, so a person working on the proxy's own machine is counted as themselves.
    • A request from this machine without a token belongs to the person local. Add a person with the id local to give that caller a team, a budget or rules; without one, local has no limits, as before. unattributed is reserved: it names requests tied to nobody.
    • The usage log records person and team on every request from then on. Requests from before people were set up stay unattributed.

    Budgets #

    A budget is in AI units, as the providers reported them: the same units as the provider budgets (budgets:). Set a daily limit, a monthly limit or both, per person and per team. Days and months are counted in UTC, so a daily budget resets at 00:00 UTC and a monthly one on the 1st.

    • A request is refused before it is sent once the person's or the team's budget is spent, with a 429 and the code budget_exceeded, in the API's own error shape. Other people are not affected.
    • A refusal for a team budget names the team but not its figures, which include other people's spend.
    • Requests that are already running when a budget runs out are allowed to finish. So a budget can be exceeded by what those last requests cost, and by nothing more. While requests are running, the proxy holds back each one's likely cost (the person's usual cost per request, and at least a small share of the budget), so only a few can start at once against a budget and a burst of parallel requests is refused.
    • What a provider reported for a request counts, even when the request then failed or was stopped part way. A request that failed with no cost reported, an answer from the response cache and the proxy's own cache-warming requests do not count.
    • Spend is read back from the usage log when the proxy starts, so a restart does not hand back a fresh budget. With the usage log off, budgets count from the moment the proxy started.
    • The usage log's budget_scope column says which budget counted a request: person, team or provider.

    Models #

    models.allow lists the models a person or a team may use: names as asked for (an alias such as coder-default, or auto), model ids, or account/model, with * as a wildcard (copilot/*; a name ending in /* also covers everything a hub passes on under it, such as hub/copilot-work/gpt-5). An empty list allows every model.

    • A person's list narrows their team's: a model must be allowed by both. A person without a list of their own has the team's. A person's list can never add a model the team's list leaves out; the People card points out an entry that reaches outside the team's.
    • A model that is not allowed is refused with a 403 and the code model_not_allowed (permission_error on the Anthropic-compatible address). The message says whose list refused it, the person's or the team's. A fallback to a model that is not allowed is skipped.
    • /v1/models lists only the models the person asking may use, on their own accounts or on the accounts assigned to them. A token tied to nobody, and a caller on this machine without a token when no local person is set up, see every model, as on a proxy without people.
    • models.fallbacks replaces model_fallbacks for that person or team, per model asked for. With an allow-list, it can send a model the person may not use to one they may: a request for claude-opus-5 answered by claude-sonnet-5. The usage log's route_reason then reads person-policy.

    Accounts #

    Each account (a provider entry, such as one GitHub Copilot sign-in) has an id and may have a nickname; either works in these lists.

    • accounts on a person, then on their team, then default_accounts for everyone, are tried first, in that order, for a model of their kind. A person on two accounts falls back from the first to the second the same way the proxy's own account fallback works. A request that names its account (copilot-work/gpt-5) is served there.
    • accounts_only: true limits a person or a team to their own accounts: anything that would be served by another account is refused with model_not_allowed. A person limited to their accounts may also use their team's, unless the team is limited to its own; then the person's accounts narrow the team's, and must be among them (the proxy refuses a config.yaml that lists another one, and says which team's list it is not on).
    • The usage log records the account that served each request (provider) and why it was used (account_source: person, team, default or request).

    You are responsible for following each provider's terms for the accounts you connect.

    The self view #

    With people_self_view: "on" (off by default; the switch is on the People card, or maple-proxy people self-view on), each person can ask the proxy for their own figures with their own token:

    curl -H "Authorization: Bearer $MAPLE_TOKEN" http://<proxy>:11535/v1/maple/me/usage?last=7d

    It answers with the person, the label of the token that asked, their own budget used and left, and their requests, tokens, AI units and estimated cost for the range, in total, by day and by model. since, until and last are the only parameters; whose figures they are is the token's to say, so there is no way to ask for anyone else's. It shows no team totals. It needs a valid proxy token even on this machine, is limited to 30 requests a minute per token, and answers 404 while it is off.

    Share one proxy with your team #

    On the proxy's machine #

    1. Set up the people as above.
    2. Let the proxy listen where your teammates can reach it, for example server.openai_compat: 0.0.0.0:11535 and server.anthropic_compat: 0.0.0.0:11537. Off this machine every request needs a token with the proxy scope; the proxy will not start that way until one exists. The setup page stays on this machine only.
    3. Reach it over HTTPS or a private network, such as Tailscale or a VPN. Plain HTTP across a network others share lets them read tokens.

    Signing in to providers, the setup page and maple-proxy commands all stay on this machine.

    On each teammate's machine #

    Each person uses their own token, with the proxy scope. Do not share tokens: every request made with one is counted as its person's.

    Maple Harness. Run maple-harness proxy connect https://proxy.example:11535 and paste the token when asked (it is not shown). The token goes into your secret store, and config.yaml gets only a reference (harness.proxy.token: ${secret:maple-proxy-token}). From then on every request carries it. The harness never starts or stops that proxy, and maple-harness auth tells you it runs on the proxy's machine. Check with maple-harness doctor: the proxy line should say the token was accepted. To keep the token in an environment variable instead, use --token-env MAPLE_PROXY_TOKEN. maple-harness proxy disconnect goes back to a proxy on your own machine.

    Plain http:// to another machine is refused unless you pass --allow-insecure, because it sends your token where the network can read it.

    Claude Code. Point it at the proxy's Anthropic-compatible address and give it your token as the key:

    export ANTHROPIC_BASE_URL=https://proxy.example:11537
export ANTHROPIC_API_KEY=<your token>

    OpenCode, or any OpenAI-compatible tool. Use the proxy's OpenAI-compatible address with /v1, such as https://proxy.example:11535/v1, and your token as the API key (in OpenCode, an openai-compatible provider entry with baseURL and apiKey). Keep the token in an environment variable rather than in a file you commit.

    Teams across chained hubs #

    When a proxy uses another Maple proxy as its parent, it inherits the parent's people, teams, their accounts, budgets and model rules, and the parent's tokens (as hashes, never the tokens), and passes them on to its own children.

    • What the proxy uses is the inherited people and teams plus its own. Inherited entries are read-only there: the People card marks them, and the commands refuse to change them.
    • A child may add its own people and teams. It may also tighten an inherited one by adding an entry with the same id: a lower budget, a narrower model or account list, or accounts_only: true. Anything that would loosen it (a higher budget, a model outside the inherited list, another team, its own tokens) is refused, and the inherited entry applies.
    • If a local entry clashes with an inherited one in any other way, the inherited entry wins and the People card lists the clash. The local entry's own tokens (and those of local people in a clashing team) are refused until you resolve it, so they never lose their rules by being counted as nobody's.
    • You can add people while the parent cannot be reached; a clash is reported once its people arrive.
    • An inherited token works at the child with the scopes it had, except the ones for chaining, administration and the setup page.
    • Budgets are counted at every hub a request passes through, each with its own rules. A hub takes a forwarded request as one of its own people only when that person signed in below with their own token; see Chain proxies into hubs.
    • The People card and maple-proxy people list show chain tokens apart from people's tokens, with the proxy each is bound to and the person it is tied to. Tie a chain token to a person to hold everything that proxy sends to that person's rules and budget.
    • If the child cannot get a current copy of its parent's people, it refuses the inherited people and tokens until it can, and keeps serving its own.

    Limits #

    • Budgets and spend are in AI units as the providers reported them; cost_estimated is an estimate from list prices. Neither is a bill.
    • Only requests with a token can be told apart. On a proxy that listens only on this machine, anyone on the machine can leave the token out and be counted as local; listen off this machine to require tokens.
    • /v1/models lists auto for a person when every model list that applies to them names auto, or when they have no model list; what auto picks is then held to their rules when it is asked for.
    • Requests already running are not stopped when a budget runs out (see Budgets).

    Going back to an older version #

    A proxy older than 2.0 ignores people:, teams:, default_accounts: and people_self_view: and keeps working: every token still works, but no person's budget, model list or accounts apply, and requests are no longer attributed. The keys stay in config.yaml and apply again after an upgrade. The usage log stays readable.
