    A cookbook of questions people ask of their usage, each with the command and what it printed. Every recipe here was run as shown; the output comes from a synthetic sample log (made-up people, models and traffic), so your figures will differ. Which store to query when is on Your data.

    Figures are AI units as the providers reported them, or list-price estimates named _estimated. Neither is a bill, and the two are never added together.

    In plain words #

    • What it is. Recipes: the questions people ask of their usage, each with the command and its output.
    • What to do. Copy a recipe and run it. maple-proxy usage query needs nothing else; the DuckDB recipes need the duckdb program. The setup page's Data & storage tab has the commands to start DuckDB on your own log.

    Before you start #

    • maple-proxy usage query needs nothing else. It reads the daily files on this machine, and in central mode the shared PostgreSQL, so run it on a replica there. It works whether the proxy is running or not.
    • DuckDB recipes need DuckDB's command line (install it), plus INSTALL ducklake once for the lake and INSTALL postgres once for PostgreSQL.
    • -table in the commands below only makes DuckDB print plain-text tables; leave it out for its usual boxes.

    With usage query #

    The filters and --group-by keys are listed in Filter your data; --metrics picks the columns (maple-proxy usage query --help lists them all).

  Person: unattributed (- in JSON and CSV) is a request no person was recorded for: sent before people were set

    unattributed is requests no person was recorded for: sent before people were set up, or with an access token tied to no person. local (not in this example) is a request from the proxy's own machine without an access token, once people are set up. In --format json and --format csv the unattributed group is -, and --person unattributed and --person - both pick it. The same way, no team is requests whose person has no team, or that have no person; JSON and CSV show -, and --team - picks it. For week by week, group by day and add the days up in a spreadsheet, or use the DuckDB recipe over PostgreSQL.

    A roll-up per hub #

    On a top hub with proxies below it, by the proxy each request started on:

    $ maple-proxy usage query --group-by origin_proxy --metrics client_requests,requests,ai_units_spent
Usage  (all requests)
  ORIGIN_PROXY  CLIENT_REQUESTS  REQUESTS  AI_UNITS_SPENT
  alice-laptop               15        34           4.950
  platform-hub                8        16           2.640
  top-hub                     4         4           1.320
  total                      27        54           8.910

  Includes the usage children sent up. requests counts lines, one per proxy a request passed through; client_requests counts each request once, and ai_units_spent and cost_estimated_spent count spend once, where it was spent.

    Use client_requests and ai_units_spent to count each request and its spend once; requests counts a line on every proxy a request passed through. Add person to --group-by for who asked.

    With DuckDB #

    The same records, in plain SQL. Each source below gives you a usage table or view and the named views (maple.requests, maple.daily_spend, maple.sessions, maple.people and the rest), so a query written for one works on the others.

    The daily files #

    maple-proxy usage schema --format sql --views > maple.sql
duckdb -cmd ".read maple.sql"

    Spend by provider, week by week (saved as weekly-provider.sql):

    SELECT date_trunc('week', day)::DATE AS week, provider,
       sum(requests) AS requests, round(sum(ai_units), 1) AS ai_units
FROM maple.daily_spend
WHERE day >= DATE '2026-09-21' AND day < DATE '2026-10-05'
GROUP BY ALL
ORDER BY week, ai_units DESC;

    The cache hit rate by tool, counted in requests rather than tokens (saved as cache-by-tool.sql):

    SELECT agent,
       count(*) FILTER (WHERE cache_class = 'hit') AS hits,
       count(*) FILTER (WHERE cache_class IN ('hit', 'partial', 'miss', 'lost')) AS classified,
       round(100.0 * hits / classified, 1) AS hit_pct
FROM maple.requests
WHERE day >= DATE '2026-10-02'
GROUP BY agent
ORDER BY classified DESC;
    $ duckdb -table -cmd ".read maple.sql" -f cache-by-tool.sql

| other         | 392  | 698        | 56.2    |
| opencode      | 292  | 490        | 59.6    |

    Over many months the daily files are many files; maple-proxy usage compact packs them into one Parquet file per month, and --source parquet-monthly makes the same views over those (Lots of history?).

    The DuckDB file #

    maple-proxy usage duckdb loads the daily files into one DuckDB file and, run again, adds only what they gained:

    $ maple-proxy usage duckdb
/home/demo/.config/maple-harness/usage/analytics/maple_usage.duckdb: 68,469 request row(s), 0 event row(s); loaded 68,469 new line(s) from 120 daily file(s) in 636ms
query it: duckdb /home/demo/.config/maple-harness/usage/analytics/maple_usage.duckdb -c "SELECT * FROM maple.daily_spend ORDER BY day DESC LIMIT 20"

    The two biggest models of each month (saved as monthly-model.sql):

    SELECT date_trunc('month', day)::DATE AS month, model,
       sum(requests) AS requests, round(sum(ai_units), 1) AS ai_units
FROM maple.daily_spend
GROUP BY month, model
QUALIFY row_number() OVER (PARTITION BY month ORDER BY sum(ai_units) DESC) <= 2
ORDER BY month, ai_units DESC;

    PostgreSQL #

    In central mode, two ways to read the shared PostgreSQL from DuckDB, both read-only. Use a role that can only read (the grants). In storage mode redis there is no PostgreSQL: usage schema --source postgres is refused and says so; usage query and usage export on a replica read every replica's usage.

    The named views over PostgreSQL. The connection string stays in an environment variable and is read when you query; it is never written into the SQL:

    export MAPLE_POSTGRES_DSN='postgres://analyst@db.example:5432/maple?sslmode=require'
export PGPASSWORD='...'      # kept out of the connection string
maple-proxy usage schema --source postgres --dsn-env MAPLE_POSTGRES_DSN --views > maple-pg.sql

    Spend by person per week for one team (saved as weekly-person.sql):

    SELECT date_trunc('week', day)::DATE AS week, person, team,
       sum(requests) AS requests, round(sum(ai_units), 1) AS ai_units
FROM maple.daily_spend
WHERE team = 'platform' AND day >= DATE '2026-09-21' AND day < DATE '2026-10-05'
GROUP BY ALL
ORDER BY week, ai_units DESC;
    $ duckdb -table -cmd ".read maple-pg.sql" -f weekly-person.sql
+------------+--------+----------+----------+----------+
|    week    | person |   team   | requests | ai_units |
+------------+--------+----------+----------+----------+

| 2026-09-21 | lena   | platform | 1408     | 529.8    |

    ATTACH, for your own SQL over the typed view maple_usage_rows (every usage column). The password comes from PGPASSWORD, so it is not in the file (saved as attach-pg.sql):

    ATTACH 'host=127.0.0.1 port=25432 dbname=maple user=analyst' AS live (TYPE postgres, READ_ONLY);
SELECT provider, error_class, count(*) AS errors
FROM live.public.maple_usage_rows
WHERE error_class IS NOT NULL AND "at" >= TIMESTAMPTZ '2026-10-08 00:00:00+00'
GROUP BY ALL
ORDER BY errors DESC
LIMIT 5;
    $ duckdb -table -f attach-pg.sql
+----------------+-----------------+--------+
|    provider    |   error_class   | errors |
+----------------+-----------------+--------+
| github-copilot | server error    | 14     |
| github-copilot | quota exhausted | 9      |
| github-copilot | overloaded      | 8      |
| github-copilot | unreachable     | 7      |
| github-copilot | canceled        | 6      |
+----------------+-----------------+--------+

    PostgreSQL holds only storage.retention_days; for anything older, query the lake. Reading PostgreSQL through these views is slower than reading the lake, and every query is work for the live database: for long ranges and dashboards, prefer the lake.

    Into a spreadsheet #

    A summary as CSV. Any usage query prints CSV with --format csv; the notes go to the terminal, not the file:

    $ maple-proxy usage query --since 2026-09-01 --until 2026-10-01 --group-by day,provider --metrics requests,ai_units,cost_estimated --format csv > september.csv
note: Figures named _estimated are the proxy's estimates, not measurements or bills.
$ head -4 september.csv
day,provider,requests,ai_units,cost_estimated
2026-09-01,github-copilot,447,189.95708199999996,
2026-09-01,anthropic,115,91.76395600000001,16.934755000000003
2026-09-01,ollama,27,0,

    Every request as CSV (or Parquet), with every column of the usage record:

    $ maple-proxy usage export --format csv --since 2026-09-01 --until 2026-10-01 --out usage-september.csv
wrote 17211 request(s) from 91 file(s) to usage-september.csv

    An Excel file from DuckDB, from any source above. DuckDB's excel extension writes .xlsx (INSTALL excel once). From the lake, a daily summary over its whole history (saved as xlsx.sql):

    LOAD excel;
COPY (
  SELECT day, provider, model, sum(requests) AS requests, round(sum(ai_units), 3) AS ai_units
  FROM maple.daily_spend
  GROUP BY ALL
  ORDER BY day, provider, model
) TO 'daily-spend.xlsx' WITH (FORMAT xlsx, HEADER true);
    duckdb -cmd ".read lake.sql" -f xlsx.sql

    Spreadsheets open the CSV and .xlsx files directly. The setup page's Usage data card also has an Export button for CSV or Parquet.
