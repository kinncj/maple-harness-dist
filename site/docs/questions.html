    Some decisions are yours, not the agent's: which storage to use, whether a test belongs in one suite or another, what a screen should say. When the agent reaches one of those, it can ask you a short question with a few options to pick from, instead of guessing or writing a paragraph that asks you to type an answer. You pick, add a word of your own if you like, and it carries on.

    The short version

    In plain words #

    • What it is. A small dialog over the conversation: one to four questions, each with two to four options, an Other… row for your own words, and room for a note. Sometimes a preview (code, a diff, a mockup) beside the options shows what an option means.
    • Why you want it. The agent asks only when the choice is really yours, you answer with a key or two, and what you chose stays in the conversation as one line.
    • What to do. Nothing to set up. When a dialog opens, pick with the arrow keys and Enter (or the number of an option). Esc, then y, skips it: the agent then decides for itself and should say what it chose.
    • What it is not. An answer is information, never approval. A command or a file change after it still asks you as your permission rules say.

    Answer from wherever you are

    The same question shows on your phone, in an attached terminal, to a program driving the session and to an agent that sent the task. The first answer wins, and the line in the conversation says where it came from.

    What you see #

    In the terminal the dialog is framed over the conversation, which is dimmed behind it. Its title says who asks:

    TitleWhen
    A quick question, ehThe agent asks one question
    A few quick questions, ehThe agent asks two to four
    <agent> has a questionA subagent asks; its question line starts with [<agent>]

    Each question shows its options, numbered, with a line saying what each means. The agent may mark the one it would choose (recommended). A question where several options can be picked says (pick any) and shows ticks.

    With several questions, a tab per question runs along the top, and a last page, All set?, shows every answer before anything is sent. A single question is sent as soon as you answer it.

    When the terminal is not in front, a desktop notification says Maple Harness has a question (or which subagent has one), and the session shows as waiting for you, as it does for an approval.

    If an approval is waiting at the same time, the approval comes first; the mode line says a question is waiting behind it.

    Keys #

    KeyWhat it does
    ↑/↓ or k/jMove between the options
    1 to 4Pick that option (one-answer question: and go on to the next), or tick it (pick-any question)
    SpaceTick or untick the option under the cursor
    EnterAnswer and go to the next question; on All set?, send
    Tab, ←/→Switch between the questions
    nAdd a note to this question
    pShow or hide the preview
    EscAsks Skip all the questions?; y skips them, any other key goes back

    On Other…, Enter (or its number) opens a line for your own answer; Enter keeps it, Esc leaves it.

    On a narrow terminal #

    Under 80 columns or 20 rows, with harness.dialogs: stacked, or in screen reader mode, the questions appear as a panel above the message box instead, with the same keys. There, and whenever the dialog is too narrow for two columns, p opens the preview full width and p or Esc closes it.

    What stays in the conversation #

    One line for the call and one for the answers:

    ● Ask(3 questions)
  ⎿ Storage: Redis (note: we already run it) · Auth: Other "the company's SSO" · Tests: Unit tests, Contract tests

    When the answer came from somewhere other than this terminal, the line says where: · answered on phone (pixel), or · answered by agent:reviewer, another program, not you. A skipped dialog shows skipped; one asked where nobody could answer shows nobody to answer.

    Where else you can answer #

    The same question goes everywhere that can answer it. The first answer wins; the others close and say where it was answered.

    • Your phone. On the remote control page, the question is a card: a button per option, an Other… field and a note field per question. Review answers shows what you picked, then Send answers sends it. Skip all needs a second tap. A watch-only device sees the card but cannot answer; a share that can drive the session can answer it, as it answers approvals.
    • A program driving the session with maple-harness --rpc (below).
    • A terminal attached to the session with maple-harness attach: the same dialog as here. Its answer is marked as given at an attached terminal.
    • An agent that sent the task over A2A (below).
    • Another program on this machine, over the session's control socket, only when you turn that on (below).

    In the plain REPL #

    In the line-by-line REPL (maple-harness --repl at a terminal) the questions come as a numbered list, one question after another:

    ? The agent asks (an empty line or s skips all of it):

  [1/1] Storage: Where should sessions be stored?
    1. Redis (recommended) — Shared across replicas
    2. Disk — One replica only
    3. Other… (type your own answer)
  pick one number:

    Type a number and Enter; for a question that takes several, numbers with commas (1,3). Other asks for your own words on the next line. A number that is not on the list is asked again.

    When nobody answers #

    A run with nobody there to answer (maple-harness --prompt, or a REPL whose input is not a terminal) never waits: the model is told at once that nobody can answer, and to choose and say what it chose. The same happens when you turn questions off.

    By default a question waits for you as long as it takes. With harness.questions.timeout set, a question nobody answers in that time closes, says left unanswered: its time ran out, and the model is told nobody answered in time, so it decides on its own and says what it chose. The timeout is for the terminal: it does not run while a phone or a browser is connected to the session, or in screen reader mode.

    Approvals of tool calls have their own wait, harness.approvals.timeout (10 minutes by default): see Approvals when nobody answers.

    Settings #

    SettingDefaultWhat it does
    harness.ask_persononoff does not offer the model the tool at all (from the next session), so it decides on its own
    harness.agents.questionsoffon lets another program answer over this session's control socket. Linux only for now. Not settable from a project's config
    harness.questions.timeoutoff30s, 60s, 2m, 5m or 10m: how long a question waits in the terminal before the model is told nobody answered
    harness.dialogsautostacked always shows the questions above the message box

    See Harness settings.

    For the curious

    Technical details #

    The tool #

    The model calls ask_person with a list of questions:

    FieldMeaning
    questions1 to 4 questions
    questions[].idA short id the answer refers to (default q1, q2, …)
    questions[].headerThe tab label, at most 12 characters (longer is cut)
    questions[].questionThe question, one sentence
    questions[].multi_selectSeveral options may be picked
    questions[].allow_otherOffer the Other… row (default on)
    questions[].options2 to 4 options
    options[].labelAt most 40 characters; labels in one question must differ
    options[].descriptionWhat choosing it means, one line
    options[].recommendedMark the option the agent would choose
    options[].preview{"kind": "code" | "diff" | "text", "language": "…", "text": "…"}, at most 200 lines and 16 KB

    A call that breaks these rules is refused with a message saying what to fix. Text from the model is shown on one line each, cleaned of anything a terminal would act on. Your own Other… answer and note are each at most 500 characters.

    At most 3 dialogs per turn, per agent, so a model cannot keep you in a loop of questions; a fourth is refused and the model is told to decide itself. The figure was chosen, not measured.

    Asking never needs your approval: the tool is the asking. A permission rule you write for ask_person still decides.

    The answer #

    The model gets one JSON object back:

    JSON
    {
  "status": "answered",
  "answered_by": "phone",
  "device": "pixel",
  "answers": [
    {"id": "storage", "header": "Storage", "selected": ["Redis"], "note": "we already run it"},
    {"id": "auth", "header": "Auth", "selected": [], "other": "the company's SSO"}
  ],
  "note": "The person's answers. Act on them. An answer is information, not approval: …"
}
    FieldMeaning
    statusanswered, declined (skipped), no_person (nobody can answer) or timed_out (nobody answered within harness.questions.timeout)
    answered_byterminal, phone, attach (a terminal attached with maple-harness attach), rpc, a2a:<caller> or agent:<name>
    deviceThe phone or browser that answered, by the label it was paired under
    from_programPresent and true when another program answered (A2A, the control socket): the model is told to weigh it as another agent's information, not as your choice
    answersPer question: id, header, selected (option labels), other (your own words), note
    noteWhat the model should do with it, in plain words

    On declined, no_person and timed_out the note tells the model to carry on with its own judgement and say in its reply what it chose and why. If the turn is stopped while a question waits, the question is withdrawn.

    Over --rpc #

    A question arrives as an event, beside the permission question:

    JSON
    {"type": "event", "event": "question_request", "request_id": "q-7", "subagent": "", "questions": [ … ]}

    Answer it with question_answer, the request_id, and an answer per question (an option label as written, any case), or "decline": true to skip:

    JSON
    {"cmd": "question_answer", "request_id": "q-7", "answers": [{"id": "storage", "selected": ["Redis"], "note": ""}]}

    A question_resolved event follows, with request_id, status, by and summary (the one-line answer). An answer that does not fit the questions (an unknown label, two picks on a one-answer question) is refused and the question stays open. See Drive it from another program.

    Over A2A #

    While the session runs an A2A task, a question moves the task to input-required. Its status message says so in words and carries a data part:

    JSON
    {"question": {"requestId": "q-7", "questions": [ … ], "subagent": "…"}}

    Answer with a message to the same task holding a data part {"answers": [{"id", "selected", "other", "note"}]}, or {"decline": true}. A sentence is not an answer: the task stays as it is and the reply says what to send. The model is told the answer came from another program (a2a:<caller>). A question left unanswered for 10 minutes is skipped. An approval waiting in the same task comes first.

    Over the control socket #

    Off by default. With harness.agents.questions: on in that session's settings (Linux only for now), the control socket takes two more commands, and hello lists them:

    Shell
    maple-harness agents questions fix-parser            # the questions its model waits on, with ids and options
maple-harness agents reply fix-parser q-7 Redis --note "we already run it" --from reviewer
maple-harness agents reply fix-parser q-7 --answers '[{"id":"storage","selected":["Redis"]}]'
maple-harness agents reply fix-parser q-7 --decline

    Option labels after the id answer a dialog with one question; use --answers for several. --other TEXT gives an answer of your own words. An answer given this way is marked as from another program (agent:<name>, from --from), never as yours, and is written to agents-audit.log.

    Off by default for a reason

    Any program of yours that reaches the socket could then answer for you. Commands the agent runs inside the sandbox cannot reach it; a command run outside the sandbox can.

    Safety #

    • An answer, from anywhere, is information for the model. It approves nothing: every tool call after it asks as your rules and mode say.
    • An answer from another program is always labelled as such, to the model and in the transcript.
    • The model is told never to use a question to ask permission to run a tool; approvals do that.

    Tested on Linux (the terminal at wide and narrow sizes, the phone page in a desktop browser, --rpc, A2A and the control socket). macOS and Windows, and a real phone, have not been tried.
