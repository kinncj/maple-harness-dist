    Commands and keys #

    On this page

    2. Modes and keys
    3. Reading the conversation
    4. How the interface looks
    5. Slash commands

    Everything you can type in Maple Harness, in one place: the keys and permission modes of a session, the slash commands, the commands you run from a shell, and the flags that start it. Each entry says what it does, its default and its trade-off. Settings in config.yaml are on Harness settings, and the proxy's on Proxy settings.

    Jump to:

    • Modes and keys ask, auto, yolo and plan, and every key in the message box and the transcript.
    • Steer or queue while it works Type mid-turn: correct the work now, or line up the next task.
    • Reading the conversation Calls, results, diffs, thinking and approvals, as the screen shows them.
    • Slash commands /model, /cost, /settings, /remote and the rest, grouped by job.
    • Commands you run from a shell Sessions, doctor, update, the gateway, services and more.
    • Command-line flags --prompt, --continue, --rpc and the others, with exit statuses.
    • Troubleshooting A key that does nothing, a copy that never arrives, a run that will not start.

    Each item has a Helps tag, because each exists to serve one or more of three goals:

    • Efficient: fewer tokens or AI units for the same work.
    • Efficacious: the work stays as good, and the safe choice is the default.
    • Effective: whole tasks succeed: the right model, and waste stopped before it grows.

    A tag appears only where it is true. Nothing here is a promise about your bill: measure your own tasks.

    The short version

    In plain words #

    • What it is. The list of everything you can type: slash commands in a session (/model, /cost, /remote), the keys, the modes, and the shell commands of both programs.
    • What to do. /help in a session lists the commands, ? on an empty message box lists every key, and Ctrl+P finds any command by what it does (forget conversation finds /clear). This page says what each does and its trade-off. For the setup page instead, see The proxy and its setup page.
    • The safe default. A session starts in ask mode: nothing is written and no command runs until you say yes.

    Five keys that get you through a first day, eh:

    1. Enter sends. While the model works, it steers the running turn or queues the message for after it.
    2. y, n or a answers an approval (a is yes for the rest of the session); v shows all of what is asked first.
    3. Esc stops the running turn; Ctrl-C twice quits.
    4. Shift+Tab switches between ask and auto.
    5. Ctrl+P opens the command palette, and ? the key map, whenever you forget the rest.

    Modes and keys #

    Permission modes decide what happens when the model wants to write a file or run a command.

    ModeWhat happensHelps
    ask (default)You are asked before each write or command. deny rules are absoluteEfficacious
    autoWrites and commands run without asking; deny rules still apply. Unlike yolo, it can be chosen with Shift+Tab or set in config.yamlEffective
    yoloEvery question is answered yes. deny rules and the sandbox still apply. It exists only when you start with --yolo; a config file can never turn it onEffective (in a disposable place only)
    plan (/plan)Read-only: the model can look but not change, and hands you a plan to approve. See Plan modeEfficacious
    KeyWhat it does
    / then typeOpens completion over built-in commands, your commands and your skills. Tab fills, ↑/↓ move, Enter runs
    EnterSends the message; while the model is busy, steers the running turn or queues it (see below)
    Ctrl+GWhile the model is busy: sends the message the other way from Enter (queued instead of steering, or the reverse); on an empty box, switches the last one you sent (see below)
    Shift+EnterA new line in the message box (Alt+Enter and Ctrl+J also work). The box grows to ten rows, counting a long line by the rows it wraps to, and then scrolls; a message can be as long as you like
    Shift+TabCycles mode: ask then auto (and yolo only when launched with --yolo)
    EscInterrupts the running turn, or clears the input when idle
    Ctrl-CClears the input; interrupts a turn; quits on a second press (with background agents working, k instead quits and keeps them working). With text selected and nothing running, it copies the selection instead of offering to quit
    y n aAnswers a tool approval (a = always, for this session)
    @Starts a file or folder of the project: a list of matches opens as you type (@pars finds internal/parser/), and Tab or Enter puts the path in your message without sending it; a folder keeps completing into it. At the very start of the message, subagents are offered first (@reviewer check this). The files are git's (tracked, and new ones not ignored) or, outside a repository, the folder's own, without hidden folders and node_modules
    The sidebarOn a wide terminal (140 columns and 24 rows or more), a column beside the conversation: the folder and branch, the model and how full its context is, the checklist, the files this conversation changed with the lines each added and removed (a click opens one in your editor; /changes lists them all; before the first change it says no files changed · clean ice), the language servers' errors and warnings with the files that have them (a click opens one), the subagents, and the MCP servers with any that are not connected and why. Where it does not fit (a narrow or short terminal), it folds into one line at the top of the screen, there only while it has something to say: the files changed (2 files +5 −1), the language servers' findings (LSP 2 errors · 1 warning) and MCP servers that are not connected; on a terminal under 12 rows, or with the sidebar off, the files changed are one note on the line below the box instead (2 files changed +5 −1). harness.sidebar sets it (auto, on or off), and Ctrl+P → Sidebar switches it for the session
    The line above the boxWhat is lined up: with the checklist on (harness.ledger: auto), its progress and the step being worked on (checklist 3/7 · now: write the parser tests), and the messages queued for after the turn (⏎ 2 queued, with ↑ on an empty box taking back your last)
    PastingA paste of six lines or more, or over 1,000 characters, goes into the message box as one chip, [Pasted text #1 · 120 lines], so the box stays readable. Sending puts the whole text where the chip is; the conversation shows the chip. Delete the chip to leave the paste out
    Ctrl+SThe session switcher, searched as you type: this session's subagents (opening one shows its transcript, as the tray does) and the saved sessions of this folder. A saved session opens beside this one, never in its place: in a new herdr tab of this workspace when you run in herdr, in a new tmux window inside tmux, and otherwise the command that resumes it is shown and copied, to run in another terminal. It starts with this session's config file and folders. In the switcher, Ctrl+E gives a session a title of your own (an empty title goes back to its first message; its name stays), and Ctrl+D deletes one and its history after you press y. A session another Maple Harness has open is marked with where it runs, and is neither opened a second time nor changed: two copies would overwrite each other
    Ctrl+RThe messages you sent from this project, newest first. Type to filter (any word of a message); Enter puts one back in the message box to send or change. They are kept in prompt-history.jsonl in the config folder, beside your saved sessions, readable by you only; a built-in command is kept without its arguments, and harness.prompt_history: false keeps nothing new
    TabOn an empty message box: move through the conversation. A bar marks one entry (the newest, or the one you last clicked); ↑/↓ or j/k move it, [/] jump to your message before or after (the start of each turn), g/G go to the first or last, Space or Enter fold or open it (on a tool call, its result), c copies it, e opens the file of a Read, Write or Edit in your editor ($VISUAL or $EDITOR, vi when neither is set; at the edit's line in vim, Neovim, nano, Emacs, micro, Helix, VS Code and similar), and Esc, Tab or typing a letter go back to the message box
    vOn an approval: all of what is being asked, in place of the transcript: the whole diff of an edit or a new file, the whole command, or every argument. It scrolls; y, n and a still answer from it, and Esc, q or ← go back to the question without answering. On a diff, s splits it in two halves, the old text beside the new with the changed words marked (from 82 columns; long lines wrap in their half), and s again goes back to one; the choice stays for the session
    Mouse wheelScrolls the transcript at any time: while the model works, while an approval or a list is open, and inside a subagent's transcript
    ↑ ↓Scroll the transcript while the message box is empty or an approval is waiting
    PgUp PgDnScroll a page, at any time. Ctrl+End jumps back to the bottom
    Ctrl+OExpand or fold everything folded: long tool output, file reads and searches (shown as "Read 120 lines"), reads and searches made together (shown as "Read 3 files, searched 1 pattern"; a call that failed stays in sight), and the model's thinking (folded to its first words once the answer is in)
    ClickOn a folded tool result or thought, or on the tool call above it, opens just that one; click it again (or its "click to fold" line) to fold it. On a file's path in the conversation (src/app.go, src/app.go:12, Read(src/app.go)), opens that file in your editor ($VISUAL or $EDITOR), at the line when one is given; only a file that exists opens. On a row of the agents tray, opens that subagent, or shows what that other agent shows now
    Click or drag in the message boxA click puts the cursor where it lands; a drag selects text and copies it (a double click selects a word, a triple click the line). With text selected, typing replaces it and Backspace or Delete removes it
    DragSelects text in the transcript, and letting go copies it. Dragging past the top or bottom scrolls. A double click selects a word, a triple click a line. The highlight stays until the next click or key
    Ctrl+YCopies the selected text; with nothing selected, the entry you last clicked; otherwise the last answer, as the Markdown the model wrote
    Shift+dragYour terminal's own selection, even while the mouse is captured (Option+drag in iTerm2). Copy it with your terminal's key, such as Ctrl+Shift+C or Cmd+C
    Ctrl+VPastes text, or a picture on the clipboard (macOS; Linux with wl-clipboard or xclip installed), which is saved under .mapleharness/pasted/ and put in your message as a chip, [Image #1 · 20261121-101010.png]: the model sees the picture when you send the message, and the text carries its path
    Drop a fileDropping files on the terminal window puts their paths in your message; a picture (png, jpeg, gif, webp) goes in as a chip, like a pasted one
    \ then EnterA new line, wherever the cursor is, for terminals where Shift+Enter arrives as a plain Enter (Alt+Enter and Ctrl+J work too)
    Ctrl+TMove into the agents tray (below); with nothing in it, the mode line says so
    ?On an empty message box: every key, grouped by where it works (Esc closes it)
    Ctrl+PThe command palette: every command, your own commands and skills, and the actions on keys. Type to filter by name or by what it does (forget conversation finds /clear); Enter or a click runs it, and a command that needs more goes to the message box with what you had typed. Tab and Shift+Tab move between its tabs: All, Commands (the built-in ones), Yours (your own commands and skills, when you have some), MCP prompts (the prompts your MCP servers offer, when they offer some) and Actions (what the keys do); the filter stays as you move
    Editing keysThe message box takes the usual editing keys: Ctrl+A/Ctrl+E (line start and end), Ctrl+W and Alt+Backspace (delete a word), Ctrl+U/Ctrl+K (delete to the start or end of the line), Alt+B/Alt+F (move by a word), Alt+</Alt+> (start and end of the message). Ctrl+P, Ctrl+T and Ctrl+Home/Ctrl+End are always the harness's keys, never editing ones; ↑/↓ move between the lines of a long message

    The message box and the status bar stay on the same rows whatever appears above them (an approval question, the agents tray, a list to choose from).

    Pictures in a message. A pasted or dropped picture is a chip in the message box. Nothing is read or sent until you send the message; delete the chip and the picture is not sent. When you send it, the picture is attached for the model to see and the chip becomes the file's path in your message, so the agent can also work with the file. One picture per message: with two chips the message is not sent, and the line says so. A model known not to take pictures (Apple's on-device model) refuses the message the same way, with what to do (remove the chip, or pick another model with /model), instead of dropping the picture without a word. While a turn runs, a message with a picture waits for you to send it after the turn. A file that is not a regular file (a device, a pipe) is never read.

    Copying. Drag to select and it's copied; Ctrl+Y or /copy copies the last answer. Nothing else needs learning. A copy goes to the clipboard two ways at once: through your terminal, which also works over SSH, and through wl-copy, xclip, xsel or pbcopy when one is installed. A terminal only takes the first if it lets programs set the clipboard; some ask you to turn that on. Inside tmux, add set -g set-clipboard on to your tmux configuration (or set -g allow-passthrough on). Through the terminal, a copy is cut at about 74 kB; the line under the status bar and the transcript say when that happens, and an installed clipboard program still gets all of it. A selection is copied as the transcript shows it, without the transcript's left margin: a long line the window wrapped is copied as separate lines, so use Ctrl+Y or /copy for an answer's exact text. To start with the mouse off, set mouse: false (configuration); /mouse on turns it on.

    Steer or queue while it works #

    The message box is never disabled: type while the model works. What you type then either steers the work in progress or queues for after it:

    • Steers (↳ steering): a correction or an addition, such as "also handle the empty list", "use the existing helper instead", "don't touch the migrations", or any short message without a "then". It reaches the model as soon as the tools it is running finish, inside the same turn.
    • Queues (⏎ queued): a next task, such as "then update the changelog", "after that, write the release notes", or a long message of several sentences. It runs as its own turn once this one ends, in order.
    • /steer <message> and /queue <message> decide it yourself, and so does Ctrl+G: pressed instead of Enter, it sends the message the other way (queued instead of steering, or steering instead of queued). While you type, the box's title says which Enter will do (Enter steers · Ctrl+G queue).
    • Ctrl+G on an empty box switches the last message you sent, while that still changes something: a steer the model has not read yet goes to the queue, and otherwise your newest queued message steers instead. A steer the model already read stays where it is, and the line under the box says so.
    • /queue on its own lists what is waiting, numbered. /queue edit N puts message N back in the box to change it and send it again, /queue rm N drops it, and /queue clear drops all of yours. Messages from other agents are marked and stay when you clear.
    • A steer that arrives as the model is already finishing its answer is sent next, as its own message, never lost.
    • Messages from the phone app, from another program over --rpc (its send command: Drive it from another program) and from other agents steer or queue by the same rules.

    Technically, a steer is added at the end of the conversation, as a message of its own, right before the model's next request in the same turn, after the tool calls already running finish (none is cut off). Nothing earlier in the conversation changes, so the provider's prompt cache keeps matching what it has seen.

    Built-in commands still run immediately. Efficient: you can correct course early without waiting for a turn to finish.

    Reading the conversation #

    In plain words: each thing the model does is one short line, named the way you would say it (Read(main.go), Bash(go test ./...), Search(pattern: "TODO")), with a mark that turns green when it worked and red when it failed. What came back sits under it. Long results are folded to a summary you can open, an edit is shown as the lines it changed, and the model's thinking is dimmed and folds away once the answer arrives. Efficacious: you can see what was done without reading all of it.

    Technically:

    • A call and its result. The result goes under its own call, after ⎿, even when a steer or a queued message was written while it ran, and when several calls run at once. A file read or a search is folded to a summary ("Read 120 lines"); a click, Ctrl+O, or Tab then Space opens it, coloured by the file's language. Reads and searches made together fold into one line, and subagents started together get a heading that counts them (● 3 agents · 2 running). Calls that change something are always shown one by one.
    • Edits. A real line diff, unchanged lines around it included, numbered from where it landed in the file, with the changed words of a replaced line in reverse video. Added and removed lines sit on a faint tint of their own colour (on a terminal with 256 colours or more; with 16 the text keeps its colour and its + or −), and the call's line is the diff's header: the file on a chip and its +N −M in the diff's colours. An edit of one occurrence says the line it starts on; an edit of every occurrence says so. A change is drawn as a diff only when the diff is exactly what will be written; otherwise its text is shown as it is.
    • Approvals. The question names the tool as the conversation does (Edit, Bash). Your answer goes on the call's own line (· allowed, ⎿ denied by you); one given on your phone or by another program says where (allowed on <device>). A very long command says how much of it is not shown; v shows all of it.
    • Answers as they stream. Each paragraph, list, table or code block is drawn formatted as soon as it is complete, exactly as it stays once the answer ends; only the part still being written is plain text, so nothing above it moves.
    • Thinking. Dimmed while it streams, then folded to its first words. harness.thinking_display sets folded (the default), open or hidden.
    • A running subagent. The line under its Agent(…) call says what it is doing (⎿ explore · turn 3 · reading main.go); the agents tray opens its whole transcript.
    • Messages from other agents show as ↘ from <sender>, never as your own words.
    • Questions from the agent. When the model asks you to choose between a few options, a dialog opens titled A quick question, eh (or <agent> has a question for a subagent): ↑/↓ move, 1-4 pick, Space ticks, Enter answers, Tab switches questions, n adds a note, p shows the preview, Esc then y skips. The conversation keeps one line of what you answered. See Questions the agent asks you.
    • Background commands that finish show one line ($ bg_1 finished · exit 0 after 3m 12s · go test ./...), and an idle agent is woken to read the result. See Background commands and monitors.
    • Resumed sessions show their calls with their files, commands, results and failures, as they looked live.
    • Narrow terminals. Where the approval question does not fit, its keys show alone ([y/n/a/v]) and the box under it says what each does; where it fits, the keys are said once, on the question, and the box says that Enter and Esc answer no. The activity line drops its notes before anything is cut, and the mode line drops its reminder (yolo keeps its warning). Checked at 40 columns.
    • Resizing the window. While you drag the window's edge, each size is drawn at once with the conversation as it was laid out (cut to fit), and the conversation is laid out again once, when you stop. A long conversation no longer lags behind the window or flashes while it catches up.

    How the interface looks #

    In plain words: Maple Harness keeps its maple colours and its sense of humour. Lists open as a framed box over the conversation, the permission mode is a coloured chip at the start of the status bar, /theme lets you try every theme on the whole screen before you keep one, and a long turn that went well ends with a short Canadian sign-off. Nothing playful ever touches an error, an approval, a refusal or a cost figure: those stay exact.

    Technically:

    • Dialogs. The command palette (Ctrl+P), the session switcher (Ctrl+S), the settings menu, the history (Ctrl+R), the theme picker, the model picker (/model) and a command's list of choices open as a framed dialog in the middle of the screen: the title in the top border after a small maple leaf, the keys in the bottom one. It is laid over the conversation, so nothing under it moves, and the conversation behind it is drawn in faint colours while it is open (not with no colour, and not in screen reader mode). A click on a row picks it; a click outside closes it, as Esc does. On a terminal under 80 columns or 20 rows, or when the list is taller than the conversation's rows, the same list is drawn above the message box as before; harness.dialogs: stacked always draws it there. The approval question is never a dialog: nothing covers it. The model's questions follow the same rule as the lists: a framed dialog where there is room, above the message box where there is not, in screen reader mode, or with stacked.
    • Keys said once. A list's keys are said beside its title (or in its border); the box under it then says the row under the cursor in full, which the list cuts to fit. When the keys do not fit beside the title, the box says them.
    • The mode chip. The status bar starts with the permission mode on a colour of its own: ask calm, auto warm, yolo red. The word is always there, so colour is never the only cue.
    • The context meter in the sidebar is a smooth bar of block characters on a thin track, in the accent colour, then the warning colour from 80% full and the error colour from 95%.
    • Themes. /theme opens the theme picker (new in 3.0: before, it printed the list of themes, which /theme list now does): moving through it re-themes the whole screen, the conversation included, with a sample line in the new colours; Enter keeps one (and saves it, as /theme <name> does), Esc or a click outside puts the old one back. /theme list prints the table. /theme auto follows Omarchy where it runs and elsewhere picks maple or maple-light from your terminal's background (a terminal that does not say keeps maple). Three themes from home: birch (light), northern-lights (dark) and toque (high contrast).
    • The start screen shows the beaver, a small M A P L E wordmark in a maple gradient (with 256 colours or more; the accent alone with fewer), and a tip.
    • After a long turn (20 seconds or more) that finished well, the mode line says how long it took, then a short sign-off (done in 4m12s · beauty), and a maple leaf falls onto it. A turn that failed or was stopped gets neither. With harness.animations: reduced the note stays and nothing falls; with off there is no note.
    • What's new. The first time you open the interface after updating to a new release, the start screen shows what is new in it, once (What's new in 3.0, eh); any key puts it away. It never shows on a first install, over a resumed conversation, or in a run without the full-screen interface (headless, --prompt, RPC, A2A).
    • Screen reader mode (harness.screen_reader: true): plain lines, each message labelled you:, maple: or tool:; the approval question starts approval needed:; the working line starts maple: and says the turn's word once; nothing moves, no boxes are drawn, lists are stacked, the sidebar is off, the start screen is words without the pixel-art beaver, and the note after a long turn is written into the conversation. The terminal bell rings when an approval waits and when a turn ends (harness.screen_reader_bell; on in screen reader mode, off otherwise unless you turn it on). This is a first version: it has not been checked with a real screen reader yet.
    • Checked at 40 columns, without true colour (256 and 16 colours), and with animations off. A dialog is drawn over the conversation without laying it out again, and moving quickly through the theme picker re-themes the screen for the row you stop on rather than for every row you pass.

    Slash commands #

    A slash command that this session does not have (not built in, and not one of your own commands or skills) is never sent to the model: Maple Harness says so and sends nothing. To send a message that starts with /, begin it with //; a path such as /etc/hosts at the start of a message is sent as it is.

    Session #

    CommandWhat it doesHelps
    /helpShows the commands and keys
    /clearStarts over: clears the screen and the conversation. Memory notes are keptEfficient
    /quit, /exitExit. With background agents still working they are stopped; /quit keep keeps them working until they finish (see When you quit with agents out)
    /sessionsLists saved sessions. Resume one with --session <name>Effective
    /fork [n]Copies the first n messages of this conversation, and only the stored history that belongs to them, into a new session, leaving this one untouched — bare /fork copies up to and including your last message, so "try that again, differently" needs no argument. It does not switch this view to the fork; resume it with --session <name>Effective
    /export [html|jsonl]Writes this conversation to a file (default jsonl) named after the session, in the working directory. Obvious secrets are redacted, but review it before sharingEffective
    /tree [list|save [name]|fork <n or name> [new-name]]Saved points inside this conversation.     Memory notes. The model saves a note with the remember tool by giving a kind (project, user, feedback or reference), a one-line title and the fact, and optionally why it matters, how to apply it, and a few tags. The harness writes every note in the same shape, so notes read the same whichever model wrote them, and they stay plain Markdown you can open and edit. Saying the same thing again updates the existing note instead of adding a copy, and an empty or oversized note is refused with the reason. Notes written by earlier versions still load. Project notes the model writes live in the project's .mapleharness/memory folder, which is not committed. The notes the harness writes on its own (the session-progress note at the end of a session, and the test and build commands it saves) live in your Maple Harness config folder under notes/<project>/, never inside the project; notes it wrote in the project folder before are moved there the next time a session starts. recall shows both kinds. The harness does not read or write project notes through a symbolic link: if .mapleharness or .mapleharness/memory is a link, the model's project notes are not used, and a note file that is a link is replaced when written, never written through.

    Session journal. After every turn the harness itself, not the model, records what the turn did: the files read and changed, the commands run and whether they passed, failed tool calls, and the model used. It is kept per session in your Maple Harness config folder, in a folder for each project (never inside the project itself), stays small (older sessions are removed), and passes through the same redaction as the rest of the harness. sessions rm removes a session's journal with it (and refuses a session another Maple Harness has open: quit that one first), and cleanup removes journals whose session is gone. The model can read this session's journal with recall and journal: true. When a test or build command has passed several times across different turns of this session, the harness saves it as a project memory note so the next session knows how to check its work. Only the plain command is saved: no environment variables in front of it, nothing chained after it, no redirections, and nothing at all if it carries something that looks like a credential. It never overwrites a note the model or you wrote, and it saves nothing that needs judgement. What a subagent reads, changes and runs goes in the same journal, marked with the subagent's name; memory notes are saved from your own session's commands only.

    Project index. Files the model writes or edits are re-indexed in the background shortly after each turn, only those files, so the index stays current during a session without slowing it down. Files changed some other way — a command, a subagent, your editor — are found after each turn too, recorded in the journal as changed from outside, and re-indexed the same way. Test files (_test.go) and build files such as go.mod and Makefile are recorded in the journal too, though the index leaves them out.

    Search by meaning. With a model for it set up in the proxy, history_search, recall and graph_search also rank results by what they mean, combined with the words they share, and recall gains a query argument. Without one they work exactly as before. See Search by meaning.

    Switching model mid-conversation. The first message on the new model carries one short note saying which model held the conversation, and that memory, the journal, history_search and the code index already hold what it would otherwise re-read. A switch back to a model that has already had the note gets a single line.

    Agents and the agents tray #

    Subagents are helper agents you define in .claude/agents/<name>.md (or ~/.claude/agents), or use from the built-in set. The model can hand them jobs, and you can run one yourself with @name <task> (Tab completes the name). While any run, a tray sits just above the message box:

    • a main row and one row per subagent, with a status mark, its name, what it is doing, elapsed time and tokens;
    • ↓ from an empty message box, or Ctrl+T, moves into it; ↑/↓ move between rows;
    • Enter, or a click on its row, opens that subagent's live transcript; the wheel and PgUp/PgDn scroll it; Esc, Enter, q, b, ←, Backspace or a click leaves it;
    • in a subagent's transcript, m (or Tab) writes to it: a running one reads your message at its next step, a finished one is resumed with its whole conversation. Enter sends, Esc drops it. See Background agents;
    • x then y stops the selected subagent; X then y stops every one still running (also Stop all agents in the palette); c collapses the tray to "N agents" on the status line.

    After the subagents come the background commands and monitors that are running or finished in the last 20 seconds ($ bg_1 go test ./... 3m 12s, ~ mon_1 watching tail -f ci.log 4 events · ends in 26m). On one of those rows, Enter shows the last 40 lines it printed (for you only), and x then y stops it; the agent is told you stopped it. See Background commands and monitors.

    The tray also lists the other agents this session talks to: each one the model sent a message to, and each one that sent this session a message (a herdr agent such as Claude Code or Codex, or another Maple session). Their rows come after the subagents, with what each is doing now (working, idle, waiting for an approval, done, or no longer there) and when the last message went either way. A row stays while that agent works or is blocked, and for two minutes after the last message. Enter or a click on its row shows what that agent shows now: a Maple session's last answer, a herdr agent's recent screen. When an agent this session wrote to stops working, the conversation says so (⇄ maple · api finished, or is waiting for an approval).

    Efficient: a subagent's long searches and tool output stay out of the main conversation, so the main conversation stays short. See Subagents.

Commands in it are redacted; it holds no prompt, file or tool output, and stays under a few megabytes. Written line by line, so a run that is killed still leaves what it did. maple-harness bench keeps one per run
    --message "text", or the text after the flagsStarts the interface with this as the first message, exactly as if you had typed it (a slash command, a skill or an @agent message works too): maple-harness --message "fix the failing test", maple-harness "fix the failing test", or maple-harness --continue "now the docs". A first word that names a command runs that command instead, and a single word close to a command's name (sesions) is refused as a likely typo, with the command it probably meant; --message always sends the text. Not with --prompt or --rpc
    --continue, --resume, --session NAMEResume the most recent session here, pick one to resume, or use a named session. A session started in another folder is resumed with a warning that its work continues in that folder. With no terminal on standard input, --resume reads nothing: it resumes this folder's only session, or lists them and asks for --session <name> or --continue
    --tag LABELLabels this session's requests in the proxy's usage log (repeatable, up to 8; k=v or a word, of letters, digits and . _ - : = /), so a tool that drives Maple Harness can count cost per unit of work with maple-proxy usage query --group-by tag. MAPLE_HARNESS_TAGS (comma-separated) does the same; both are added together
    --config PATHUse a specific config.yaml
    --yoloAllow yolo mode (see above)
    --tuiThe full-screen interface, which is the default anyway; kept so older scripts keep working
    --replUse the plain line-based interface instead of the full-screen one
    --rpcRead newline-delimited JSON commands from stdin and write newline-delimited JSON events to stdout, for scripting and IDE integration. See Drive it from another program
    --remoteAlso let another device drive this session. --remote-listen, --remote-tls, --remote-allow-host and --remote-insecure-http set how
    --allow-tool RULEAllows calls matching the rule without asking, for this run (repeatable): bash(go test*), read_file, or Claude Code's and Copilot CLI's forms (Bash(npm run test:*), shell(git:*)). Never a call a deny rule of yours matches. The run prints what it allows. See Rules for one run
    --deny-tool RULEDenies calls matching the rule, for this run (repeatable); always wins. Written without *, it also denies the command with arguments
    --policy FILERules for this run from a YAML or JSON file with allow, deny and ask lists, written as for --allow-tool
    --wait-for-resetWith --prompt: when every route is out of a provider's limit, waits for the reset the proxy says (within harness.limits.max_reset_wait) and carries on, instead of ending with status 75
    --refusal-exit-codeWith --prompt: exits with status 4 when a call was refused because nobody answered (as harness.approvals.refusal_exit_code: on)

    Some flags do not mix: --prompt runs one turn and cannot be combined with --remote or a first message; --rpc is its own way of driving the session and takes none of --prompt, --repl or --remote; --remote needs the full-screen interface, so not --repl. Each refusal says which.

    Exit status, for scripts:

    StatusMeans
    0The run finished
    1An error, said on the error stream; also a --prompt message that was not sent (an unknown slash command, or a cost preview left unconfirmed) and a run that cannot ask you on an unverified proxy (below)
    2An unknown command word or a bad flag: nothing ran
    3A --prompt run stopped because the same problem kept failing; it says what it tried
    4Only with --refusal-exit-code or harness.approvals.refusal_exit_code: on: a --prompt run that finished but refused a call because nobody answered
    5A --prompt "/goal …" run that ended with its goal not met (its turns or budget ran out, it paused, or it was judged impossible). See Loops
    75A --prompt run that stopped for a provider's limit instead of waiting it out (no --wait-for-reset, or a wait past harness.limits.max_reset_wait); --json-summary has limit_reset with when it lifts

    A question about a tool call that nobody answers within harness.approvals.timeout (10 minutes) is denied, and with no terminal on standard input it is denied at once: a piped y never approves. Each refusal is printed on the error stream with the rule that would allow it, and listed under refusals in --json-summary. See Approvals when nobody answers.

    A run that nobody can answer (--prompt, --rpc, serve, or no terminal) does not start when the proxy on this machine cannot be verified as yours: it exits with status 1 at once and prints This session cannot ask you, so it did not start. with the fixes. For CI jobs, see CI jobs and containers.

    Troubleshooting #

    What you seeWhyWhat to do
    Shift+Enter sends the message instead of starting a new lineSome terminals send Shift+Enter as a plain Enter\ then Enter, Alt+Enter or Ctrl+J all make a new line
    Shift+Tab never reaches yoloyolo exists only in a session started with --yolo; no config file can turn it onStart with maple-harness --yolo, in a disposable place only
    A drag or Ctrl+Y says copied, but nothing is on the clipboardThe terminal does not let programs set the clipboard, or tmux keeps it to itselfTurn that on in your terminal; in tmux add set -g set-clipboard on; or install wl-copy, xclip, xsel or pbcopy (Copying)
    A copy arrives cut shortThrough the terminal a copy stops at about 74 kB, and the line under the status bar says soInstall a clipboard program (above), which gets all of it
    Your terminal's own selection does not workMaple Harness has the mouseShift+drag (Option+drag in iTerm2), or /mouse off; mouse: false starts with it off
    Ctrl+V pastes no picture on LinuxReading a picture from the clipboard needs wl-clipboard or xclipInstall one, or drop the file on the window
    A message with a picture is not sentTwo picture chips in one message, or a model that takes no picturesKeep one chip, or pick another model with /model
    A message starting with / and a name answers that there is no such command, and nothing is sentIt is not a built-in, one of your commands or a skill; it is never sent to the modelCheck /help or Ctrl+P; to send text that starts with /, begin it with //
    maple-harness: unknown command "...": did you mean "..."? (exit status 2)The only word given is one or two letters away from a command's name, so it reads as a typo of that commandRun the command it names, or send the word as a message with maple-harness --message "your word"
    This session cannot ask you, so it did not start.A run nobody can answer (--prompt, --rpc, serve, no terminal) on a proxy that cannot be verified as yoursFollow the fixes it prints; for CI see CI jobs and containers
    No sidebarIt needs 140 columns and 24 rows, or it is off (harness.sidebar)Widen the window, or Ctrl+P → Sidebar for this session; narrower, it folds into one line at the top
    A saved session will not open from Ctrl+SAnother Maple Harness has it open, and two copies would overwrite each otherQuit that one first, or switch to the terminal where it runs
    Something else is offmaple-harness doctor checks the setup and says what to do; --report FILE writes a redacted bundle for a bug report
