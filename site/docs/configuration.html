    The harness reads the settings under harness: in config.yaml (usually ~/.config/maple-harness/config.yaml). The proxy's settings are in the same file and are covered in the Proxy settings. Changes under harness: apply the next time you start the harness; the proxy picks up its own changes without a restart.

    Every setting has a Helps column, because each exists to serve one or more of three goals:

    • Efficient: fewer tokens or AI units for the same work.
    • Efficacious: the work stays as good, and the safe choice is the default.
    • Effective: whole tasks succeed: the right model, and waste stopped before it grows.

    A tag appears only where it is true, and trade-offs are stated. Nothing here is a promise about your bill: measure your own tasks. Keys are written relative to harness:, so sandbox.mode means harness.sandbox.mode.

    Run /configuration in a session to see every setting's effective value, right now, and which file it came from. /configuration set <key> <value> changes one and saves it to your global config.yaml — for example /configuration set loop_guard.mode warn. Most settings here are read once when the harness starts, so a change through /configuration applies the next time you start, not to the session you set it from; the response says so.

    Per-project overrides #

    A project can carry its own .mapleharness/config.yaml (or .mapleharness/config.json) that changes some of harness:'s settings just for that project, on top of your global config.yaml. It only needs the keys it changes:

    # .mapleharness/config.yaml, committed with the project
default_model: gpt-6-sol
loop_guard: { mode: warn }

    Anything the project's file does not mention keeps your global value — setting loop_guard.mode above does not reset loop_guard.warn_after or anything else. A list (mcp_servers, sandbox.hide, and so on) is the exception: if the project's file names one at all, that is the whole list for this project, not an addition to your own.

    notifications.* stays governed by your global config only, whatever a project's file contains: a notification destination can be a command, and letting a cloned repository set one would let it run something whenever a session finishes, needs approval, or fails.

    Since this file runs from a cloned repository, the first time you run the harness in a project that has one (or a .claude/hooks.json, or a .mcp.json), it asks whether to trust it — naming exactly what it would run or apply. Say no, or run non-interactively, and the project's file has no effect: the session runs on your global config alone. maple-harness trust list | approve | forget manages the decision afterwards — the same one decision covers hook files too; see Tools, skills and hooks.

    Long conversations #

    When a conversation outgrows the model's window, older messages leave the model's view. Nothing is thrown away:

    1. Older parts of a long conversation stay searchable. Every message is stored, word for word, beside the saved session before it leaves the model's view, and the model can look any of it up again with the history_search tool: by words, a file path, a tool, or a message number. A search returns a few short snippets, so it never floods the conversation. The store is part of the session: --continue and --resume bring it back, a /fork or /clone gets its own copy, and removing the session removes it. It stays on your machine with the same file permissions as the session.
    2. In their place, a record built from the conversation itself: every request (the first one always), the files read and changed, the commands run and whether they passed, the names of failing tests, what failed, and the assistant's last words. It also quotes, word for word, the sentences from earlier replies that read like a decision, a requirement, a fix, a cause or an open item (digest_key_points). Credentials are replaced with a marker before it is written. It needs no model, no network and no credit, and it ends by telling the model which stored messages it replaces and that history_search finds them.
    3. By default, that is all. Making room sends no request to any model, so it costs nothing, in auto mode or not. A short line in the conversation says a record was kept and that earlier turns are searchable.
    4. A written summary, only if you ask for one with compress_with_model. With free, only a model on your own machine or network is asked. With on, the harness asks, in order: the model you just switched away from (it has read this conversation already); compress_model, or when that is not set the cheapest suitable model within compress_scope (a model on your own machine or network first); then the current model. A model already known to be out of credit, over its daily budget or rate limited is skipped without asking it. If the summary goes to a different provider or account than the one your session is on, a line in the conversation says where it went. The history is sent in pieces that each fit the model's window, and the answer streams, so a slow local model is not mistaken for a dead one. While this runs, the activity line says which model is summarising; Esc stops it and leaves the conversation as it was. /cost lists each summary request, with the model, apart from your turns; with no summary request there is no such line.

    The stored history is bounded: once a session's store grows very large, its oldest messages are dropped, and a search says which messages are no longer there. A /fork to an earlier message copies only the stored history that belongs to the messages it keeps. A session started under the name of one that was removed never sees the old session's history.

    If the proxy answers with a fallback that has a smaller window than the model you asked for, the harness works to the smaller window until your model answers again.

    Notifications #

    Messages to your phone or desktop when a session needs approval, stops with an error, or needs your guidance. They say which project and what happened, and nothing else: never a command, a file's content or an error's text. Off until you list a destination. Try it with maple-harness notify test.

    Separately from these, a session asks your terminal to show a desktop notification when a turn finishes or needs your approval, in the form your terminal understands: foot, kitty, Ghostty, WezTerm, iTerm2 and Windows Terminal are recognised, and other terminals get the most common form. Inside tmux, add set -g allow-passthrough on to your tmux configuration so it reaches the terminal. For a notification that does not depend on the terminal, set notifications.desktop: true, which uses notify-send on Linux and osascript on macOS.

    Housekeeping and appearance #

    KeyDefaultWhat it doesHelps
    retention.sessions_days30How old a saved session must be before cleanup treats it as oldEfficient
    retention.keep_per_dir5How many recent sessions per directory cleanup always keepsEfficient
    retention.auto_pruneoffRun what cleanup --yes would, once a day, when a session startsEfficient
    theme, theme_colorsthe default themeA colour theme by name, and per-role colour overrides
    mouseonThe mouse wheel scrolls in every state, a click opens one folded tool result or a subagent, and a drag selects text and copies it. Your terminal's own selection then needs Shift held (Option in iTerm2). false starts with the mouse off, which gives plain selection back, and the wheel scrolls only where the arrow keys do. /mouse on and /mouse off switch it while running
    animationsonHow much the interface moves. on: a leaf in the theme's colours while the model thinks, a spinner with the tool's name while a tool runs, a soft shimmer on the working line, a cursor at the end of a streaming answer, the context meter easing to its new value, a gentle pulse on an approval question, and a small note when a long turn finishes. reduced: a still symbol for each state and nothing moves (the elapsed time still counts). off: as reduced, without the streaming cursor and the note. on is reduced automatically when NO_COLOR is set, TERM is dumb or the output is not a terminal, and draws fewer frames over SSH. Nothing is redrawn for animation while the session is idle, and output is never slowed down
    image_pasteautoCtrl+V with a picture on the clipboard saves it into the project and puts its path in your message (macOS; Linux with wl-clipboard or xclip), and dropped pictures are attached. off pastes text only, and dropped pictures go in as paths
    image_paste_commandnoneA command that reads the clipboard picture instead of the built-in reader, on macOS or Linux (for example pngpaste -). It runs directly, not through a shell (write sh -c '…' for one). If an argument contains {path}, the command writes the picture to that file; otherwise it prints the picture to its output. PNG, JPEG, GIF, WebP and BMP are accepted, up to 20 MB and 3 seconds. A non-zero exit or anything that is not a picture means there is no picture, and Ctrl+V pastes text
    system_promptnoneText added to the harness's base instructionsEffective
    engineering_prompt_modeautoWhether a short engineering-standards note is added: auto (only when the project has no AGENTS.md or CLAUDE.md), always or neverEfficacious
    engineering_promptbuilt inReplaces the text of that noteEfficacious

    theme also takes any of the following built-in names (/theme lists them the same way), or theme_colors can override individual roles (accent, deep, light, text, muted, faint, ok, warn, err) on top of any of them:

    • Dark: maple (default), ocean, forest, mono, dracula, nord, gruvbox, catppuccin-mocha, tokyo-night, solarized-dark, monokai, one-dark, everforest, rose-pine, hackerman (the green-on-black terminal look, a community nickname rather than one published scheme)
    • Light, for a light terminal background: maple-light, gruvbox-light, catppuccin-latte, solarized-light, one-light
    • Colour-vision-deficiency-friendly: colorblind-dark, colorblind-light — the status colours (not just the accent) are chosen from the Okabe–Ito palette to stay distinguishable under red-green colour blindness, the most common form. This is a design choice, not a certification: nothing here has been tested against colour-vision simulation software.
    • auto: on a machine running Omarchy, follows the desktop's own active theme (whatever omarchy theme current reports), and keeps following it while Maple Harness runs: switch the Omarchy theme and Maple Harness's colours change within a couple of seconds, including what is already on screen. A desktop theme with a Maple equivalent uses it; one without (Kanagawa, for example) takes its colours from the Omarchy theme itself. theme_colors still applies on top. Choosing another theme with /theme <name> stops following until you choose /theme auto again. Everywhere else, including a Linux machine not running Omarchy, macOS or Windows, auto is maple.

    Most of the dark and light themes reproduce a well-known published colour scheme (Dracula, Nord, Gruvbox, Catppuccin, Tokyo Night, Solarized, Monokai, One Dark/Light, Everforest, Rosé Pine), so it looks the same here as it does in an editor or terminal already set up with it.

    KeyDefaultWhat it does

    An annotated example #

    version: 1

harness:
  default_model: gpt-6-sol          # or an alias
  auto_model: false                 # true: /model auto on from the start
  auto_model_map:                   # pin what auto uses for each kind of work
    heavy: gpt-6-sol
  auto_avoid: ["*-codex*"]          # the default; [] to allow them
  effort: medium
  compress_with_model: off          # off (no summary request, no cost) | free | on
  compress_model: gpt-6-sol-mini    # with it on: who summarises; unset picks the cheapest suitable
  compress_scope: same-account      # same-account | same-provider | any
  digest_key_points: on             # quote decisions, fixes, open items from earlier replies; off to leave them out

  permission:
    mode: ask                       # ask | auto | yolo (yolo needs --yolo)
    rules:
      - { pattern: read_file, decision: allow }
      - { pattern: "bash(rm -rf*)", decision: deny }

  sandbox:
    mode: auto                      # off | auto | strict
    network: allow                  # allow | deny
    when_unattended: off            # on: contain commands in auto and yolo mode
  file_policy:
    read: hidden-only               # hidden-only | project | anywhere

  loop_guard: { mode: stop, warn_after: 3, stop_after: 6 }
  tool_output: { failed_max_lines: 120 }   # 0 = never shorten
  lsp: auto                         # auto | off
  bash_file_writes: warn            # warn | deny | allow
  ledger: "off"                     # off | auto

  subagents: { max_parallel: 3, max_turns: 50 }

  notifications:
    desktop: true
    events: [approval, error, stalled]

  retention: { sessions_days: 30, keep_per_dir: 5, auto_prune: false }
