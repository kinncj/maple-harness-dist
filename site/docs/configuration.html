Harness reference: config.yaml #

The harness reads the settings under harness: in config.yaml (usually ~/.config/maple-harness/config.yaml). The proxy's settings are in the same file and are covered in the Proxy reference. Changes under harness: apply the next time you start the harness; the proxy picks up its own changes without a restart.

Every setting has a Helps column, because each exists to serve one or more of three goals:

  • Efficient: fewer tokens or AI units for the same work.
  • Efficacious: the work stays as good, and the safe choice is the default.
  • Effective: whole tasks succeed: the right model, and waste stopped before it grows.

A tag appears only where it is true, and trade-offs are stated. Nothing here is a promise about your bill: measure your own tasks. Keys are written relative to harness:, so sandbox.mode means harness.sandbox.mode.

Run /configuration in a session to see every setting's effective value, right now, and which file it came from. /configuration set <key> <value> changes one and saves it to your global config.yaml — for example /configuration set loop_guard.mode warn. Most settings here are read once when the harness starts, so a change through /configuration applies the next time you start, not to the session you set it from; the response says so.

Per-project overrides #

A project can carry its own .mapleharness/config.yaml (or .mapleharness/config.json) that changes some of harness:'s settings just for that project, on top of your global config.yaml. It only needs the keys it changes:

# .mapleharness/config.yaml, committed with the project
default_model: gpt-6-sol
loop_guard: { mode: warn }

Anything the project's file does not mention keeps your global value — setting loop_guard.mode above does not reset loop_guard.warn_after or anything else. A list (mcp_servers, sandbox.hide, and so on) is the exception: if the project's file names one at all, that is the whole list for this project, not an addition to your own.

notifications.* stays governed by your global config only, whatever a project's file contains: a notification destination can be a command, and letting a cloned repository set one would let it run something whenever a session finishes, needs approval, or fails.

Since this file runs from a cloned repository, the first time you run the harness in a project that has one (or a .claude/hooks.json, or a .mcp.json), it asks whether to trust it — naming exactly what it would run or apply. Say no, or run non-interactively, and the project's file has no effect: the session runs on your global config alone. maple-harness trust list | approve | forget manages the decision afterwards — the same one decision covers hook files too; see Tools, skills and hooks.

Notifications #

Messages to your phone or desktop when a session needs approval, stops with an error, or needs your guidance. They say which project and what happened, and nothing else: never a command, a file's content or an error's text. Off until you list a destination. Try it with maple-harness notify test.

theme also takes any of the following built-in names (/theme lists them the same way), or theme_colors can override individual roles (accent, deep, light, text, muted, faint, ok, warn, err) on top of any of them:

  • Dark: maple (default), ocean, forest, mono, dracula, nord, gruvbox, catppuccin-mocha, tokyo-night, solarized-dark, monokai, one-dark, everforest, rose-pine, hackerman (the green-on-black terminal look, a community nickname rather than one published scheme)
  • Light, for a light terminal background: maple-light, gruvbox-light, catppuccin-latte, solarized-light, one-light
  • Colour-vision-deficiency-friendly: colorblind-dark, colorblind-light — the status colours (not just the accent) are chosen from the Okabe–Ito palette to stay distinguishable under red-green colour blindness, the most common form. This is a design choice, not a certification: nothing here has been tested against colour-vision simulation software.
  • auto: on a machine running Omarchy, follows the desktop's own active theme (whatever omarchy theme current reports); falls back to maple everywhere else, including a plain "not running Omarchy" Linux machine, macOS or Windows. A desktop theme with no close Maple equivalent falls back to maple too.

Most of the dark and light themes reproduce a well-known published colour scheme (Dracula, Nord, Gruvbox, Catppuccin, Tokyo Night, Solarized, Monokai, One Dark/Light, Everforest, Rosé Pine), so it looks the same here as it does in an editor or terminal already set up with it.

An annotated example #

version: 1

harness:
  default_model: gpt-6-sol          # or an alias
  auto_model: false                 # true: /model auto on from the start
  auto_model_map:                   # pin what auto uses for each kind of work
    heavy: gpt-6-sol
  auto_avoid: ["*-codex*"]          # the default; [] to allow them
  effort: medium

  permission:
    mode: ask                       # ask | auto | yolo (yolo needs --yolo)
    rules:
      - { pattern: read_file, decision: allow }
      - { pattern: "bash(rm -rf*)", decision: deny }

  sandbox:
    mode: auto                      # off | auto | strict
    network: allow                  # allow | deny
  file_policy:
    read: hidden-only               # hidden-only | project | anywhere

  loop_guard: { mode: stop, warn_after: 3, stop_after: 6 }
  tool_output: { failed_max_lines: 120 }   # 0 = never shorten
  lsp: auto                         # auto | off
  bash_file_writes: warn            # warn | deny | allow
  ledger: "off"                     # off | auto

  subagents: { max_parallel: 3, max_turns: 50 }

  notifications:
    desktop: true
    events: [approval, error, stalled]

  retention: { sessions_days: 30, keep_per_dir: 5, auto_prune: false }
