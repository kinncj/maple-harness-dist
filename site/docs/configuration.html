The harness reads the settings under harness: in config.yaml (usually ~/.config/maple-harness/config.yaml). The proxy's settings are in the same file and are covered in the Proxy settings. Changes under harness: apply the next time you start the harness; the proxy picks up its own changes without a restart.

Every setting has a Helps column, because each exists to serve one or more of three goals:

  • Efficient: fewer tokens or AI units for the same work.
  • Efficacious: the work stays as good, and the safe choice is the default.
  • Effective: whole tasks succeed: the right model, and waste stopped before it grows.

A tag appears only where it is true, and trade-offs are stated. Nothing here is a promise about your bill: measure your own tasks. Keys are written relative to harness:, so sandbox.mode means harness.sandbox.mode.

The short version

In plain words #

  • What it is. Every setting of the agent, the part of config.yaml under harness:.
  • What to do. Most people never edit it: /settings in a session lists every setting and changes every one of them, and /configuration set <key> <value> any single value. The lists of entries with several fields each (permission rules, MCP servers, language servers, skill folders, notification places) open in a list of their own inside /settings, where you add, change, remove and reorder them in a form: see Lists in /settings. A project can override some settings in its own folder. The proxy's settings are a separate page, and on its setup page.
  • Not sure what a setting does? Pick it in /settings and press ?: its help opens in full, what it does, when to change it, its default beside your value (and this project's), whether a change applies now or at the next start, what each of its values means and, for one that decides what the agent may do without asking, a Careful line. ? again hides it; while you type a value, ? is just a character. In a list's form, the field you are on says what it takes and when to fill it in. /configuration get <key> prints the same text.

Lists in /settings #

In plain words. Pick one of permission.rules, mcp_servers, lsp_servers, skills.sources or notifications.sinks in /settings and press Enter: you see its entries. Enter changes the one picked in a form of its fields, a adds one, d removes the one picked (after you press y), and for the two whose order matters (permission rules, where the first match wins, and skill folders) K and J move it up and down. Every change is saved at once to your own config.yaml, never to a project's, and takes effect the next time a session starts. Passwords and tokens you type there are hidden as you type, kept in the secret store, and never shown again. Anything that starts a program is shown to you, and asked about, before it is saved.

Technically.

  • Each save is checked the way loading config.yaml checks it (a rule's pattern is compiled as a session compiles it, a notification address is checked before it is kept), and nothing is written when a check fails: the form stays open and says why. When the list changed in the file since you opened it (another session, or an edit), the save is refused and you open it again, so nothing is overwritten.
  • Secret values (an MCP server's header and environment values, a notification sink's address, token and headers) go to the secret store, and the file gets a reference: ${secret:mcp-server/<server>/header/<name>.<id>}, ${secret:mcp-server/<server>/env/<NAME>.<id>}, ${secret:notifications.<sink>.url.<id>} (and .token.<id>, .header.<name>.<id>). Each save keeps a new value under a name of its own, so it never overwrites one another session is using, and the one it replaced is removed once nothing in config.yaml names it. The form shows a stored value as (kept): leave it to keep it, type over it to replace it. A value typed as a reference (${env:NAME}, ${secret:name}) is written as it is, except one naming a credential Maple keeps for one of its own features, which is refused. What a server or a sink kept is only ever given to that one, as your own config.yaml describes it: a project's .mcp.json or config that defines a server of the same name, sending somewhere else, does not get it. Renaming an entry moves its values; removing one deletes them.
  • An entry that starts a program (an MCP server's command, a language server, a command sink) shows the whole command line (and the names of the environment it is given) and asks for y before it is saved, when it is new, when its program, arguments or environment changed, or when it was switched to a type that runs a program. Only a key pressed after the question is shown answers it. Text that is not a name and a value in a header or environment field (a token pasted on its own) is masked whole, and never repeated in a message.
  • Arguments are typed as on a command line: spaces separate them, quotes hold a space. Name=value pairs (headers, environment) are separated by commas; a comma inside a value is typed \, (and a backslash just before a comma, or at the end of a value, \\), as in every name=value setting /settings takes: Accept=text/html\, application/json, X-Team=t1 is two headers. An MCP server's or a sink's name is letters, digits, - and _.
  • What the form, its question and the list show of an address hides its query, fragment and user part (https://mcp.example/sse?…), and of a command's arguments the value of one named like a credential: --token=…, --api-key …, API_KEY=…, Authorization: Bearer …, an address's query. The program and its other arguments are shown whole. Only what is shown is masked: the value is saved exactly as you typed it, so a credential you would rather not have in config.yaml at all goes in the environment field (kept in the secret store) instead.
  • An entry you do not touch is written back exactly as it was, so a hand-written one keeps its form.

Per-project overrides #

A project can carry its own .mapleharness/config.yaml (or .mapleharness/config.json) that changes some of harness:'s settings just for that project, on top of your global config.yaml. It only needs the keys it changes:

YAML
# .mapleharness/config.yaml, committed with the project
default_model: gpt-6-sol
loop_guard: { mode: warn }

Anything the project's file does not mention keeps your global value — setting loop_guard.mode above does not reset loop_guard.warn_after or anything else. A list (mcp_servers, sandbox.hide, and so on) is the exception: if the project's file names one at all, that is the whole list for this project, not an addition to your own.

notifications.* stays governed by your global config only, whatever a project's file contains: a notification destination can be a command, and letting a cloned repository set one would let it run something whenever a session finishes, needs approval, or fails.

proxy.* and proxy_logs are your global config's only too: they say where every request, and your proxy's access token, are sent, and where a proxy the harness starts writes its log. A project's file that sets them gets a note when the session starts, and the keys are ignored.

delegates.* is your global config's only as well: running your own Claude Code uses your sign-in and your plan, which only you turn on.

cost_preview_confirm_above is also yours alone: a question before a costly message is a limit you set on your own spending, so a project cannot add one or change it. A project may still turn cost_preview on for itself.

Since this file runs from a cloned repository, the first time you run the harness in a project that has one (or a .claude/hooks.json, a .claude/settings.json with hooks, or a .mcp.json), it asks whether to trust it — naming exactly what it would run or apply. Say no, or run non-interactively, and the project's file has no effect: the session runs on your global config alone. maple-harness trust list | approve | forget manages the decision afterwards — the same one decision covers hook files too; see Tools, skills and hooks.

Long conversations #

When a conversation outgrows the model's window, older messages leave the model's view. What leaves it is kept and searchable:

  1. Older parts of a long conversation stay searchable. Every message is stored, word for word, beside the saved session before it leaves the model's view, and the model can look any of it up again with the history_search tool: by words, a file path, a tool, or a message number. A search returns a few short snippets, so it never floods the conversation. The store is part of the session: --continue and --resume bring it back, a /fork or /clone gets its own copy, and removing the session removes it. It stays on your machine with the same file permissions as the session.
  2. In their place, a record built from the conversation itself: every request (the first one always), the files read and changed, the commands run and whether they passed, the names of failing tests, what failed, and the assistant's last words. It also quotes, word for word, the sentences from earlier replies that read like a decision, a requirement, a fix, a cause or an open item (digest_key_points). Credentials are replaced with a marker before it is written. It needs no model, no network and no credit, and it ends by telling the model which stored messages it replaces and that history_search finds them.
  3. By default, that is all. Making room sends no request to any model, so it costs nothing, in auto mode or not. A short line in the conversation says a record was kept and that earlier turns are searchable.
  4. A written summary, only if you ask for one with compress_with_model. With free, only a model on your own machine or network is asked. With on, the harness asks, in order: the model you just switched away from (it has read this conversation already); compress_model, or when that is not set the cheapest suitable model within compress_scope (a model on your own machine or network first); then the current model. A model already known to be out of credit, over its daily budget or rate limited is skipped without asking it. If the summary goes to a different provider or account than the one your session is on, a line in the conversation says where it went. The history is sent in pieces that each fit the model's window, and the answer streams, so a slow local model is not mistaken for a dead one. While this runs, the activity line says which model is summarising; Esc stops it and leaves the conversation as it was. /cost lists each summary request, with the model, apart from your turns; with no summary request there is no such line.

The stored history is bounded: once a session's store grows very large, its oldest messages are dropped, and a search says which messages are no longer there. A /fork to an earlier message copies only the stored history that belongs to the messages it keeps. A session started under the name of one that was removed never sees the old session's history.

If the proxy answers with a fallback that has a smaller window than the model you asked for, the harness works to the smaller window until your model answers again.

Hook files #

With hooks.files empty, hooks are read from these files, in this order, each adding to the ones before: hooks.json in the configuration folder (yours), then the project's .mapleharness/hooks.json, .claude/hooks.json, and the hooks key of Claude Code's project settings, .claude/settings.json and .claude/settings.local.json. A project's own files run only after you say yes to them (see above). A Claude Code settings file that holds no hooks, only permissions, is never asked about.

A project already set up for Claude Code gets the same checks here. For hooks from Claude Code's settings files:

  • a matcher names Claude Code's tools (Bash, Write|Edit, Read, Grep, Glob, WebFetch, Task) and must match the whole name, as in Claude Code; the harness's own name for the tool (bash, write_file) matches too;
  • the hook is given the tool under Claude Code's name, with tool_input.file_path beside path, and CLAUDE_PROJECT_DIR is set to the project folder;
  • exit status 2 refuses the action, with the hook's error output (or, when that is empty, its output) as the reason; so does Claude Code's JSON answer, {"decision": "block"} or a permissionDecision of deny;
  • on Stop, the same answers ({"decision": "block", "reason": …}, or exit status 2 with the reason on the error output) block the stop and send the agent back for one more turn, told the reason; {"continue": true} keeps Claude Code's meaning there and asks for nothing. A Stop hook's input carries stop_hook_active and last_assistant_message. See A Stop hook that sends it back.

Some Claude Code hook features have nothing to attach to here, and the harness says so with a note instead of ignoring them quietly: hooks for events it never fires (such as SessionEnd, PreCompact, Notification or SubagentStop), a matcher such as startup on an event that has no tool, and a PermissionRequest hook's answer (it runs only as a notice that approval is being asked). A hook that answers permissionDecision allow or ask, or puts a changed input in hookSpecificOutput.updatedInput, gets a note the first time: the call still goes through your usual permission check, with its original input. The events it fires are SessionStart, UserPromptSubmit, PreToolUse, PostToolUse, PermissionRequest, PermissionResult, Stop, AgentStart and AgentEnd. PermissionResult's input carries decision (allow or deny) and answered_by: person, or for a call denied without an answer timeout or no_person (see Approvals when nobody answers).

When the harness asks whether to trust a project, it lists under each file the commands it would run (each hook's event and command, each MCP server's command or address, and the MCP servers, language servers and clipboard command a project's .mapleharness/config.* sets), so you can read them before answering. Hook files that a project's config names in hooks.files are the project's too: they must be inside the project folder, and they are part of the same question, listed with their commands. The question also names the environment variables an MCP server sets (and flags ones such as NODE_OPTIONS or LD_PRELOAD that change how programs start), the headers it sends, and each setting in the project's config that gives tools more room (permission mode and allow rules, sandbox, file rules, skill folders). What the harness reads from these files is what you approved: a file changed after you said yes is asked about again, never used as changed. The harness checks those files only, not the scripts or programs their commands run: a hook that runs ./check-before-write.sh runs whatever that script holds at the time, so read those too before you say yes. The hooks.files in your own config.yaml is yours and is read as it is.

Hooks in your own Claude Code settings (~/.claude/settings.json) are not read: they are Claude Code's.

A remote MCP server is never connected to a link-local or cloud-metadata address, even with allow_private; the exact addresses a trusted server needs can be allowed only with the environment variable MAPLE_MCP_ALLOW_ADDRESSES, never from a config file. See Reaching cloud metadata or link-local services.

In plain words: pick a theme with /theme in a session, which lets you try each one on the whole screen before you keep it; auto matches your desktop on Omarchy and your terminal's light or dark background elsewhere.

theme also takes any of the following built-in names (/theme list lists them the same way), or theme_colors can override individual roles (accent, deep, light, text, muted, faint, ok, warn, err) on top of any of them:

  • Dark: maple (default), ocean, forest, mono, dracula, nord, gruvbox, catppuccin-mocha, tokyo-night, solarized-dark, monokai, one-dark, everforest, rose-pine, hackerman (the green-on-black terminal look, a community nickname rather than one published scheme), northern-lights
  • Light, for a light terminal background: maple-light, gruvbox-light, catppuccin-latte, solarized-light, one-light, birch
  • Themes from home: birch (light: paper white and bark grey, a rust accent, birch-leaf gold), northern-lights (dark: a night-sky navy, the aurora's violet and green) and toque (high contrast, red and white like the hat: white text and accents on a dark terminal, the status bar on flag red). Their text and status colours were checked for contrast with the WCAG formula against the background each is made for.
  • High contrast: toque.
  • Colour-vision-deficiency-friendly: colorblind-dark, colorblind-light — the status colours (not just the accent) are chosen from the Okabe–Ito palette to stay distinguishable under red-green colour blindness, the most common form. This is a design choice, not a certification: nothing here has been tested against colour-vision simulation software.
  • auto: on a machine running Omarchy, follows the desktop's own active theme (whatever omarchy theme current reports), and keeps following it while Maple Harness runs: switch the Omarchy theme and Maple Harness's colours change within a couple of seconds, including what is already on screen. A desktop theme with a Maple equivalent uses it; one without (Kanagawa, for example) takes its colours from the Omarchy theme itself. theme_colors still applies on top. Choosing another theme with /theme <name> stops following until you choose /theme auto again. Everywhere else, including a Linux machine not running Omarchy, macOS or Windows, auto is maple on a dark terminal and maple-light on a light one, by the background your terminal reports when the session starts (a terminal that does not say keeps maple).

Most of the dark and light themes reproduce a well-known published colour scheme (Dracula, Nord, Gruvbox, Catppuccin, Tokyo Night, Solarized, Monokai, One Dark/Light, Everforest, Rosé Pine), so it looks the same here as it does in an editor or terminal already set up with it.

Where the harness finds the proxy #

KeyDefaultWhat it does
version1The configuration file's format version
server.openai_compat127.0.0.1:11535The proxy's OpenAI-compatible address, which the harness talks to
server.anthropic_compat127.0.0.1:11537The proxy's Anthropic-compatible address
server.webui127.0.0.1:11539The proxy's setup page, which /proxy and doctor use

To use a team hub, sign your own proxy in to it (Join your laptop to a team hub): the harness keeps these settings as they are. To use a proxy on another machine directly, set proxy.* (usually with maple-harness proxy connect <url>, which stores the token for you). Unset, nothing changes: the harness uses the proxy at server.openai_compat on this machine, its own: the normal way. Set, it is a proxy you connected to (an advanced setup for CI and containers), even at a local address (an SSH tunnel, a port forward, a container's port). See Connect the harness to a proxy, Teams, and Which setup do I need? for when to use proxy.url and when proxy.trust_unchecked.

KeyDefaultWhat it does
proxy.urlnoneThe address of a proxy run elsewhere, with its scheme, for example https://proxy.example:11535. The harness sends its requests there and never starts, stops or restarts that proxy; auth, savings and the quota line work through the proxy's setup page, so they run on its machine
proxy.tokennoneThat proxy's access token, written only as ${secret:name} (the secret store) or ${env:NAME}. A token written out in config.yaml is refused. It is sent as Authorization: Bearer on every request; to a proxy on this machine without proxy.url, only once it proved it is yours, so for one that cannot, use maple-harness proxy connect
proxy.allow_insecureoffAllows plain http:// to a proxy on another machine, which sends the token where the network can read it. Use https, or a private network such as Tailscale or a VPN and then this
proxy.trust_uncheckedoffWhile the proxy on this machine is unverified (an older release, or one run as another user, in a container or with a different settings folder), the harness asks before a session starts and tools ask before every run. On, it does not ask and tools run as your rules say: for CI and containers. Nothing secret is sent to such a proxy and the Claude delegate stays off either way. MAPLE_TRUST_UNCHECKED_PROXY=1 does the same for one run. It never sends proxy.token: a proxy that needs a token is connected with maple-harness proxy connect. See Verified and unverified proxies and the CI recipes

How long a request waits for the model to start answering:

KeyDefaultWhat it does
first_output_timeout_seconds0: follow the proxyHow long a request waits for the proxy to start answering, which it does once the model's first output arrives. 0 follows the proxy: 10 minutes, or longer when the proxy says it waits longer for one of its providers (a model server you run waits 30 minutes by default; see providers[].first_output_timeout_seconds in Proxy settings). When the time runs out the request is asked again at most twice, then the turn stops with a message naming the model and this setting. Raise it, and the provider's, for a slow local model on a long write

The harness starts the proxy itself if nothing is listening. That proxy keeps no log unless you ask for one:

KeyDefaultWhat it does
proxy_logsoffWhere a proxy the harness starts writes its log. on: logs/proxy.log in the configuration folder (usually ~/.config/maple-harness/logs/proxy.log). A path (absolute, or starting with ~/): that file. off: no log, and its output is not kept

The file is created readable only by you, and when it has grown past 10 MB the harness moves it to proxy.log.1 (replacing an older one) the next time it starts the proxy. It is the proxy's own log, the same as maple-proxy serve --logs <file>: one line per request and no prompts or answers. /proxy shows where it is, and /proxy logs (or /proxy logs 100) shows its last lines. A proxy you started yourself, or one running as a service, is not affected. The setting is read when the harness starts, so after changing it start the harness again, then /proxy restart.

An annotated example #

YAML
version: 1

harness:
  default_model: gpt-6-sol          # or an alias
  auto_model: false                 # true: /model auto on from the start
  auto_model_map:                   # pin what auto uses for each kind of work
    heavy: gpt-6-sol
  auto_avoid: ["*-codex*"]          # the default; [] to allow them
  effort: medium
  compress_with_model: off          # off (no summary request, no cost) | free | on
  compress_model: gpt-6-sol-mini    # with it on: who summarises; unset picks the cheapest suitable
  compress_scope: same-account      # same-account | same-provider | any
  digest_key_points: on             # quote decisions, fixes, open items from earlier replies; off to leave them out

  permission:
    mode: ask                       # ask | auto | yolo (yolo needs --yolo)
    rules:
      - { pattern: read_file, decision: allow }
      - { pattern: "bash(rm -rf*)", decision: deny }

  sandbox:
    mode: auto                      # off | auto | strict
    network: allow                  # allow | deny
    when_unattended: off            # on: contain commands in auto and yolo mode
  file_policy:
    read: hidden-only               # hidden-only | project | anywhere

  loop_guard: { mode: stop, warn_after: 3, stop_after: 6 }
  tool_output: { failed_max_lines: 120 }   # 0 = never shorten
  lsp: auto                         # auto | off
  bash_file_writes: warn            # warn | deny | allow
  limits:                           # memory caps and heavy runs: memory-limits.md
    command_memory: auto            # a size (4G, 512M), auto (half your memory, at most 8G), or off
    session_memory: auto            # a size, auto (half your memory), or off
    heavy_runs: 1                   # 1 to 64, auto, or off
    heavy_wait: 30m                 # how long a heavy run waits for a slot; heavy_wait_headless: 10m
    resume_after_reset: "on"        # wait out a provider's limit and carry on; max_reset_wait: 6h
  ledger: "off"                     # off | auto
  cost_preview: "off"               # off | large | on (an estimate, never sent to the model)

  subagents: { max_parallel: 3, max_turns: 50, outlive_turn: "on" }
  job_notices: wake                 # wake | next | off: background commands that end, monitors' lines
  schedule: { jobs: "on", durable: "off", durable_budget: "1", durable_timeout: 30m }   # scheduling.md
  ask_person: on                    # on | off: the model's multiple-choice questions to you
  questions: { timeout: "off" }     # off | 30s | 60s | 2m | 5m | 10m
  approvals: { timeout: 10m, refusal_exit_code: "off" }   # off | 1m … 30m; on: --prompt exits 4 after a refusal
  a2a: { question_timeout: 10m, may_approve: [] }         # a2a serve: callers' questions, and grants by token id
  bash: { background_on_timeout: "off" }   # on: a command past its timeout moves to the background
  agents: { listen: on, approvals: off, questions: off }

  notifications:
    desktop: true
    events: [approval, error, stalled]

  retention: { sessions_days: 30, keep_per_dir: 5, auto_prune: false }
