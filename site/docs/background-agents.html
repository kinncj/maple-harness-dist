Background agents: out on the ice while you talk #

Since 3.0 an agent the model starts in the background keeps working after the turn ends. You can go on talking to the main agent, or leave it idle, and each background agent's report comes back later on its own: it lands in the conversation and wakes the main agent, which reads it and carries on. A finished agent can be given a follow-up and picks up where it left off, with everything it already knew.

The short version

In plain words #

  • What it is. Helpers that keep working while you and the main agent move on. When one is done, its report arrives by itself and the main agent reads it.
  • Why you want it. A long search, a test run or a second opinion no longer holds the conversation up. You keep the main agent free for the next thing.
  • What to do. Nothing: it is on by default. To get the old behaviour (the turn waits for every background agent before it ends), set harness.subagents.outlive_turn: off in /settings.
  • Where to look. Ctrl+T opens the agents tray: who is out, for how long, and doing what.

What you see #

When a turn ends with agents still working, one line says so, and the line under the input box keeps saying it while the session is idle:

◯ 2 agents still out on the ice · their reports land here when they are done
⏵⏵ ask mode (shift+tab to cycle: ask → auto)  ·  ◯ waiting on 2 agents

When an agent finishes and nothing else is running, its report appears as one line and the main agent starts a turn to read it:

◯ explore (a1) finished · found 42 files  ↳ wakes the agent

While a turn is already running, the report reaches the main agent at its next step instead. A long-running agent also sends a short progress note now and then (at most every three minutes, and only when it has done something since the last one). While nothing runs, a note is only shown to you; the main agent gets the report itself.

The agents tray (ctrl+t, or Down from an empty input box) lists every agent with how long it has run and what it is doing.

Talking to an agent #

Open an agent from the tray (Enter on its row) to see its transcript. Press m to write to it:

  • an agent that is still running reads your message at its next step;
  • a finished agent is resumed: it starts again in the background with its whole conversation, and your message at the end. Its new report comes back like the first one.

The view's title says talking to explore while you write, so it is never mistaken for the main input. Enter sends, Esc drops what you wrote.

The main agent can do the same with its tools (below), so "check that edge case too" can go to the agent that already knows the code.

What can be resumed

An agent you stopped is not resumed; start a new one instead. Only the newest 20 finished agents keep their conversation for resuming (each up to 2 MB of text); older ones say so.

Those limits are chosen, not measured. Those 20 are saved with the session, so they can still be resumed after you quit and start it again: see After a restart.

From your phone, the agents sheet does the same: Message on a running agent, Resume with a message on a finished one. See Remote control.

Stopping agents #

WhereWhat it does
x on an agent in the tray, then yStops that agent
X in the tray, then yStops every agent still running
The palette (ctrl+p): Stop all agentsThe same
EscStops the main agent's turn, and an agent it waits for in the foreground; background agents keep working (with outlive_turn: off, Esc stops them too)
/clearStops running agents too, with a note: their reports would belong to the conversation you cleared
QuittingThe first Ctrl-C names the agents still working; the second stops them and quits, and k quits and keeps them working (below)

A stopped agent's task on the lineup goes back to pending, with a note saying why, so another agent (or the main one) can take it. If it worked in its own copy of the project, the copy is kept.

When you quit with agents out #

In plain words:

  • What it is. You want to close the terminal, but an agent is halfway through a long job. You can let it finish instead of stopping it.
  • Why you want it. An hour of work does not have to be thrown away because it is time to go home.
  • What to do. The steps below.
  1. Press Ctrl-C once. The line under the input box names the agents still working.
  2. Press k to quit and keep them working (or type /quit keep). Press Ctrl-C again instead to stop them and quit, as before.
  3. Later, start the session again with maple-harness --session <name>: their reports are waiting in it.

What the terminal says when you press k:

◯ 1 agent(s) keep working: tester (a3).
  Their reports are saved in session spendline-api: maple-harness --session spendline-api picks them up.
  This terminal stays busy until they finish, at most until 18:40 (harness.subagents.keep_timeout).
  You may close it: they keep working. Ctrl-C here, or kill 41207, stops them. maple-harness agents lists this session as finishing.
  Anything they ask your approval for is refused, since nobody is here to answer.
  • Each report is added to the conversation and saved as it lands. The next maple-harness --session <name> starts with the reports there, and the main agent reads them with your next message.
  • maple-harness agents lists the session as finishing while its agents work. It takes no messages then.
  • Closing the terminal does not stop them. Ctrl-C in that terminal, kill <pid>, or keep_timeout (30 minutes by default) stops them; they are saved as stopped when the session ended, so you can resume them later.

Nobody is there to say yes

k is not offered while an agent waits for your approval or a question waits for your answer: answer it first. From the moment you press it, anything they would ask you is refused: a tool call that would wait for your yes is turned down, and the agent carries on without it. Calls your permission rules already allow are not asked, so they still run.

Technical details: the session's own process stays alive without its interface until the agents finish, so they keep their copies of the project, their memory caps and their limits. Every approval they would ask for is refused, and so is every question to you (it settles as "nobody is here"). The phone or browser connected to the session is let go when you quit. A --prompt run, --repl and --rpc never get here: their turns wait for their agents before they end.

After a restart #

The finished agents' conversations (the newest 20, each up to 2 MB of text) are saved beside the session, in a file readable by you only, whenever they change. Start the session again with --session <name> and they are back under their old ids, marked as from before the restart. Ask the main agent to follow up ("ask the tester to check the rounding too"): its agent_message resumes that agent with its whole conversation. On the phone, the agents sheet lists them under Finished, each with Resume with a message. The terminal's tray shows an agent only while it runs and for a short while after, so a resumed one shows there again once it runs. An agent that was still working when the session ended was stopped then, and is saved as such; resuming it tells it that changes it made in its own copy of the project were not applied, so it checks the files before it carries on. An agent you stopped yourself stays stopped. The file goes when the session is removed (maple-harness sessions rm, or cleanup).

Settings #

SettingDefaultMeaning
harness.subagents.outlive_turnonon: background agents keep working after the turn, and their reports wake the session. off: the turn waits for every background agent before it ends, as before 3.0
harness.subagents.keep_after_exitofferoffer: quitting with agents still working offers k to keep them working. off: quitting always stops them
harness.subagents.keep_timeout30mHow long kept agents may work after you quit: 10m, 30m, 1h, 2h or 4h

This applies in the full-screen terminal, and to a session you drive from your phone or another device. A --prompt run, the plain REPL (--repl) and --rpc always wait for their agents before the turn ends, so nothing exits or goes idle with work still out.

For the curious

Technical details #

The tools the model uses #

The same four tools that reach other agents on your machine reach this session's own agents, by their id (a3), by name#id (tester#a3), or by a name only one agent has:

ToolOn one of this session's agents
agent_readIts state, its transcript so far, and its report once finished. On a background command or monitor (bg_1, mon_1): its last output lines
agent_waitWaits until it finishes, with a timeout (default 5 minutes, at most 30). targets waits for whichever of several finishes first. A report returned here does not arrive again as a message
agent_messageSteers a running agent, or resumes a finished one in the background with its whole conversation (also one saved before a restart)
agent_stopStops it cleanly, with an optional reason kept in its transcript; no report follows. Also stops a background command or monitor. In ask mode it asks you first, as kill_shell does (a rule allowing agent_stop lets it through)

Only the main agent can stop or message this session's agents: a subagent may read the others, never stop or restart them, and never targets itself.

How a report reaches the model #

A report is added at the end of the conversation (so the provider's prompt cache keeps working), opened by a note saying it is the report of work the agent started, not your words. Several reports that arrive while one turn runs are read at its next step.

Safety #

  • A background agent has the same permissions as before: every tool call that would ask you still asks, in the terminal or on your phone, labelled with the agent's name, even after the turn that started it has ended. The tools that act outside the session (typing into a pane or another agent, starting one, a monitor) ask in auto and yolo mode too, as they do for the main agent.
  • A turn started by a report is held, like a turn another agent's message starts: in auto or yolo mode its tool calls still ask you. Your own allow rules still apply.
  • An agent started during such a held turn (or while serving A2A) stays held for its whole life, even after that turn has ended, and so does an agent resumed or steered from one. Its questions can only be answered by you, never over the control socket.
  • A report is marked as the agent's information, not instructions. An agent's transcript is shown without any terminal control sequences.
  • Letting an agent go past its budget is asked each time, never "always".
  • An agent's own limits (memory, budget, permissions) come from its file: see Make your own.
  • When the session ends, every agent still running is stopped, and the terminal says which, unless you chose to keep them working (above): then nobody can approve anything they ask for, so those calls are refused.
  • From the phone, only a device paired to drive this computer can message an agent: not a watch-only device, a shared link, or a device limited to some sessions. The message goes through the same checks as any other the page sends, and the agent reads it as from you on that device ("Message from the person (on work phone)").
