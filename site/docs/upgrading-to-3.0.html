Upgrading to 3.0 #

If you use Maple Harness on your own machine, upgrading to 3.0 asks nothing of you: update, restart the proxy, and carry on. 3.0 is a large release, so its number changes, but what worked on 2.x keeps working. The new features stay out of the way until you set them up.

This page says what keeps working, what is new, what behaves differently, the one thing that may ask you a question again, and how to go back to 2.x. For the tour of what is new, see What's new in 3.0.

The short version

In plain words #

  • On one computer, nothing to do. Update, restart the proxy, carry on. Your settings, sign-ins, tokens, sessions and usage history keep working.
  • New things stay out of the way. Model groups, rate limits, request tags and the LiteLLM provider only do something once you add them to your settings.
  • Approvals nobody answers are denied. After 10 minutes, or at once in a run with no terminal, where a piped y no longer approves. A script that relied on that lists what it may do with --allow-tool instead (details).
  • One question may come back. A project you trusted before, whose .claude/settings.json has Claude Code hooks, is asked about once more, because those hooks now run here too. Answer it once.
  • Going back to 2.x works, after you take out any litellm provider. 2.x ignores the other 3.0 settings, so a group's name and the rate limits stop working until you return to 3.0.

Nothing to do #

Everything a 2.x release left on your disk keeps working on 3.0:

  • your config.yaml and settings, sign-ins and provider keys;
  • access tokens, people and teams, and the phones and computers you paired;
  • saved sessions, which resume where you left them;
  • the usage log, the events log, your exports, and the DuckDB queries you already wrote.

We tested this by starting 3.0 on the files that each release from 1.0 to 2.6.3 left behind, and asking it the same questions that release had answered. The ports, the commands and the setup page's first steps are the same as before.

How to upgrade #

  • Installed with the one-line installer: run maple-harness update (or the installer again), then restart the proxy. See Install.
  • The proxy as a background service: update, then restart the service. See Update.
  • A distribution package (deb, rpm, apk): install the 3.0 package, then restart the proxy.
  • In a container or on Kubernetes: use the 3.0 image, or build it from the 3.0 release as before. See Run the proxy in Docker and Run the proxy on Kubernetes.
  • Several replicas: replace them as for any release. Add settings that only 3.0 knows (below) once every replica runs 3.0: a 2.x replica ignores them. A mix of 2.x and 3.0 replicas on one PostgreSQL and Redis has not been tested yet; if you can, upgrade them together.
  • A hub with proxies below it: upgrade the proxies below as well. A proxy below that still runs 2.x lets only a rotated token's new secret in, with no grace period for the old one.
  • Blocking a token while two versions share one folder (or a replica is not yet upgraded): the 2.x program can drop the block record. The token then stops working for good rather than working again; revoke it and make a new one.

New, and off until you set it up #

None of these changes how your requests are routed until you add it to your settings.

The proxy: routing and limits

  • Model groups. One model name served by several accounts, regions or servers, spread between them, with retries, and a conversation kept on the deployment that answered it. See Model groups.
  • Rate limits for people and teams. Requests a minute, input tokens a minute and requests at once. See Rate limits.
  • Content-policy fallbacks. Models to try only when a provider refuses a request for its content. See Fallbacks.
  • How much a model server works on at once, and request priority when it is full. See How many requests a model server takes at once.
  • Your own rules for auto: words in a message that set its weight, and several models for one weight. See Your own rules for auto.
  • Request tags. Label a request with X-Maple-Tags (or LiteLLM's x-litellm-tags) and sum usage by story, feature or job.
  • Pass-through routes to a provider's own API. See Pass-through routes.
  • Response cache controls per request, and answers shared within a team. See Caching.

The proxy: control, for a shared proxy

  • Guardrails: block, mask or log secrets, personal data, banned terms and your own patterns, with the proxy's own checks or a service you name. See Guardrails.
  • Organizations, roles, rules per access token, budgets per end user, model access groups, access hours and address lists. See Access control.
  • Block, expire and rotate tokens. See Rotate or revoke a token.
  • Content export and callbacks: prompts and answers of the people you name to Langfuse, Phoenix or an OpenTelemetry collector, and each usage line to a webhook, Langfuse, Datadog or storage. See Content export and callbacks.
  • The MCP hub is no longer experimental. A 2.x mcp_hub section works unchanged. New and opt-in: signing in to hosted MCP servers, access lists per team and token, prompts and resources, tool pinning, and setting the hub up from its page on the setup page. See MCP hub.
  • A2A: Maple Harness as an agent other agents hand tasks to, and the proxy as a gateway in front of several agents. See Agents that call agents (A2A).

LiteLLM

  • LiteLLM, both ways. A litellm provider type, and a guide for putting Maple behind a LiteLLM gateway; LiteLLM's management API and health routes on the Maple proxy. See Use it with LiteLLM.
  • Move a LiteLLM config to Maple: maple-proxy import litellm, from a file or a running LiteLLM. It changes nothing unless you pass --write. See Move a LiteLLM config to Maple.

Maple Harness

  • Answer a session's approvals from another program (harness.agents.approvals: on; Linux only for now). See Talking to other agents.
  • GitHub Copilot's instruction files (harness.copilot_instructions: on). See Configuration.
  • Label a run's requests with --tag or MAPLE_HARNESS_TAGS. See Command-line flags.

Deployment

  • A container image for every release, a Helm chart, Docker Compose quick starts and Terraform examples. See Run the proxy in Docker and With Helm.

New, and on by default #

These need no setup and change nothing for the tools you already use.

The proxy

  • The OpenAI Responses API on the proxy's OpenAI-compatible address, so tools that speak it, such as Codex CLI, work through the proxy. See Codex CLI.
  • More of the OpenAI API: rerank, moderations, images, audio, files and batches, for providers that offer them, and the legacy /v1/completions. See More API routes.
  • More of the Anthropic API: the model list and token counting on the Anthropic-compatible address.
  • A LiteLLM client's key header (x-litellm-api-key) is read as the access token, so a tool set up for LiteLLM needs only its address changed.
  • A new usage log column, tags (schema version 9). Lines written before 3.0 show it empty. See Your usage data.

Maple Harness

  • Start the interface with a task: maple-harness "fix the failing test", or --message "...". A first word that names a command still runs that command, as before.
  • Sessions for programs: maple-harness sessions list --json and sessions show <name> --json. See Drive it from another program.
  • Claude Code's project hooks: hooks in a project's .claude/settings.json and .claude/settings.local.json run here as in Claude Code, after you trust the project. See Hook files.
  • Steer a turn while it works: a correction typed while the model works reaches it mid-turn, a next task waits for the turn to end, and Ctrl+G, /steer and /queue decide it yourself. See Modes and keys.
  • The terminal interface: a clearer transcript (one line per tool call, real diffs, folded reads), the key map (?), the command palette (Ctrl+P), the session switcher (Ctrl+S), a settings menu (/settings), a sidebar on wide terminals, @ for files, Ctrl+R for what you sent, and the mouse in the message box. See Commands and keys.
  • Background subagents, a shared task list, and a copy of the project of their own for agents that write. See Agents in the background. A finished agent can be given a follow-up and picks up with everything it knew (m in its view in the tray); agent files take disallowedTools, isolation, background, and Maple's own permissions and limits (a memory cap and a budget per agent). See Background agents and More fields.
  • Rules for one run: --allow-tool, --deny-tool and --policy, in Maple's form or Claude Code's and Copilot CLI's. A deny rule of yours always wins. See Rules for one run.
  • Approvals of headless runs on your phone: a --prompt run with no terminal, and a2a serve, show their approvals on a paired phone while this machine's gateway runs. See Answer from your phone.
  • Questions everywhere: in a terminal attached with maple-harness attach, and as a numbered prompt in the plain REPL. See Questions the agent asks you.
  • Agents talk to each other, and the agent opens panes and tabs beside itself, in herdr, tmux, WezTerm and kitty. See Use it with herdr and Use it with tmux.
  • Sign in to MCP servers that ask for it, from .mcp.json. See Servers that ask you to sign in.
  • Worktrees: /worktrees, maple-harness worktree, the phone's session sheet and the agent's worktree tool list, make and remove the repository's git worktrees. harness.worktrees.location chooses where they go; the default, beside, keeps them where worktree_open and /worktree put them before, and a background agent's copy stays in .mapleharness/worktrees. See Worktrees.
  • Attested releases: with GitHub's gh installed, the installers and update check that a release's checksums come from the public release workflow. See Install.

What behaves differently #

Nothing here needs a change from you, but you may notice it.

Read your allow rules for write_file and edit_file once

Those rules now match the file's path. An allow rule such as write_file(src/*) that used to ask now allows those writes (details in the first item below).

  • Permission rules match what they name. A deny or ask rule's * now also covers a command that goes on to a second line, and write_file and edit_file rules match the file's path (they never matched before). An allow rule such as write_file(src/*) that used to ask now allows those writes: read your allow rules for these two tools once. See Permissions and safety.
  • A provider's limit is a 429 that says when it lifts. When every route of a request is out of limit or quota, the proxy answers 429 (rate_limit_error) with X-Maple-Retry-At and Retry-After, where it used to answer 502. The harness waits for that time and carries on instead of stopping (harness.limits.resume_after_reset; a --prompt run stops with exit status 75 unless you pass --wait-for-reset). --rpc, serve, a2a serve and --repl wait too. A limit that cuts a streamed answer now ends the stream with an error that says when it lifts (a last {"error": ...} chunk, or Anthropic's event: error), where the stream used to just end. See When a provider's limit runs out.
  • Background agents in a repository with git's per-worktree settings on (extensions.worktreeConfig, which git sparse-checkout turns on) no longer get their own copy of the project: git would read those settings from a place commands in the sandbox can write. The agent works in the project itself, as with subagents.isolation: none, and says why. Other repositories are not affected. See Worktrees.
  • An approval nobody answers is denied after 10 minutes. Before, it waited as long as it took. Now that one call is denied (recorded as answered_by: timeout) and the run goes on; nothing is ever allowed this way. The wait pauses while a phone or browser has the session open. In the terminal, the plain prompt, shared sessions, serve and --rpc. To wait as long as it takes again, set harness.approvals.timeout: off. See Approvals when nobody answers.
  • A piped answer never approves. In --prompt or --repl with standard input that is not a terminal, a y or a on the pipe used to approve; now nothing there is read, and each question is denied at once (answered_by: no_person) with the rule that would allow it. Give a script its permissions with --allow-tool, --deny-tool or --policy instead. At a terminal, --prompt asks as before.
  • In a --prompt run where nobody can be reached, the questions that are always answered one at a time are denied with a reason: typing into another agent or pane, starting an agent, opening a pane or worktree, a monitor, the cost confirmation, a subagent's request to go past its budget (that subagent stops), applying a subagent's changes, and your local Claude's confirmations (it does not run).
  • Work another agent sent (a turn its message started, a session agent_start opened in a pane) asks you, not that agent and not the control socket; unanswered past the timeout the call is denied and the reply tells the sending agent you did not answer.
  • Every refusal nobody answered is shown: on the error stream (■ refused …), under refusals in --json-summary, to the model, and as the new refused notification, which is in the default list of harness.notifications.events. The PermissionResult hook's input gains answered_by. The exit status does not change unless you ask for status 4 (harness.approvals.refusal_exit_code: on or --refusal-exit-code).
  • serve and remote hosts without a terminal ask only while someone can answer (a phone or browser connected, or a paired device that may drive sessions); with neither, a question is denied at once. A pane_run naming a pane's program is put to the paired phone instead of being left to your rules.
  • A2A callers can approve less. A caller can still deny anything, but approve only what your allow rules already cover, unless you grant its token with maple-harness a2a grant <token id>. A run outside the sandbox and anything approved one run at a time are always yours. A timed-out question is recorded as timeout (it used to say a2a (no answer in time)), and its wait is now harness.a2a.question_timeout. See Who may approve what.
  • --resume without a terminal no longer reads a line to choose a session (a pipe's line, or its end, used to pick one). With one session in this folder it resumes it; otherwise it lists them and asks for --session <name> or --continue.
  • Waiting for a heavy-run slot is bounded by harness.limits.heavy_wait (30 minutes, as before) in a session you use, and by harness.limits.heavy_wait_headless (10 minutes) in --prompt, --rpc, serve and a2a serve. It used to be 30 minutes everywhere.
  • Typing while the model works can now steer the running turn instead of always waiting for it to end (above).
  • Background agents keep working after the turn ends. In 2.x the turn waited for every agent the model started in the background; now the turn may end while they work, and each report wakes the session when it lands, so you can keep talking meanwhile. Esc stops the turn but no longer the background agents (the tray's X does), and quitting with agents out asks for a second Ctrl-C. To keep the 2.x behaviour, set harness.subagents.outlive_turn: off. --prompt, --repl and --rpc wait for their agents as before. See Background agents.
  • An approval or a question that appears while you type waits until you pause for half a second before it takes a key, so the next letter of your message cannot answer it by accident. Ctrl-C is never held.
  • The setup page's Live range is today, on every card. In 2.x it meant no time filter, so some cards showed 30 days or a session's whole history.
  • A reasoning model on your own model server (llama.cpp, LM Studio, MLX and the like) with no output limit set is sent the room its context window leaves, at most 32,768 tokens, instead of being stopped at the server's own default. A model's max_output_tokens still wins.
  • Sandboxed commands cannot reach the tmux, WezTerm or kitty socket, and .git/commondir and .git/config.worktree are read-only for them and for the file tools, like .git/config.
  • maple-proxy mcp-hub status --json still has the experimental field, now false.
  • Your own local MCP servers given a secret (${secret:…} or ${env:…}, or a credential written out, in their environment or arguments) start from your home folder while the project is not trusted, and the session says so; in a trusted project they start in it as before. Trust the folder (maple-harness trust approve, which now works for a folder with nothing to ask about), or set cwd: project on the server, to keep it in the project. A server's program is found on your own PATH's absolute folders. See Where a local server starts.
  • maple-harness trust approve does not grant trust under a command Maple started, or without a terminal unless --yes is given (a script of yours that runs it needs --yes). A session whose standard input is not a terminal no longer asks the trust question; it continues without the project's files, as a run that cannot ask.
  • A project's MCP servers (its .mcp.json or settings, local or remote) may name only non-credential variables and ${secret:mcp-project/<id>/…} values; one that names anything else is not started, said. While a project is not trusted, its local servers' PATH leaves out the folders inside its repository. Your own servers still inherit your environment as in 2.x; the new harness.mcp.scrub_credential_env: on starts them without credential variables. See Where a local server starts.
  • pane_run into a pane whose program Maple does not know (the workspace names a program other than the one the agent started there) names that program; while you watch you are asked once for that pane and program, and while nobody watches only an allow rule for it lets the call through. Panes the agent opened, running what it started there, need no name. See Which panes pane_run asks about.
  • References in a local MCP server's environment (${secret:…}, ${env:…}) are resolved as it starts; before, the server got the reference as written.

The question that may come back #

Maple Harness asks before it runs anything a project brings with it (hooks, MCP servers, project settings), and asks again when those files change. In 3.0 a project's Claude Code settings file counts as one of them when it has hooks, so a project you trusted under 2.x that has such a file is asked about once more.

  • In the interface: you see the question with the files it names. Answer it once.
  • In a run that cannot ask (--prompt, --rpc, a job with no terminal): the run says so and continues without that project's hooks, MCP servers and project settings. Review the files, then run maple-harness trust approve in the project once, and later runs load them again.

Going back to 2.x #

Install a 2.x release by name (see Install) and restart the proxy.

Before you start a 2.x proxy

Take out every provider of type litellm from config.yaml. A 2.x proxy does not know that type and refuses to start, naming the provider.

Everything else 3.0 wrote stays readable by 2.6.3: settings, tokens, people and teams, sessions and the usage log, including lines with the new tags column. What 2.x does not do while you are on it:

  • it does not serve a model group's name (requests for it are answered "model not found");
  • it does not enforce people's and teams' rate limits;
  • it does not use content-policy fallbacks, and it does not have the Responses API.

The 3.0 settings stay in config.yaml, so they work again when you return to 3.0. Put the litellm providers back then.

Several replicas sharing a store (storage mode redis, or central with PostgreSQL and Redis): stop every 3.0 replica, then start the 2.x ones, and the same way back; do not run the two versions side by side. 2.6.3 starts on the store 3.0 used and reads its usage lines. It does not use organizations, rules per access token, lifetime budgets, the semantic cache, the investigations or the A2A gateway, and leaves what 3.0 stored for them alone: back on 3.0 they all work again, including tasks made through the A2A gateway before. Settings saved on 2.x's setup page keep the 3.0 settings beside them.

  • Storage mode central (PostgreSQL) needs no extra step: the typed view maple_usage_rows keeps 2.6.3's columns, so 2.x starts on it, and 3.0's newer usage columns are in maple_usage_rows_v9 beside it, which 2.x leaves alone.
  • Lifetime budgets count less after a long stay on 2.x: 2.x's usage retention deletes spend older than the retention period without adding it to the lifetime total. Keep the stay short, or set server.usage_retention_days: 0 (keep everything) while you are on 2.x.

For the curious

Technical details #

  • Versioning. 3.0 is a major release by size. Nothing that worked on 2.x is removed or changes meaning: the config keys, commands, ports, the proxy's HTTP API and the stored data of 2.x keep working. New settings are optional keys.
  • What was checked. An upgrade check starts the 3.0 programs on files left by each release from 1.0 to 2.6.3, with private folders and a stand-in model server, and compares their answers. A downgrade check starts 2.6.3 on files left by 3.0 with every new setting in use (a litellm provider, a model group, rate limits, content-policy fallbacks, tagged requests): 2.6.3 refuses the litellm provider by name, starts once it is taken out, serves every 2.x model, keeps people's model rules, and reads the usage log in its usage query and CSV export; 3.0 then starts again on what 2.6.3 left.
  • Usage schema 9. One new column, tags, NULL on older lines (with whole_batch, response_cache_kind and semantic_similarity). In PostgreSQL, the typed view maple_usage_rows keeps schema 8's columns, as 2.6.3 made it; maple_usage_rows_v9 has every schema 9 column. Query maple_usage_rows_v9 for the new ones. maple-proxy usage schema declares it, so the DuckDB views keep working on a mix of old and new lines. Readers that go by column position in a CSV export should go by column name, as with every earlier schema version.
  • Trust records. A project's trust decision is tied to the exact set of files that run and their contents; a new file in that set, such as a Claude Code settings file with hooks, makes the decision out of date, as an edited file always did.
  • Several replicas. A second downgrade check runs two 2.6.3 replicas on an empty store in storage mode redis, and in storage mode central on a real PostgreSQL 17, then two 3.0 replicas using every 3.0 feature that stores data, then 2.6.3 again (including a settings change on its setup page), then 3.0 again, checking each feature on each side; no usage line is lost.
  • Not checked yet: a real Redis's persistence during it, 2.x and 3.0 replicas running at once, a managed PostgreSQL, and the container image and Helm chart in a real cluster.
