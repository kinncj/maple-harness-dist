    Metrics and telemetry export #

    The proxy can hand what it already knows about each request (counts, timings, tokens, health, budgets) to the monitoring and security tools you run: a Prometheus /metrics endpoint, an OpenTelemetry (OTLP) export of traces, metrics and logs, and the audit events as JSON lines for a SIEM. All of it is off by default; on one machine nothing changes until you turn something on.

    It is metadata only. No prompt, answer, file, tool argument, key or token is ever exported, and no error text either: a failure is exported as its fixed class (rate limited, server error), never as what the provider said.

    Turn it on #

    On the setup page, open Data, then Observability export (collapsed at the bottom). Every switch there is written to config.yaml and applied at once, without a restart. Or in config.yaml:

    metrics:
  prometheus: on        # serve /metrics
  per_person: off       # on: also count requests per person and team (see below)

otel:
  endpoint: https://collector.example.com:4317   # setting it turns the OTLP export on
  protocol: grpc                                 # grpc or http (HTTP/protobuf)
  headers:
    authorization: ${secret:otel/authorization}  # credentials as references, never written here
  traces: on            # one span per request
  metrics: on           # the same figures as /metrics
  logs: off             # on: the proxy's own log lines too

log:
  audit_lines: off      # on: audit events as JSON lines on standard output

    A header that carries a credential (authorization, anything with token, key or secret in its name) must be a ${secret:...} or ${env:...} reference: store it with maple-proxy secrets set otel/authorization (the value on standard input) and the proxy refuses a value written into the file. A reference may only name an otel/ secret or an OTEL_ or MAPLE_ environment variable, so a provider key cannot be sent to a collector by mistake. Headers are never shown or changed on the setup page, and are never sent over plain http:// to another machine unless you set otel.insecure_http: on for a network you trust.

    Prometheus #

    Where to scrape #

    FromAddressToken
    This machinehttp://127.0.0.1:11539/metrics (the setup page's address)none; with a setup-page password, a token with the metrics scope
    Another machine, a container, Kubernetesthe OpenAI-compatible address, /metricsa token with the metrics scope

    Make a token with maple-proxy metrics token prometheus (shown once). The metrics scope reads /metrics and nothing else: it cannot use the models, and no token made before Maple 2.1 has it, whatever its scopes. In a container, mount the tokens as the secret access.metrics_tokens (one label=token a line), like the proxy tokens. Revoke a token on the setup page, under Remote access. Each token may scrape about once a second (a burst of five); a 30-second scrape interval is plenty.

    # prometheus.yml
scrape_configs:
  - job_name: maple-proxy
    metrics_path: /metrics
    authorization:
      credentials_file: /etc/prometheus/maple-metrics-token
    static_configs:
      - targets: ["maple-host.example.com:11535"]

    maple_tokens_total{direction="input"} includes the cached tokens; cached is the part read from the provider's cache. Counters start at zero when the proxy starts.

    Labels stay bounded #

    Every label has a fixed set of values or a cap on how many it keeps (a model name past the cap is counted as other), so a client sending a new model name with every request cannot grow your Prometheus without end. There is no session, conversation, token or person label.

    metrics.per_person: on adds person and team to maple_requests_total and maple_ai_units_total, and to spans. It is a choice with two costs: more series (one per person per provider and model), and your metrics then name the people using the proxy, for whoever can read them. Leave it off unless you need per-person figures in your monitoring; the setup page's Team tab and maple-proxy usage already have them.

    Several replicas #

    Each pod serves its own /metrics, counting what it answered. Scrape every pod and add them up in Prometheus (sum by (provider, model) (rate(maple_requests_total[5m]))). Gauges such as maple_budget_used are each pod's own view. For the Prometheus Operator, the Kubernetes samples have a component, config/metrics, with a ServiceMonitor that sends a metrics token (see Kubernetes).

    Grafana #

    Some starting points:

    • requests a second by outcome: sum by (outcome) (rate(maple_requests_total[5m]))
    • error ratio by provider: sum by (provider) (rate(maple_requests_total{outcome="error"}[5m])) / sum by (provider) (rate(maple_requests_total[5m]))
    • 95th-percentile latency: histogram_quantile(0.95, sum by (le, model) (rate(maple_request_duration_seconds_bucket[5m])))
    • time to first token: the same with maple_time_to_first_token_seconds_bucket
    • cache reads: sum(rate(maple_tokens_total{direction="cached"}[1h])) / sum(rate(maple_tokens_total{direction="input"}[1h]))
    • budget use: maple_budget_used / maple_budget_limit
    • a degraded or demoted model: maple_provider_health{state!="healthy"} == 1

    OpenTelemetry #

    With otel.endpoint set, the proxy sends to an OpenTelemetry collector over OTLP, gRPC (grpc, the default, port

    1. or HTTP/protobuf (http, port 4318; the signal paths /v1/traces, /v1/metrics and /v1/logs are added to

    the address). http:// is plain text and https:// is TLS.

    • Traces: one span per request, in one trace per client request (a request tried on two providers is two spans in one trace). Its attributes are the facts the usage log already records: provider, the model asked for and the one that answered, outcome, error class, input, output and cached tokens, AI units, time to first token, route reason, attempts and hops. Never content, session, conversation or token.
    • Metrics: the same figures and names as /metrics, as cumulative sums, gauges and histograms, once a minute.
    • Logs: the audit events (below) whenever the export is on, and with otel.logs: on the proxy's own log lines too.

    The export never slows a request: spans and log records wait in a bounded queue and are sent in batches every few seconds; when the collector is slow or down, a full queue drops the newest, and the setup page shows how many were sent and dropped, and the last error. Nothing piles up in memory.

    Environment variables #

    The standard OTEL_* variables fill in what otel: leaves unset: OTEL_EXPORTER_OTLP_PROTOCOL, OTEL_EXPORTER_OTLP_HEADERS, OTEL_EXPORTER_OTLP_TIMEOUT, OTEL_SERVICE_NAME (default maple-proxy), OTEL_RESOURCE_ATTRIBUTES, OTEL_BSP_SCHEDULE_DELAY, OTEL_BSP_MAX_QUEUE_SIZE, OTEL_BSP_MAX_EXPORT_BATCH_SIZE and OTEL_METRIC_EXPORT_INTERVAL. A signal's own endpoint (OTEL_EXPORTER_OTLP_TRACES_ENDPOINT and the like) wins for that signal; OTEL_TRACES_EXPORTER=none (or metrics, logs) turns one off, and OTEL_SDK_DISABLED=true all of them. The environment never turns the export on by itself: only otel.endpoint does, so a variable meant for another program does not start sending.

    Collector #

    A minimal OpenTelemetry Collector configuration that receives from the proxy:

    receivers:
  otlp:
    protocols:
      grpc: {endpoint: 0.0.0.0:4317}
      http: {endpoint: 0.0.0.0:4318}
processors:
  batch: {}
exporters:
  debug: {}            # replace with your backend's exporter
service:
  pipelines:
    traces:  {receivers: [otlp], processors: [batch], exporters: [debug]}
    metrics: {receivers: [otlp], processors: [batch], exporters: [debug]}
    logs:    {receivers: [otlp], processors: [batch], exporters: [debug]}

    Audit events for a SIEM #

    The audit events are what was done to the proxy's access and settings: a token made or revoked, refused and rate-limited requests, setup-page sign-ins and settings written, secrets moved, and MCP hub tool calls. With log.audit_lines: on (or MAPLE_LOG_AUDIT=on) each is also written to standard output as one JSON line, ready for a log collector:

    {"time":"2026-10-11T12:00:00.000Z","level":"INFO","msg":"audit","component":"audit","at":"2026-10-11T12:00:00Z","event":"token.create","actor":"setup-page","ip":"127.0.0.1","method":"POST","path":"/api/access/tokens","detail":"id=… label=laptop scopes=proxy"}

    Refusals are written at level WARN. With the OTLP export on, the same events go out as log records (log.type=audit). Anything shaped like a token, key or password is replaced with [redacted] before it is written, the same way as in the audit file on disk. Single sign-on sign-ins include who signed in (the identity provider, the subject and the email address), as a SIEM expects.

    What is never exported #

    • prompts, answers, files, images, tool definitions, tool arguments or results;
    • error text from a provider (only its class);
    • keys, tokens, header values, setup-page passwords;
    • session ids, conversation ids, request fingerprints and access-token labels in metrics and spans;
    • people and teams, unless metrics.per_person is on.
