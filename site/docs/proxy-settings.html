This is the complete list of what you can change on the proxy: the cards on its setup page, the keys in config.yaml, the commands, and the response headers you can read. For a guided tour, read The proxy and its setup page first.

The proxy and the harness share one config.yaml. A save on the setup page keeps the harness: section and any setting the proxy does not know, and changes only the lines of the settings you changed, so your comments stay. Adding or removing a provider leaves the other providers as you wrote them; moving a provider up or down the list writes the provider list in the proxy's own layout, without its comments. Saves from the harness, the setup page and maple-proxy commands wait for each other, so none undoes another's change.

Every setting has a Helps column, because each one exists to serve one or more of three goals:

  • Efficient: fewer tokens or AI units for the same work.
  • Efficacious: the work stays as good as it would be without the setting, and the defaults are safe.
  • Effective: whole tasks succeed: the right model answers, and waste is stopped before it grows.

A setting is tagged only where that is true. Where a setting trades one goal against another, the trade-off is stated. Nothing here is a promise about your bill: measure your own tasks.

The short version

In plain words #

  • What it is. The complete list of the proxy's settings, cards, commands and response headers.
  • What to do. On the setup page you rarely need this page: each card explains itself, All settings (in the System group) lists every setting with its default and when it applies, and Find anything (Ctrl K, ⌘ K on a Mac, or /) finds one by a word. Come here for the exact key, the default and the trade-off.

Settings at a glance #

The Setup page card column names the page in the setup page's sidebar, then the card. Every key in this table is also listed on All settings, grouped by page, which edits the ones that have no card of their own and says where to change the rest; a page whose settings are not all on a card ends with More settings for this page, the same forms for that page alone. Find anything finds any of them by name or by key.

The blocks with several parts (access control, routing rules, concurrency, the semantic cache, model details and cloud accounts, pass-through routes, the investigations' thresholds, the content collector and callbacks, the MCP hub's lists, servers and tool loop, the A2A gateway) have a form of their own on the page they belong to, each in a fold under its card. The proxy checks a form with the rules it reads config.yaml with, and says a refused value beside its field. A secret typed into one goes to the secret store, with a reference in the file, and is never shown again; a changed address asks for the secrets sent to it again. The forms that send data or credentials somewhere, or decide who may act for whom, need a page password (Page password, Protect this page, which also lists them); without one, the raw configuration editor refuses the same changes, and the form's folded header says needs a page password. Through single sign-on they are read-only (change it on the proxy's own machine), and the ones about this machine are not shown. A few settings stay in config.yaml only, each for a reason: the setup page's own address, anything that starts a program, the MCP hub's listener, the address an Azure account's key goes to, and where the proxy keeps its state (storage).

Model server requests #

In plain words: a model server you run often understands more request settings than the standard OpenAI ones, such as vLLM's and SGLang's min_tokens, top_k, repetition_penalty, guided_json or chat_template_kwargs. The proxy now sends those on to the server exactly as your tool wrote them, so a tool that sets them gets what it asked for through the proxy too. And when a request offered the model no tools but the model calls some anyway (a model trained on another tool's commands may), the proxy shows those calls as text in the answer, marked, instead of handing your tool calls it has no way to run. Nothing is run and nothing is hidden.

YAML
providers:
  - id: gpu
    type: openai-compatible
    base_url: http://127.0.0.1:8000/v1
    unknown_fields: pass        # the default; drop sends only the fields the proxy knows
    unoffered_tool_calls: text  # the default; pass hands them on as tool calls

On the setup page: Guards & limits, Model server requests.

Technical details:

  • Which fields. The top-level fields of a /v1/chat/completions request that the proxy does not read itself go to the server after the proxy's own fields, sorted by name, so the start of each request stays the same from one turn to the next. Never passed on this way, whatever the client writes (the proxy sends its own value, or none): the fields the proxy sets or reads itself (model, messages, tools, tool_choice, stream, stream_options, max_tokens, max_completion_tokens, temperature, stop, reasoning_effort, thinking, user, metadata, tags, prompt_cache_key, n, functions, function_call); anything starting with maple; credentials, addresses, headers and routing a gateway would read from a request (api_key, api_base, base_url, extra_headers, user_config, models, fallbacks, prices and logging callbacks, names starting litellm, aws_, vertex_, azure_, google_ or bedrock_, and others like them); server settings that would undo the proxy's own limits or your choices (the output limit under another name such as n_predict or Ollama's options, adapters such as lora_path, priority, cache slots and request ids, remote addresses, logit processors, a per-request chat_template, echo, best_of, beam search, service_tier, store); and any name that is not lower-case letters, digits and _. At most 64 fields and 1 MB in all; past that none are sent (the request still is) and the answer carries X-Maple-Extra-Fields: dropped: more than 64 fields or 1 MB.
  • Which providers. Only the model servers you run (ollama, lmstudio, omlx, lemonade, unsloth, and openai-compatible at a local address or marked local: true). An openai-compatible provider at a hosted address is a gateway or a cloud service, and never gets them (nor are its tool calls rewritten). Every other provider drops them, as before: a request translated to another API (anthropic, bedrock, vertex, gemini, apple-foundation-models), a hosted service (github-copilot, openrouter, xai, azure, litellm) and another Maple proxy (maple). A request that falls back from a model server to one of these loses them too. The Responses API (/v1/responses) and the Anthropic-compatible port do not pass them.
  • Caching. A request with extra fields is answered from the response cache only by an answer to the same fields, and the search-by-meaning cache passes it by.
  • Guardrails. Your pre_call guardrails check the extra fields' values as text too. A match that blocks, blocks; one that would mask refuses the request (guardrail_blocked), since a field cannot be masked and stay what the server reads.
  • Unoffered tool calls. Only for a request with no tools at all. Each call becomes a fenced tool_call block with its name and arguments as the model wrote them, after a line saying the calls were not run; the answer ends as a normal one (finish_reason stop), and X-Maple-Unoffered-Tool-Calls: <n> says how many (on a streamed answer, when the calls came before any text, since the headers go out with the first output). A request that offered tools is never changed, even when the model calls one it was not offered: your tool decides.

Model groups #

A model group serves one name from several deployments: the same model on several accounts, regions or local servers. Callers ask for the group's name; each request goes to one deployment, and the next takes over when it cannot answer.

YAML
model_groups:
  - name: team-gpt
    strategy: round-robin        # or ordered, weighted, least-busy, latency, cache-aware
    retries: 1                   # ask a deployment once more after a transient failure
    deployments:
      - model: copilot-work/gpt-5.5
      - model: copilot-home/gpt-5.5
        weight: 2                # for the weighted strategy
  • Which deployment first. round-robin (the default) takes them in turn; ordered always starts with the first; weighted picks the first at random in proportion to weight; least-busy starts with the one with the fewest requests in flight on this proxy; latency starts with the one whose recent answers came fastest (one not yet measured goes first, so each is measured); cache-aware starts with the one expected to hold the start of its prompt in its cache (below).
  • A conversation keeps its deployment. Once a deployment has answered a conversation, the conversation's later requests go back to it for a few minutes after each use, while that account's prompt cache is likely to hold its start, even on a proxy alone. A deployment known not to answer (out of quota, rate limited, held back) is not kept to.
  • Cache-aware (3.1), for several servers of one model of your own (vLLM, SGLang, llama.cpp). Each server keeps the prompts it worked on in its own cache, and can reuse that work when the next prompt starts the same way. cache-aware sends each request to the deployment this proxy expects to hold the longest start of its prompt, from what it sent where. A conversation it knows nothing about goes to a deployment picked from the conversation's start, the same one on every replica of the proxy, without the replicas sharing anything. When the expected deployment has clearly more requests in flight than the least busy one (more than busy_slack requests more, and more than busy_ratio times as many), the least busy takes the request instead, so a prompt many requests share spreads over more servers. A deployment known not to answer, or at its concurrency limit while another is not, is not chosen; failures fall back as below.
    • When it helps: conversations and agents that send long prompts again and again (a system prompt, tools, a growing history) to two or more servers of the same model.
    • When it does not: one server; cloud accounts (their caches are the provider's, and a conversation already keeps its deployment); short or unrelated prompts.
    • What it knows is an estimate, not what a server kept: a server may have dropped a prompt to make room, or restarted. Each request's route_reason says cache-aware:hit (sent where its prompt was expected), cache-aware:miss (nothing known yet) or cache-aware:overflow (the expected deployment was too busy). GET /v1/maple/capacity?model=<group> shows, under cache_aware, each deployment's remembered prompt starts, its requests and its hit ratio (null before its first request), labelled estimated, for this proxy since it started (left out when people are configured, as the concurrency counts are).
    • Several replicas each keep their own memory. In central mode, a conversation one replica moved is followed by the others through the shared conversation pins.
  • When a deployment cannot answer, the next one is asked, as an account fallback would be: for a refused account as well as a spent quota, an overload or no answer. Before any output only, as every fallback. After the deployments come their accounts' own provider_fallbacks. Two deployments that reach the same account and model are asked once. A provider budget with when_spent: stop passes over that deployment rather than refusing the request, since the group can still be served.
  • Retries. After an overload, a server error or no answer, a deployment is asked again up to retries times (0 to 3), a quarter of a second more each time, before the next deployment. A spent quota, a rate limit or a refusal is not asked again. The card's Any model row sets the same for every model, grouped or not (retries), and whether a connection lost before any of its answer arrived is asked once more (retry_lost_connection).
  • The name. A group may take a model's own name (gpt-5.5, with the deployments named <provider>/<model>): it then serves that name instead of the last account in the file. It may not be an alias, contain /, or be auto or auto-heavy, auto-medium, auto-light, and an alias may not point at a group. The model list shows the group under its name, described by its first deployment. model_fallbacks may list a group (its deployments are then tried as the group's are), and give a group its own fallbacks, tried after all its deployments. A person or team allowed the group's name may use every one of its deployments.
  • Tags. A request's tags (X-Maple-Tags, or x-litellm-tags) pick among tagged deployments: a plain tag sends it to the deployments carrying that tag (or, when none does, to the untagged ones); !tag keeps it off the deployments carrying it; &tag sends it only to deployments carrying it. When ! or & leaves no deployment, the request is refused with no_deployment_for_tags (400). A request without tags may use every deployment.
  • In the usage log each request has the deployment that answered in provider and model, and requested is the group's name.

X-Maple-CapacityHow many requests the backend that answered takes at once, when known: the same figure as GET /v1/maple/capacity (see Concurrency). Left out while it is not known
X-Maple-RouterFor a request for auto: the weight the proxy judged it to be and the name it went to, for example auto: heavy -> auto-heavy (see Auto mode at the proxy). For Copilot Auto: the models Copilot offered, and whether Copilot chose the model for this request or the account's default model was used (with the reason). Both, separated by ;, when a weight goes to Copilot Auto. When the model that answered is one provider health has demoted: health: would demote <provider>/<model> (<why>), or with health_failover: on, health: <provider>/<model> demoted (<why>). Model names, counts and failure classes only
X-Maple-FusionOn a Copilot Fusion High or Max request: its place in the turn, for example high; cascade; phase=escalation; outcome=escalated; reviews=2; id=fusion-…: the tier, how the turn is worked, this request's part (solver, escalation, repair, revision), how the turn ended (on its last request), the scores of the reviews made for this request, and the turn's id. Labels and scores only. It also lists the request's other calls (calls=judge:0.620:u,…: the step, the AI units Copilot stated and u when Copilot was told you started it, which it counts as a premium request; held marks an answer a review is deciding on) and who Copilot was told started the request's own call (self=u or self=a).
X-Maple-PromotionWhen the provider that answered runs a promotion that ends within three days: <id>; ends=<time>; percent=<n>; <the provider's message>. Each request through it will cost more after it ends; Maple Harness says so once
X-Maple-Trace-IdOn a call through the A2A gateway: the call's trace id, the one the caller sent or a new one. Send it back (with X-Maple-A2A-Hops) on calls an agent makes for the same task, so the gateway's budget per trace holds
X-Maple-Fallback-FromPresent when a fallback answered: the model that was passed over, and why
X-Maple-Cachehit, partial, miss or lost: how the provider's cache did. Not sent on streamed responses
X-Maple-Cache-Read, X-Maple-Cache-WriteTokens read from and written to the cache, where the provider reports them
X-Maple-Cache-ResponseOnly while response_cache is on: hit (a saved answer; nothing was sent to the provider, so the answer reports no tokens and no cost), miss (sent to the provider; the answer may be saved) or bypass (not a request the cache answers). Sent on streamed responses too. A client may send X-Maple-Cache: allow on a request to say a saved answer is fine for it. semantic-hit when the semantic cache answered
X-Maple-Semantic-CacheOnly while the semantic cache is on for the request: hit; similarity=0.973 (an earlier answer, to a latest message that close in meaning, from 0 to 1; nothing was sent to the provider), miss (sent to the provider; the answer may be saved) or bypass (not a request it answers: a tool turn, images, a temperature above 0, or no embedding model). Sent on streamed responses too
X-Maple-Cache-Control (request)Per-request controls for the response cache and the semantic cache, comma-separated, as LiteLLM names them: no-cache (ask the provider; the new answer may still be saved), no-store (do not save this answer), ttl=<seconds> (keep this answer at most that long, never longer than response_cache_ttl), s-maxage=<seconds> (accept only a saved answer at most that old) and namespace=<name> (a set of saved answers of its own: letters, digits and . _ - :, up to 64). The standard Cache-Control: no-cache and no-store request headers are read too
X-Maple-Prefix-StabilizedWhat the prefix stabiliser changed in the request, if anything
X-Maple-Tool-Results-TrimmedHow many old tool results were replaced, and about how many tokens
X-Maple-ImagesHow many images were resized or replaced by a note, and about how many image tokens that left out (an estimate from the provider's published rule)
X-Maple-AlertOnly while a spend alert is in force: one value per alert, <id> <level> <message>, for example budget.80@budget:provider:copilot@2026-10-08 warn copilot has used 80% of today's budget (160 of 200 requests); it resets at 00:00 UTC. The id stays the same for the alert's whole period, so a client can show it once. Provider ids and figures only
X-Maple-InitiatorSent by Maple Harness, with the value agent, on a request it makes on its own (a check after an answer, a summary): the proxy then tells GitHub Copilot the request is the agent's, not a new turn of yours, and Copilot Auto and Copilot Fusion keep it in the current turn. It can only mark a request the agent's, and is honoured only from a tool on the proxy's own machine (without an access token) or from a chained Maple proxy; from anyone else behind a shared proxy it is ignored. The usage log records who started each request (initiator).
X-Maple-Model-SwitchSent by Maple Harness on the first request after you switch model, with the value user and nothing else, so maple-proxy usage auto-report can say what followed a choice of auto
X-Maple-Snapshots-TrimmedHow many browser page snapshots were recognised, how many were sent as changes only or cut, and about how many tokens that left out
X-Maple-IgnoredOn a Responses API request (POST /v1/responses): the request fields the proxy received and did not act on, when acting on them could have changed the answer, for example tools.web_search, text.format
X-Maple-Token-CountOn POST /v1/messages/count_tokens: how the count was made; provider (asked of the Anthropic account that serves the model) or estimated (from the request's size)
X-Maple-Context-TrimmedPresent when the context guard dropped old turns to fit the model's window
X-Maple-Output-NoteOn an answer that is not streamed, when it needs saying how the answer ended: a reasoning model used its whole output limit on reasoning before any answer. A streamed answer carries the same note as output_note in its usage. See When the output limit goes on reasoning
X-Maple-ClientSent by the harness so its requests can be told apart from other tools' in the Cache card
X-Maple-SessionSent by a client (the harness sends it automatically) so its requests, and any subagent's, group together on the Sessions card
X-Maple-PrioritySent by a client: interactive (the default), batch or background. When a provider with a concurrency entry is full, waiting requests go in by priority. A priority:batch (or priority=batch) tag says the same when the header is absent. A request can only lower its own priority
X-Maple-ProviderSent by a client on /v1/files and /v1/batches: the provider account to use, when the query has no provider (see Files and batches)
X-Maple-TagsSent by a client: the request's tags, comma-separated (letters, digits and . _ - : = /, at most 8), kept in the usage log's tags column. x-litellm-tags is read the same way when it is absent
X-Maple-GuardrailsSent by a client: guardrails to run on this request although they are not on by default, comma-separated. On a response: what each guardrail that ran decided, for example pii=masked, keys=passed (labels only)
X-Maple-Usage-RowsOn a download from the setup page's Usage data card: how many requests the exported file holds
X-Maple-Usage-SchemaOn the same download: the version of the usage record schema the file follows
X-Maple-Retry-At, X-Maple-Retry-Basis, X-Maple-Retry-SourceOn a 429 when every route of the request was refused for a limit (a rate limit, a spent quota or budget): when the earliest of them lifts (RFC 3339, UTC), whether the provider stated that time or it is estimated, and what it was read from. Retry-After and the error body's maple_retry say the same. See When a provider's limit runs out
X-Maple-FailureOn an error answer to a chained proxy only: the failure's class (daily budget spent, quota exhausted, rate limited, overloaded, server error, unreachable, chain loop, too many hops), so the proxy below falls back the right way
X-Maple-Chain-Person, X-Maple-Chain-Team, X-Maple-Chain-Origin, X-Maple-Chain-Via, X-Maple-Chain-Ids, X-Maple-Chain-Hops, X-Maple-Chain-Request, X-Maple-Chain-ProofRequest headers a proxy sends to its hub: who asked, the first proxy, the path, the hop count, the request's id, and, for a person a hub above defined, a proof that they signed in with their own token (never the token). A hub reads them only from a proxy-chain token and removes them from every other request
X-Maple-SettingsOn a refused change on the setup page of a proxy whose settings come from its configuration files (storage.settings: file): read-only
Idempotent-Replayedtrue on an answer played back for a repeated Idempotency-Key (see Kubernetes)
X-Maple-Config-BaseOn the setup page's raw configuration: which version of the file it shows. Sent back with a save, a copy that is out of date is refused, so it cannot undo a change made since
X-Maple-Config-PathSent by a maple-proxy command that tells the running proxy about a change it saved: the configuration file it wrote. The proxy applies the change only when that is its own file, and otherwise keeps its configuration

WhereWhat
versionThe configuration file's format version, currently 1
~/.config/maple-harness/config.yamlThe proxy's and the harness's settings
~/.config/maple-harness/embeddings/The installed built-in model for search by meaning, one folder per model, and the cache of computed vectors in cache/, private to you
~/.config/maple-harness/setup-page-password.jsonThe setup page's password as a salted hash, and its signed-in browsers, private to you. Absent when the page has no password
~/.config/maple-harness/access.jsonAccess tokens (hashed) and the remote-control switch. Managed by the setup page
~/.config/maple-harness/chain-bindings.jsonWhich proxy each proxy-chain token is bound to, private to you. Absent until a chain token is bound. Kept apart from access.json so that going back to a 1.x release does not unbind them
MAPLE_DUCKDB (environment)The duckdb program the proxy's analytics refresh and the usage duckdb and usage lake commands run, as an absolute path; --duckdb overrides it. Without it, duckdb on the PATH. A relative path, a program found only through the current folder, or a program or folder any user can change is refused. The program gets a minimal environment, not the proxy's (see the data lake's troubleshooting)
Your system keyringProvider keys and sign-ins. Without a keyring, a private file with the same protection, and the proxy says so
~/.config/maple-harness/usage/maple_harness_proxy_usage_ledger-YYYY-MM-DD.jsonlThe usage log, one file per UTC day, private to you (or <usage_ledger>-YYYY-MM-DD.jsonl when server.usage_ledger names another path; none when it is off). One JSON object per request (see Your usage data): at, duration_ms, requested, model, provider, streamed, tools, messages, input_tokens, output_tokens, cached_tokens, cache_write_tokens, ai_units, error, client, agent, surface, conv, fallback, cache_class, cache_reason, and since schema version 2 schema_version, session, warming, cost_estimated, cost_currency, priced and the per-request cost and savings estimates (types and meanings: the usage record schema).
