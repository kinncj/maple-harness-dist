What /cost tells you #

/cost is the session's own bill, read back to you in plain numbers: what has been spent, request by request, and — new — which parts of the conversation are costing the most by being sent again and again. This page walks through each part of its output and, for each thing it can flag, what to actually do about it. It makes no promise about your bill: read Seeing and reducing what a task costs for the broader picture, and measure your own tasks.

The totals line #

The first line is the session so far: input and output tokens, how many requests were billed, and — where the provider states one — AI units (Copilot) or an estimated dollar figure (see Anthropic and estimated cost below). Under it: the model in use, how many requests were billed against how many were asked again after a failure, and the overall share of input served from the cache.

What to do about it: a retried-request count that keeps climbing on the same kind of task is worth watching — each retry pays for the request twice. If the overall cache share looks low for a task that has run a while, the next section says where in the session that happened.

Subagents #

If this session delegated any work with @agent or the delegate tool, /cost ends with a "Subagents" line — how many ran, and what they cost on their own — and a "Session + subagents" line, which is the true total: the main conversation's own spend plus every subagent's. This is the number that matches what your account was actually billed, and it is why the very first line of /cost (the main conversation alone) can look much smaller than that on a session that delegated most of its real work — the main conversation's own figure was never wrong, it just was not the whole bill. The status bar and /context already show the combined figure; /cost now does too.

What to do about it: if the "Session + subagents" total is far above the main figure, that is expected on a session that used subagents heavily — it is not a sign anything is broken. If you need the true total from a script instead of reading /cost, --json-summary's ai_units (and input_tokens/output_tokens) fields are the combined total too, with subagent_ai_units and friends breaking out just the delegated share.

/savings is a different question — what the harness's own techniques (loop_guard, log shortening, model choice) saved and cost, not the account's true total. A subagent's spend is deliberately never valued there: there is no defensible counterfactual for what its parent would have done instead, so nothing is credited or charged either way. On a session that delegated most of its real work, /savings says this plainly — how many subagents ran and what they cost — rather than the generic message a session where nothing happened at all would show, and points back at /cost for the number that includes them.

The last requests table #

A row per recent request: input, cached, written and output tokens, AI units, the cache hit rate for that one request, and the model. Two things get flagged automatically:

  • "model changed" — a different model answered this request than the one before it. A new model starts with nothing cached, so the whole conversation is billed again at full price on its first turn.
  • "low cache hit" — this request's own hit rate fell well below what the rest of the session is getting.

What to do about it: if you see "model changed" more than once in a task you meant to keep on one model, check whether /model auto is switching under you, or whether you switched by hand — either way, staying on one model for the rest of a long task avoids paying to rebuild the cache again. "low cache hit" with nothing else unusual is often something upstream of that request changing the start of the conversation; it is worth a look at what happened right before it.

Where the next request's input goes #

An estimated breakdown of what the next request would send, by kind: the system prompt, the tools on offer, your own messages, anything looked up on your behalf, the model's own replies and tool calls, and tool results. It is a token-count estimate (about four characters to a token), useful for proportions rather than an exact figure.

What to do about it: if tool results dominate this breakdown, the next section names which ones and why.

Most expensive tool results #

A tool's result is not paid for once. It stays in the conversation and is sent again on every request after it, until it is trimmed or the session ends — so a single large result from early in a long session can end up costing far more than its own size ever suggested. This section ranks the tool results still in the conversation by that real cost: the result's size multiplied by how many times it has been sent again since it first appeared, both for individual calls and totalled by tool name.

A result that has not been sent again yet shows no cost here, even if it is large — the cost is in the resending, not in the one call that produced it.

What to do about it, per line:

  • A large read_file or grep result high on the list: ask for less next time it comes up — a narrower pattern, or a line range instead of the whole file — and, if the information in it is no longer needed, say so; it stays in the conversation until something removes it.
  • One tool name dominating the "by tool" total: that is usually a habit worth changing for the rest of the task — a search being repeated instead of reused, or a whole file being read where a smaller one would do.
  • Nothing shown here at all: either the session is early (nothing has been resent yet) or your tool results are simply small relative to the rest of the conversation — nothing to act on.

Today the harness only shortens a failed command's output for you automatically (see /savings); a large result from a call that succeeded is kept exactly as it came back, because shortening it without being asked could remove something the model still needs.

Anthropic and estimated cost #

Copilot states a price for every call it serves. Claude through Anthropic's own API does not — its responses carry token counts only, never a price. /cost reflects that honestly: an Anthropic request shows its tokens like any other, and no price, unless the provider is set up to estimate one.

An operator can turn on estimate_cost for an Anthropic provider (see the proxy reference), which prices each such call from Anthropic's own published rates instead. This figure is always shown as an estimate — in dollars, never mixed into Copilot's AI-units figure — because it is a list-price guess, not what the account was actually billed: a committed-use rate, a promotion, or a change to Anthropic's prices since this was last updated could all make it wrong in either direction.

What to do about it: if you rely on a precise bill, check your provider's own account page rather than this figure. If Anthropic's calls in /cost show tokens but never a dollar figure at all, estimate_cost is either off or the model in use is one this estimate does not yet cover — either is fine to leave as is if you only need the token counts.
