Memory caps and heavy runs #

The agent runs commands for you: tests, builds, scripts. Some of them use a lot of memory, and several agents can start several of them at once. Maple Harness caps how much memory those commands may use, and lets only one heavy run (a test suite, a build) go at a time, so the commands it runs can never take your whole machine.

Stopped at a cap is not a crash

When a command is stopped at a cap, that is the cap working, not a crash and not a memory leak in Maple. The message says which cap it was and how to change it.

The short version

In plain words #

  • What it is. A ceiling on the memory of each command the agent runs, another on all of one session's commands together, and a queue for heavy runs so two test suites never fight over your memory.
  • Why it is there. A few test suites run at the same time, or one test that reads without a limit, can fill all of a computer's memory in seconds. The system then starts killing programs at random, often your terminal or your browser. The caps stop the one command that went too far, and nothing else.
  • What you do. Usually nothing: the defaults are safe. If a command you trust really needs more, raise its cap in /settings (search for limits) or in config.yaml. If you have plenty of memory and want two test suites at once, set limits.heavy_runs to 2 or auto.
  • What you see. A stopped command says, in one line, stopped at the memory cap, which cap, and this page. A command waiting its turn says waiting for a heavy-run slot and who holds it.

What is capped #

CapWhat it coversDefaultSetting
Per commandOne command the agent runs (a bash call or a background job) and every process it starts, togetherHalf of your memory, at most 8 GiBlimits.command_memory
Per sessionEvery command one session runs, its helper agents' included, togetherHalf of your memorylimits.session_memory
Heavy runsHow many test suites and builds run at once, across all your sessions and agents on this computer1limits.heavy_runs

Not capped: Maple Harness itself, the proxy, and programs you start yourself. A command typed into a terminal pane (pane_run) is capped only when it is a heavy run, on Linux with a user systemd (below), and when your shell is a POSIX one (sh, bash, zsh, dash, ksh); it then runs as sh -c '…' under the cap, so your shell's aliases and functions do not apply to it. It never waits for a heavy-run slot, because Maple cannot see when a pane's command ends. An agent started in a pane (agent_start) is not capped by this session: a Maple Harness session there caps its own commands.

"Half of your memory" is the memory this program may use: inside a container or a limited desktop session, that limit counts, not the whole machine's. Inside such a limit no cap is ever larger than it, whatever the settings say, and the limit on the number of processes is passed on too.

Why these defaults #

The figures were chosen, not measured: 8 GiB is enough for a large race-enabled Go test suite or a big build, and one heavy run at a time is the rule that kept a busy machine usable once several agents worked on one project. A command that needs more than 8 GiB is rare, and when one does, it is better to hear it plainly and raise the cap on purpose.

What counts as a heavy run #

A command is a heavy run when its first words are one of these (after cd … &&, environment settings such as CI=1, and wrappers such as time, nice or timeout 600):

go test, go build, go install, make, gmake, ninja, cmake --build, ctest, bazel, bazelisk, cargo test, cargo build, cargo nextest, npm test, npm run test, npm run build, npm ci, pnpm test, pnpm run test, pnpm build, pnpm run build, yarn test, yarn build, yarn run test, yarn run build, bun test, npx jest, npx vitest, npx playwright test, pytest, python -m pytest, python3 -m pytest, tox, nox, mvn, gradle, gradlew, dotnet build, dotnet test, swift build, swift test, docker build, podman build.

The agent can also mark a command it knows is heavy (a project's own test script), and it then waits like the others. It can never take a command out of the list. You can:

  • add your own with limits.heavy_commands, for example just ci or task test;
  • take one out with limits.not_heavy, for example make lint.

make targets that start something long-running or small are never heavy runs: make serve, make server, make dev, make run, make watch, make start, make up, make down, make logs, make help, make clean, make fmt, make format and make docs-serve.

What a cap hit looks like #

In the conversation, under the command, one line for you:

■ stopped at the memory cap: the command used more than 8 GiB (harness.limits.command_memory). A limit, not a crash or a leak: https://kinncj.github.io/maple-harness-dist/docs/memory-limits.html

The agent reads the full reason before the command's output: the cap, its setting, that it is not a crash, and what to try instead (a smaller part of the test suite, fewer jobs at once such as go test -p 2 or make -j2, or looking for something that reads without a limit). It is told not to run the same command again unchanged, and to ask you if the command really needs more.

When the session cap is the one hit, the line says this session's commands used more than … (harness.limits.session_memory), and the command stopped is the one using the most. Background jobs you no longer need count towards it: the agent can stop them with kill_shell.

If the computer itself ran out of memory (something else used it all), the line says so and that it was not one of Maple's caps.

After a cap hit the session carries on normally: only that command was stopped.

What waiting for a slot looks like #

A heavy run that finds every slot taken waits, and you see who has it:

waiting for a heavy-run slot: 1 of 1 in use by session fix-auth (pid 4242): "go test -race ./..." for 2m10s. It starts as soon as one is free (harness.limits.heavy_runs).

When it gets its turn it runs, and its result starts with how long it waited. The wait does not count against the command's own timeout. Esc stops the wait like any command; a command that waits longer than limits.heavy_wait (30 minutes) is not run, and the agent is told why. In a run nobody watches (--prompt, --rpc, serve, a2a serve) the wait is limits.heavy_wait_headless (10 minutes), so a script fails sooner. Both take 1m, 2m, 5m, 10m, 15m, 30m or 1h. A background job (run_in_background) gets its id at once, bash_output says it is waiting, and kill_shell cancels it before it starts. A background job gives its slot back after 30 minutes even if it is still running, so a long one cannot hold off every other session.

What a waiting command shows about the holder (its session, its command) was written by another program, so it is cleaned of anything a terminal would act on, shortened, and the command is shown in quotes.

A slot held by a session that ended, however it ended (closed, crashed, killed), is free again at once.

Change the caps #

  1. In a session, type /settings, then limits to filter the menu. Each cap shows its value, what it does and what it accepts.
  2. Press Enter on one, type the new value (empty goes back to the default), and Enter again: it is saved to your own config.yaml.
  3. Start a new session: the caps are read when a session starts.

Or in config.yaml:

YAML
harness:
  limits:
    command_memory: 12G      # a size (512M, 4G, 1.5G), auto, or off
    session_memory: auto     # a size, auto, or off
    heavy_runs: auto         # 1 to 64, auto, or off
    heavy_commands: [just ci, task test]
    not_heavy: [make lint]
  • Sizes are in binary units: 1G is 1024 MiB. The smallest cap is 64M.
  • heavy_runs: auto allows one heavy run per command_memory of memory free when the run starts (one per 8 GiB with the default cap), at least 1 and at most 8.
  • These settings are yours: a project's own .mapleharness/config.yaml cannot set or loosen them.
  • Changes apply the next time you start a session.

off is a real off

off turns a cap off. It is there for a machine where you would rather have the old behaviour, and it is not recommended: with no cap, a few test suites at once, or one test that reads without a limit, can fill the machine's memory, and the system then stops programs it picks itself, often your terminal.

A cap for one agent #

An agent's file can give it a lower cap of its own (limits.memory: 4G, see Make your own): each command that agent runs may use at most that much, never more than command_memory. It applies even with command_memory: off. A command stopped at it says stopped at this agent's memory cap, names limits.memory in the agent's file, and is otherwise reported like any other cap hit.

For the curious

Technical details #

Linux with a user systemd (most desktop distributions): each command runs in its own transient systemd scope with MemoryMax set to the command cap, MemorySwapMax=0 (so a command cannot get around the cap by swapping), and OOMPolicy=kill (when the kernel stops the largest process, the rest of that command stops with it, so a pipeline does not carry on as if it worked). All of a session's scopes sit in one slice, maple-h<pid>.slice, that carries the session cap. The kernel enforces both, at once. You can see them with systemctl --user list-units 'maple-*'. Maple runs systemd-run, systemctl (and on macOS ps) only from the system's own folders, never from your PATH.

Linux without a user systemd, and macOS: Maple reads the memory of the command's process tree twice a second and stops the whole tree once it is over the cap. It counts each process's resident memory, so memory shared between processes counts more than once and a command may be stopped a little earlier than a kernel cap would stop it. A command that allocates very fast can go over by what it allocates in half a second before it is stopped, and a command short enough to finish within half a second may not be measured at all. A process that leaves the command's process tree on purpose (a daemon that detaches itself) can leave the watch. On macOS this has not been run on a Mac yet.

Windows: no memory cap is applied in this release. Heavy-run slots work.

The address-space limit (ulimit -v, RLIMIT_AS) is not used on purpose: it limits reserved address space, not memory, and some tools reserve far more than they use (Go's race detector reserves terabytes), so they could not run under it at all.

Heavy-run slots are small lock files in a folder only you can use (under $XDG_RUNTIME_DIR when it is set, otherwise in the temporary folder), shared by every Maple Harness session of your user on this computer. Each slot is held by an operating-system lock, which the system releases the moment the process holding it ends. If that folder can be written by other users, slots are not used, and the command says so.

Process counts were already capped separately: a command that starts processes without end is stopped and told so. See Harness settings.
