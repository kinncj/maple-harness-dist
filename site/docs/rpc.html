    Drive it from another program #

    On this page

    maple-harness --rpc reads commands from another process instead of a person, and writes back everything that process needs to follow along: the model's own output, tool calls and results, questions that need an answer, and the running cost — as it happens, not only once the whole session ends. It is how a CI step, an editor plugin, or a script of your own drives a session the same way the terminal interface does.

    The short version

    In plain words #

    • What it is. A way for another program (a CI job, an editor plugin, your own script) to drive a Maple session, line by line, as the terminal does.
    • Why you want it. Automate the agent and still see every tool call, question and cost as it happens.
    • What to do. Start maple-harness --rpc from your program and exchange one JSON object per line. The commands and events follow.

    Start it #

    Shell
    maple-harness --rpc

    It never starts on its own; it is meant to be the child of whatever is driving it. One JSON object per line comes in on stdin, one JSON object per line goes out on stdout. Nothing else is written to stdout — diagnostics and notes go to stderr, the same convention --prompt uses, so a plain harness --rpc < commands.jsonl > events.jsonl captures exactly the protocol.

    It cannot be combined with --prompt, --repl or --remote: each is its own way of driving the session, and --rpc is this one.

    Nobody can answer a question here, so when the proxy on this machine cannot be verified as yours, --rpc does not start: it writes nothing on stdout, prints the reason and the fixes on stderr, and exits with status 1. Start the proxy as the same user with the same settings folder (or let the harness start it), or see CI jobs and containers for a proxy you do not start.

    Commands #

    Every line you send is one JSON object with a cmd field, and an optional id you choose — it comes back on the response so you can match one to the other.

    cmdWhat it does
    promptStarts a new turn with text. Rejected while one is already running — say steer or follow_up instead, because they mean different things.
    steerAdds text to the turn that is running right now, delivered after its current tool calls finish and before the model is asked again. Rejected when nothing is running.
    follow_upQueues text for after the running turn finishes, or starts it at once if nothing is running.
    sendA message the way the terminal takes one: it starts a turn when nothing runs; while one runs it steers it or queues for after it. mode says which (steer or queue); without it (or auto) the words decide, by the terminal's rules ("also …" steers, "then …" queues). The response's disposition is started, steered or queued.
    abortCancels the running turn and refuses any permission question it left open. A no-op when nothing is running.
    limit_resumeEnds a wait for a provider's limit now and tries again (the terminal's /resume now); if the limit is still there, it waits again. disposition resumed, or noop when nothing waits. See When a provider's limit runs out
    permission_answerAnswers a permission_request event by its request_id, with allow (and optionally always, for the rest of the session).
    question_answerAnswers a question_request event by its request_id, with answers (one per question), or "decline": true to skip it.
    JSON
    {"id": "1", "cmd": "prompt", "text": "add a test for the empty-cart case"}

    The response says what happened to the command itself, not how the turn it may have started turns out:

    JSON
    {"type": "response", "id": "1", "cmd": "prompt", "ok": true, "disposition": "started"}

    disposition is started (a new turn began), queued (waiting for the current one), steered (a send that went into the running turn), aborted, noop, or handled (a permission or question answer). A steer that was accepted answers queued, as it always has: it waits for the turn's next step. ok: false carries an error saying why — malformed JSON, a missing field, an unknown command, or a command that does not apply right now (a prompt while one is already running, a steer with nothing to steer). None of these stop the session; the next line is read as normal.

    Events #

    What the turn itself does streams as further lines, "type": "event", tagged by event:

    eventCarries
    assistant_delta / assistant_donetext (and thinking, when the model reasoned)
    tool_call / tool_resulttool, tool_arg
    steeredtext — a steer (a steer command, or a send that steered) landed and is now part of the conversation
    noticetext — something worth telling a person, from the harness itself
    permission_request / permission_resolvedA tool call waiting for approval, and its answer (below)
    question_request / question_resolvedThe model's question to the person, and how it ended (below)
    limit_wait / limit_resume / limit_stoptext; limit_wait also carries retry_at (RFC 3339): every route is out of a provider's limit and the turn waits until then. Let it wait, send limit_resume, or abort. A wait longer than harness.limits.max_reset_wait is asked first, as a permission_request for wait_for_reset (allow waits, deny stops)
    turn_start / turn_endmsg_id; turn_end also carries stop_reason, error if any, and usage

    usage is the session's running total — tokens, cache reads and writes, AI units — the figures --prompt --json-summary writes as its session_* fields, sent after every turn rather than only once at exit. It is the true total: if this turn delegated work to a subagent (see subagents), that subagent's own tokens and AI units are folded in here too, the same as they are in /cost and the status bar — not just the driving turn's own requests.

    JSON
    {"type": "event", "event": "turn_end", "msg_id": "m1", "stop_reason": "end_turn",
 "usage": {"turns": 3, "input_tokens": 8120, "cached_tokens": 7200, "cache_write_tokens": 400, "output_tokens": 540, "ai_units": 4.1}}

    A permission question #

    A tool call that needs approval under your permission settings — the same settings --yolo and the interface's own mode control (ask/auto/yolo) govern — is not decided for you. It arrives as an event:

    JSON
    {"type": "event", "event": "permission_request", "request_id": "a1b2c3", "tool": "bash", "tool_arg": "rm -rf build/"}

    Answer it the same way a person would:

    JSON
    {"cmd": "permission_answer", "request_id": "a1b2c3", "allow": true}

    and a permission_resolved event confirms it, with allow and always. A question left unanswered waits up to harness.approvals.timeout (10 minutes by default), as it would for a person at a terminal; then that one call is denied, a permission_resolved event says so, and the turn goes on. harness.approvals.timeout: off waits as long as it takes, as before 3.0. --allow-tool, --deny-tool and --policy work with --rpc too. See Approvals when nobody answers.

    A question for the person #

    When the model asks the person to choose (Questions the agent asks you), the dialog arrives as an event, with subagent set when a subagent asks:

    JSON
    {"type": "event", "event": "question_request", "request_id": "q-7", "questions": [
  {"id": "storage", "header": "Storage", "question": "Where should sessions live?", "allow_other": true,
   "options": [{"label": "Redis", "description": "Shared, survives restarts"}, {"label": "Memory", "description": "Simplest"}]}]}

    Answer with the option labels picked (any case), an other answer in your own words where allow_other is true, and a note, one entry per question; or "decline": true to skip the dialog and let the model decide:

    JSON
    {"cmd": "question_answer", "request_id": "q-7", "answers": [{"id": "storage", "selected": ["Redis"], "note": ""}]}

    A question_resolved event follows, with request_id, status (answered or declined), by (who answered: rpc, terminal, phone, …) and summary, the answer on one line. An answer that does not fit the questions is refused (ok: false, with the reason) and the question stays open; one that comes after another answer won says already answered, or no such question. The model is told the answer came over --rpc. An answer is information for the model, never an approval: a tool call after it still sends a permission_request as your settings say.

    Launch it from another program #

    A program that opens the harness in a terminal pane for a person (an orchestrator, an editor, a script that sets up a task) can use these instead of the pipe above:

    • Start with a task. maple-harness --message "implement story 12" (or the text after the flags) starts the interface with that as the first message, as if typed. From a script, use --message "$TASK": text after the flags that starts with - is read as a flag, and a single word that names a command runs the command. Add --yolo for a run that should not stop to ask.
    • Find and resume sessions. maple-harness sessions list --json lists saved sessions (name, folder, title, times, messages, tool calls, tokens, and the command line that resumes each); sessions show <name> --json adds the transcript, with each tool call's arguments and each result (file contents and command output included). Both carry "schema": 1, which changes only if a field is removed or changes meaning. Resume with maple-harness --session <name>.
    • Project rules. Hooks in a project's .claude/settings.json, written for Claude Code, run here too, after the person trusts the project; see Hook files.
    • See its state. In herdr, the pane shows whether the session is working, waiting for approval or idle; anywhere, the window title says the same.

    What it is not #

    This is a local pipe between a parent process and the child it started — there is no listening address and no token, because whoever can write to this process's stdin already has everything a shell here would give them. If you want a session another device can join over the network instead, see Control it from your phone, which is a different feature with its own, separate authentication.
