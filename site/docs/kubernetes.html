    This page runs maple-proxy on Kubernetes from the samples in the infra/ folder of the public repository: plain manifests with Kustomize overlays for one replica, or three replicas sharing PostgreSQL and Redis. They are starting points: read them and adapt them to your cluster.

    The samples #

    FolderWhat it is
    manifest/maple-proxy/The proxy: Deployment, Service, PodDisruptionBudget, an example ConfigMap and an example Secret
    manifest/postgres/, manifest/redis/One PostgreSQL and one Redis, for trying it out. In production use your managed or production services, with backups
    manifest/maple-mcp-hub/The MCP hub as one replica of its own
    config/single/One replica, its state on a PersistentVolumeClaim: the proxy as on a machine
    config/ha/Three replicas, shared state in PostgreSQL and Redis, settings from the ConfigMap
    manifest/maple-lake/, config/ha-lake/Usage history in a DuckLake (see Usage for analysis)

    Every pod runs as a non-root user with a read-only root file system, no added capabilities, the default seccomp profile and no service-account token; it has liveness, readiness and startup probes, resource requests and a memory limit.

    One replica #

    1. Build and push the image (no image is published; see Docker):

    git clone --depth 1 https://github.com/kinncj/maple-harness-dist.git
cd maple-harness-dist/infra/docker
docker buildx build --build-arg MAPLE_VERSION=v2.0.0 --platform linux/amd64,linux/arm64 \
  -t registry.example.com/you/maple-proxy:2.0.0 --push .

    2. Set the image and the secrets. In config/single:

    cd ../config/single
kustomize edit set image maple-proxy=registry.example.com/you/maple-proxy:2.0.0

    Edit manifest/maple-proxy/secret.example.yaml (or create the Secret maple-proxy from your secret manager): the key access.proxy_tokens holds one label=value per line, the tokens your tools use (with mh_ in front). Each key of the Secret is a file in /run/secrets/maple, read-only.

    3. Apply and check:

    kubectl apply -k .
kubectl -n maple rollout status deploy/maple-proxy
kubectl -n maple logs deploy/maple-proxy

    Tools in the cluster reach http://maple-proxy.maple.svc:11535/v1 (OpenAI) and :11537 (Anthropic). From outside, add an Ingress or a LoadBalancer Service with HTTPS. The proxy answers only to host names it knows: MAPLE_ALLOWED_HOSTS in the Deployment lists the Service's names; add yours.

    The setup page is served only on the pod's own loopback address, as on a machine. Reach it with a port forward, which connects to the pod itself:

    kubectl -n maple port-forward deploy/maple-proxy 11539:11539

    and open http://127.0.0.1:11539. In this overlay, settings are kept on the volume like on a machine: change them on the page. The models for search by meaning download to their own volume (maple-models).

    Several replicas #

    When you need it #

    One replica is enough for most teams: the proxy is light, and a restart takes seconds. Run several when a restart or a lost node must not interrupt anyone, or when one replica is not enough. Several replicas need PostgreSQL and Redis (storage.mode: central): a replica then keeps nothing that matters on its own, so any replica can serve any request, and a replica can stop at any time.

    What lives where #

    WhatOne replica (storage.mode: disk, the default)Several replicas (storage.mode: central)
    Usage logDaily files on the volumePostgreSQL (each line once), and a copy on each replica's own folder
    Events, alerts firedFiles on the volumePostgreSQL; each alert fires once, on one replica
    Audit logA file on the volumePostgreSQL too (maple-proxy audit tail reads both)
    Person and team budgetsCounted in memory from the usage logPostgreSQL, counted as each request ends; the day is the database's
    Provider budgets (budgets:)Counted in memory from the usage logEach replica counts every replica's requests, within seconds
    Settings (config.yaml) and access tokensFiles on the volumeThe ConfigMap and Secret (read-only on the page), or PostgreSQL (storage.settings: central)
    The setup page's passwordA file on the volumePostgreSQL
    Signed-in browsers, wrong-password countsMemory and a fileRedis
    Rate limits, bad-token throttleMemoryRedis
    Quota marks, provider healthMemoryRedis
    Response and embeddings cachesMemory (and a file for embeddings)Redis, encrypted with storage.key
    Conversation pinsnoneRedis
    Repeated requests (Idempotency-Key)MemoryRedis
    Cards (cache, savings, sessions) and learned pricesMemory, saved to filesRebuilt from every replica's usage in PostgreSQL
    Embedding modelsThe volumeEach replica's folder, or one shared volume
    The MCP hubIn the proxyOne replica of its own

    Set it up #

    config/ha adds PostgreSQL and Redis samples, three replicas, and settings from the ConfigMap:

    cd config/ha
kustomize edit set image maple-proxy=registry.example.com/you/maple-proxy:2.0.0

    Edit the Secret patch in kustomization.yaml (and manifest/postgres/service.yaml's password, the same in both):

    Secret keyWhat it holds
    storage.postgres_dsnpostgres://user:password@host:5432/db?sslmode=require
    storage.redis_urlredis://:password@host:6379/0, or rediss:// for TLS
    storage.key64 hex characters (openssl rand -hex 32): encrypts what goes to Redis
    proxy.request_hash_salt, embeddings.cache_key, events.fingerprint_keyOptional. Left out, each is derived from storage.key, so every replica has the same ones and the shared caches work across replicas. If you set them, 64 hex characters each, the same for every replica: a replica refuses to start with a placeholder such as REPLACE-ME, or with values other than those of a replica that is running (to change them, or storage.key, stop every replica first)

    The Deployment refers to them as ${secret:storage/postgres_dsn} and so on, never by value. Then:

    kubectl apply -k .
kubectl -n maple rollout status deploy/maple-proxy

    The first replica creates the tables (the others wait for it), and each replica's start line says storage=central with its name.

    Settings: from the ConfigMap, or from the page #

    • From the ConfigMap (MAPLE_SETTINGS_SOURCE=file, the sample's choice): config.yaml is the ConfigMap, managed like the rest of your cluster. The setup page shows everything, usage included, and refuses changes with a note that settings come from the configuration files (the X-Maple-Settings: read-only header). Change the ConfigMap and roll the replicas out.
    • From the page (MAPLE_SETTINGS_SOURCE=central): config.yaml and the access tokens are kept in PostgreSQL. A change on any replica's page reaches every replica within a second or two, and a revoked token is refused by every replica within a second. Two changes at the same moment on two replicas do not merge: the first saved is kept and the other is put back, and the log says so.

    Provider sign-ins. A provider with an API key in the Secret (${secret:provider/<id>/api_key}) works on every replica. A sign-in made in the browser (GitHub Copilot's device sign-in) is kept by the replica it was made on; with several replicas, sign in on each, or prefer a key. The short-lived session token a signed-in account gives is shared: one replica asks for it, the others use it.

    Load balancing #

    • Round robin is right: nothing needs sticky sessions. A conversation keeps to the provider account that last answered it on every replica (so the provider's prompt cache keeps hitting), signed-in browsers are known to every replica, and rate limits count across replicas.
    • If you want them anyway, hash on the X-Maple-Session header that Maple Harness sends.
    • Never let the load balancer retry a POST on another replica: a model request is not safe to send twice. A client that retries can send an Idempotency-Key header: a repeat with the same key gets the same answer and is not charged again, on any replica; a repeat while the first is still running is refused with 409; a streamed answer cannot be played back, so its repeat is refused with 409 saying so.
    • Keep idle and read timeouts long (streams can take minutes; the keep-alives arrive every 15 seconds).
    • Behind an Ingress or a load balancer that adds X-Forwarded-For, list its addresses in server.trusted_proxies (or MAPLE_TRUSTED_PROXIES): the addresses of your Ingress controller's pods, and nothing wider, since anything inside a listed range can name its own client address. The balancer must add the client to the header, not pass on the one the client sent. Otherwise every request seems to come from the balancer, and one client sending wrong tokens gets every client refused with 429 for a minute. With it, each client is counted on its own; a header from any other address is ignored, so a client cannot choose its own address. A Service on its own (no Ingress) adds no header and needs nothing.

    When PostgreSQL or Redis is away #

    • PostgreSQL away: requests are still served. Requests of people with a budget are refused with 503 until it is back (storage.budgets_when_down: open lets them through, uncounted). Usage lines wait in a small queue in the replica's memory (storage.spool_max_records, 2000) and are written once it is back, each once. They are lost if the replica stops before then, and the log says how many. /readyz says not ready.
    • Redis away: requests are still served. The setup page answers 503 (signed-in browsers cannot be checked), rate limits refuse callers from other machines and so does the wrong-token limit for a wrong or missing token (a valid token is still served), caches miss, conversation pins and shared quota marks fall back to each replica's own, and no replica runs the jobs only one replica runs. /readyz says not ready.

    Use a single Redis (or one with a standby); a Redis cluster is not supported.

    Keep PostgreSQL and Redis to the proxy. The settings kept in PostgreSQL (config.yaml, the access tokens and the setup page's password) are signed with a key derived from storage.encryption_key, and every replica checks the signature each time it reads them: a copy changed in the database by someone without that key is refused. The replicas keep the copy they had (a row removed from the table counts as changed), put it back, write a SECURITY line to the log and record a settings.refused event. A replica that starts while the shared copy is refused does not start until a running replica has put a good copy back (with none running, restore the maple_documents table from a backup). Budgets, usage and sessions are not signed, so still treat write access to either database as admin access to the proxy. The samples allow only the proxy's pods (and the lake jobs) in with NetworkPolicies and give Redis a password; use TLS (sslmode=require, rediss://) when they are outside the cluster.

    Upgrades #

    Roll replicas out one at a time (the sample sets maxUnavailable: 0). A new release adds to the database's tables and never removes or renames anything that the release before still uses, so old and new replicas run side by side during the rollout; upgrade one release at a time. A replica that stops turns not ready first, waits for endpoints to drop it (preStop, 5 seconds; it needs Kubernetes 1.30 or later), finishes its running requests and streams (up to terminationGracePeriodSeconds, 600 in the sample), then exits.

    Backups #

    Back up PostgreSQL (pg_dump, or your provider's backups): it holds the usage, events, budgets, settings and audit log. Redis holds nothing that must survive: after losing it, browsers sign in again and caches fill again. Old usage is deleted after server.usage_retention_days by one replica.

    Usage for analysis #

    The shared PostgreSQL holds every replica's usage and events as two read-only views with typed columns: maple_usage_rows (every column of the usage record, in its order, after _day, _ingested_at and _ingest_seq) and maple_events_rows (the events columns after _event_id, _day, _ingested_at, _ingest_seq and _proxy_instance). Give analysts a PostgreSQL role that can only read them, and they can query them from DuckDB directly:

    INSTALL postgres; LOAD postgres;
ATTACH 'host=postgres.maple.svc dbname=maple user=analyst' AS maple (TYPE postgres, READ_ONLY);
SELECT person, sum(ai_units) AS ai_units, count(*) AS requests
FROM maple.public.maple_usage_rows
WHERE at >= now() - INTERVAL 7 DAY
GROUP BY person ORDER BY ai_units DESC;

    maple-proxy usage query and usage export, run in a replica (kubectl exec), read the same data.

    Keep a short window in PostgreSQL and the whole history in a lake. PostgreSQL is the live database; it keeps storage.retention_days of usage and events (by default server.usage_retention_days, 90). For history beyond that, manifest/maple-lake (and the overlay config/ha-lake) copies closed periods into a DuckLake every hour: its catalog in its own schema (maple_lake) of the same PostgreSQL, its data files on a volume or in S3. The copy only ever adds, each line once, so deleting old rows in PostgreSQL never removes anything from the lake. The jobs run the official DuckDB image on SQL the proxy writes for you (maple-proxy usage lake --emit-sql move for the hourly job, and --emit-sql maintain for the daily job that merges small files and removes what old snapshots no longer need); generate it again after an upgrade. A lake keeps one source: once the move has filled it, a run that would load a machine's daily files into it is refused (--allow-mixed-sources overrides that). For S3, give the job credentials in its Secret or, better, workload identity (IRSA, Workload Identity).

    What changes the cost: how often the copy runs (more often means fresher history and more, smaller files to merge), how long PostgreSQL keeps rows (its size), how often maintenance runs and how many old snapshots it keeps (the lake's storage), and where the data files live (a volume, or object storage and its requests). Analysts attach the lake read-only the same way. maple-proxy usage lake --emit-sql attach --catalog-dsn-env MAPLE_POSTGRES_DSN --data-env MAPLE_LAKE_DATA_PATH prints what to run in duckdb, with MAPLE_POSTGRES_DSN set to a read-only connection string for the analyst (host=postgres.maple.svc dbname=maple user=analyst, for example) and MAPLE_LAKE_DATA_PATH to the data path. For data in S3 (s3://your-bucket/maple/) add --s3, which also loads the httpfs and aws extensions and reads credentials from DuckDB's credential chain. Without it, the command prints:

    -- Maple usage lake, read-only. Needs DuckDB with the ducklake extension (INSTALL ducklake; once),
-- the postgres extension (INSTALL postgres; once) and the catalog's connection string in $MAPLE_POSTGRES_DSN.
INSTALL ducklake;
INSTALL postgres;
LOAD ducklake;
LOAD postgres;
CREATE OR REPLACE TEMPORARY SECRET maple_lake (TYPE ducklake, METADATA_PATH getenv('MAPLE_POSTGRES_DSN'), METADATA_SCHEMA 'maple_lake', DATA_PATH getenv('MAPLE_LAKE_DATA_PATH'), METADATA_PARAMETERS MAP {'TYPE': 'postgres'});
ATTACH 'ducklake:maple_lake' AS maple_lake (READ_ONLY);
USE maple_lake;
-- For example:
--   SELECT * FROM maple.daily_spend ORDER BY day DESC LIMIT 20;
--   FROM maple_lake.snapshots();                                -- the lake's versions
--   SELECT count(*) FROM main.usage AT (VERSION => 3);          -- as it was at one of them

    More in The Maple data lake.

    The MCP hub #

    The hub's servers are programs and sessions that live on one machine, so the hub runs as one replica of its own (manifest/maple-mcp-hub, started with maple-proxy mcp-hub serve), with its own ConfigMap; clients connect to its Service. The proxy replicas do not serve it. It has a Secret of its own: never mount the proxy's in its pod, since the hub runs other programs. Off the pod's loopback address the hub needs TLS, or insecure_http behind an Ingress that terminates TLS, and an mcp-hub token.

    Run MCP servers as containers of their own. A stdio server is a program the hub starts. On a machine the hub starts it inside a sandbox; the container image has no sandbox (it would need user namespaces, which most clusters do not give a pod), so there the hub refuses to start a stdio server and says why. Instead, run each server as its own container that serves MCP over HTTP, and add it to the hub by URL (type: http):

    • As a sidecar in the hub's pod (manifest/maple-mcp-hub/sidecar.example.yaml): the server listens on the pod's loopback address and the hub reaches it at http://127.0.0.1:<port>/mcp with allow_private: true. It has its own image, user and limits, and the hub's Secret is not mounted in it. It shares the pod's network.
    • As its own Deployment and Service for a server you trust less, with a NetworkPolicy that lets only the hub in; add it with the Service's URL and allow_private (and allow_insecure, or give it TLS).

    mcp_hub.allow_uncontained_stdio: true starts stdio servers in the container anyway, without containment: such a program can read everything the hub's container can, its mounted Secret included, and reach the network. Use it only for programs you would trust with that Secret.

    Its tokens come from that Secret: access.mcp_hub_tokens, one label=token per line (make each token with openssl rand -hex 24), the same way the proxy's tokens come from access.proxy_tokens. They get the mcp-hub scope only, and only in the hub's pod. To revoke one, take its line out of the Secret: the hub applies the change within a minute, without a restart, and removing every line (or the key) revokes them all. An example value left in place is refused, so the hub does not start with a token anyone could read. Refused requests go to the hub's audit log, as the proxy's do.

    Reaching cloud metadata or link-local services #

    The hub never connects an MCP server to a link-local address (169.254.0.0/16, fe80::/10) or a cloud metadata address (such as 169.254.169.254 or fd00:ec2::254), also in the standard IPv6 forms that carry such an address, and allow_private does not change that: on a node, the metadata address hands out the node's or the pod's cloud credentials to whatever asks, and a server address that ends up there (a typo, a changed DNS record) would let an MCP connection read them.

    If a server you trust really lives at one of these addresses, list the exact addresses, each with a port if you like, in MAPLE_MCP_ALLOW_ADDRESSES on the hub's container. It is read only from the environment, never from the ConfigMap, the Secret or the setup page, so it changes only with the Deployment itself:

    # manifest/maple-mcp-hub/deployments.yaml
spec:
  template:
    spec:
      containers:
        - name: maple-mcp-hub
          env:
            - name: MAPLE_MCP_ALLOW_ADDRESSES
              value: "169.254.170.2:80"   # exact addresses only: no names, ranges or wildcards

    A bad value stops the hub from starting, with a message in its log. When set, the hub logs a warning with the addresses at start, maple-proxy mcp-hub status shows them, and the first connection by each server to each is written to the audit log. An allowed address in a private range (such as fd00:ec2::254) also needs allow_private on the server. Whatever answers at an allowed address can be reached by every server that resolves there, so allow as few as you can. More in MCP hub.

    Logs #

    kubectl -n maple logs deploy/maple-proxy -f
kubectl -n maple logs -l app.kubernetes.io/name=maple-proxy --prefix

    Logs are JSON on standard output, one object per line, with proxy_instance naming the pod; see Docker: Logs for the fields, levels and shipping. Probes are left out of the request log.

    Images and memory #

    The pod's memory limit sets how much image resizing may take at once (25% of it by default) and Go's own memory limit (90% of it); see Docker: Images and memory. Raise limits.memory, or images.resize_memory, if your tools send many large screenshots at once.

    Search by meaning #

    Each replica downloads a model on first use into its own folder (an emptyDir in config/ha). To download once for all, mount one ReadWriteMany volume at /models in every replica: replicas installing the same model at the same moment wait for one another, and each download is checked against its pinned checksums before it is moved into place.
