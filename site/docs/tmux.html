Use it with tmux #

On this page

  2. What you can do

  5. Technical notes
  6. Tested versions
  7. If it does not work

Maple Harness can open panes and windows beside itself in tmux, the way it does in herdr: to run a server or a long build next to the conversation, to start another agent, or to open a file, a diff or a worktree. WezTerm and kitty work the same way.

The short version

In plain words #

  • What it is. When you run Maple inside tmux, the agent can split the window or open a new one, run a command there and read what it printed, and start another agent (a second Maple session, Claude Code, Codex) in a window of its own. You can do the same yourself with /tab, /pane, /panes and /worktree.
  • What it asks. A command in a pane runs outside the agent's sandbox, so the agent asks you every time before it types one or starts an agent, even in auto mode. Your own commands run straight away.
  • What to do. Nothing: start maple-harness (or mpl) inside tmux.

What you can do #

Your commands. Typed by you, they run without asking. Windows are tmux's tabs.

CommandWhat it does
/tab new [name]a new window beside this session's, and moves you to it
/pane split [right|down] [command]splits this session's pane, with the command running in the new one
/pane run <command>the command in the last pane you opened (a new split if there is none)
/pane file <path>the file in your editor ($VISUAL, $EDITOR, or less) beside the session
/pane diff [args], /pane loggit diff or git log beside the session
/pane close [pane]closes the last pane you opened, or one this session opened
/panesevery pane of the tmux server, with this session's own, yours and the agent's marked
/worktree <branch> [base]a git worktree for the branch in a new window, with a new Maple session in it

The agent's tools. pane_open, pane_run, pane_read, pane_close, worktree_open and agent_start, as described in Panes, tabs and agents beside the session. pane_open, pane_run, agent_start and worktree_open ask you every time, even in auto or yolo mode (an allow rule you write still applies), and your deny rules for bash refuse the same commands in a pane. The tools only act on panes the session opened itself, never on yours.

Agents in windows. A Maple session started with agent_start says what it is doing (working, waiting for an approval, idle) in the agents tray, and the agent can wait for it and read its answer. tmux does not know what other agents are doing, so for Claude Code, Codex and the rest the tray shows them without a state and the agent reads their pane instead. In herdr their state is shown too.

Worktrees #

/worktree feat/login (or the agent's worktree_open, which asks every time) runs git worktree add with the repository's hooks turned off, from the main checkout only (where .git is a folder of its own). The worktree goes beside the repository, as <repository>-<branch> (../app-feat-login for app on feat/login); a branch that does not exist is made from the current commit, or from the base you give. A new window opens there, and /worktree starts a Maple session named after the branch in it, with this session's settings file and folders.

Choosing the workspace #

harness.workspace decides where panes open:

ValueWhat it does
auto (default)herdr when the session runs in one of its panes, else tmux, WezTerm or kitty, whichever it runs in, else a herdr running on this machine (new tabs only)
herdr, tmux, wezterm, kittyonly that one
offno panes: the tools and commands say so
YAML
harness:
  workspace: tmux

For the curious

Technical notes #

  • tmux. The harness talks to the tmux server it runs in, named from TMUX, and to the pane in TMUX_PANE; it never reaches another tmux server. A command is typed as literal text and then Enter, so nothing in it is read as a key name. Folder and window names with # are passed as plain text.
  • WezTerm. Through wezterm cli (spawn, split-pane, send-text, get-text, kill-pane, list), with WEZTERM_PANE naming this session's pane.
  • kitty. Through kitty's remote control (kitten @): it needs allow_remote_control and listen_on in kitty.conf, so that KITTY_LISTEN_ON is set in its windows. kitty's windows are the panes, and a split uses the splits layout. listen_on must be a socket file (unix:/path/to/kitty.sock, which the sandbox hides from the agent's commands); with another kind of address, Maple does not use kitty.
  • zellij is not supported: its command line does not say which pane it opened, so the pane could not be read, typed into or closed afterwards.
  • A command is one line of printable text; a line break or a control character is refused, so a command cannot press keys of its own.

Tested versions #

tmux 3.x (3.8, 2026-11-19: splits, windows, typing a command and reading its output, listing and closing panes, and names with #, on a private tmux server). WezTerm and kitty are written to their documented command lines and checked against recorded command lines only: they have not been tried in a running WezTerm or kitty yet.

If it does not work #

  1. Check that the harness runs inside tmux: echo $TMUX in the same shell prints the server's socket.
  2. For kitty, check that KITTY_LISTEN_ON is set (remote control on); for WezTerm, that WEZTERM_PANE is.
  3. harness.workspace: off turns it all off; harness.workspace: tmux uses tmux even inside herdr.
