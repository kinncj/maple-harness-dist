    Single sign-on for the setup page #

    On this page

    Team admins can sign in to a shared proxy's setup page with their company account (Google, Microsoft Entra ID, Okta, any OpenID Connect provider, or GitHub) instead of sharing one password. Off unless you turn it on. A proxy for one person on one machine does not need it: give the page a password instead (More > Protect this page).

    How it works #

    • The setup page on the proxy's machine does not change. It still listens on this machine only, and its password (if you set one) still works there. Maple's own commands keep using it.
    • Single sign-on serves the page on a second address you choose (setup_page.sso.listen), which people reach through your load balancer or ingress at the address in redirect_url, over HTTPS. That address answers only to the host name in redirect_url.
    • That address is never open. Every visitor signs in first. It does not take access tokens, and by default it does not take the page's password either (password: allowed changes that).
    • An admin sees the dashboards, usage, health and settings, and manages people, teams, their budgets and models, and access tokens with the proxy or metrics scope. Changing providers, keys, settings, remote control, webhooks, the page's password or the MCP hub, other kinds of tokens, sign-ins in progress, the secret store and the activity log stay on the setup page on the proxy's machine, or in config.yaml. Who may sign in is set only in config.yaml: the page cannot change it.
    • An admin can read the proxy's configuration: provider addresses, listen addresses, and cloud account and role names. Never keys or secrets.
    • A sign-in lasts session_lifetime (one hour by default, at most twelve), counted from when it started. Taking someone out of admins in config.yaml (or turning single sign-on off) takes effect on their next click. Taking them out of a group at your identity provider takes effect when their sign-in ends. Sign out (Settings tab) ends that browser's sign-in and closes its live view at once; Sign out other browsers ends every other single sign-on browser.
    • Open the page by typing or bookmarking its address. Like the setup page on your machine, it refuses requests that come from another site, including a plain link on an intranet page.

    Who counts as an admin, in admins (any one is enough):

    KeyMatches
    emailsA verified email address, exactly (case does not matter)
    domainsA verified email address in that exact domain (no subdomains, no wildcards). Not for GitHub
    groupsA value of the ID token's groups claim (groups_claim, default groups); GitHub: an organisation (my-org) or a team (my-org/my-team)
    subjectsThe account's unique id at the provider (the ID token's sub; GitHub: the numeric user id)

    Turn it on #

    1. Register Maple with your identity provider as a web application with the redirect (callback) address https://<the address people open>/sso/callback. The recipes below say where.

    2. Store the client secret where the proxy reads secrets. On a machine:

      maple-proxy secrets set sso/client_secret    # paste the secret, then Enter; it is never shown

      In a container, put it in the mounted secret under the key sso.client_secret.

    3. Add setup_page: to config.yaml and restart the proxy:

      setup_page:
  sso:
    enabled: true
    issuer: https://accounts.google.com
    client_id: 1234-abc.apps.googleusercontent.com
    client_secret: ${secret:sso/client_secret}
    redirect_url: https://maple-admin.example.com/sso/callback
    listen: 127.0.0.1:11547          # where your load balancer or reverse proxy sends that address
    admins:
      emails: [ana@example.com]
      domains: [example.com]

    4. Point your load balancer, ingress or reverse proxy (with TLS) at listen, keeping the Host header the browser sent. Open https://maple-admin.example.com/ and choose Sign in with Google.

    The proxy refuses to start with single sign-on half set up, and says what is missing. In particular it refuses a redirect_url on this machine (localhost, 127.0.0.1): on one machine, use the page's password. And it refuses a listen address reachable from other machines unless the proxy serves it with TLS itself (tls_cert_file, tls_key_file) or you say the network between your load balancer and the proxy is yours alone (insecure_backend: true).

    The settings #

    All under setup_page.sso in config.yaml. Read at start, except admins, groups_claim, password, session_lifetime, self_view and people, which apply on the next request after you save the file.

    KeyDefaultWhat it does
    enabledfalseTurns single sign-on on
    provideroidcoidc (Google, Microsoft, Okta and any OpenID Connect provider) or github
    namethe provider'sThe name on the sign-in button
    issuerThe provider's issuer, https:// (OIDC only)
    github_urlhttps://github.comGitHub Enterprise Server's address (GitHub only)
    client_idThe client (application) id
    client_secretA ${secret:NAME} reference; never the secret itself
    redirect_urlhttps://<host>/sso/callback, exactly as registered with the provider
    listenThe address the page is served on for single sign-on (host:port); not one of the proxy's other addresses
    tls_cert_file, tls_key_fileServe listen with TLS
    insecure_backendfalseAllow listen off this machine without TLS (logged at start)
    scopesScopes asked for besides openid email profile (for example groups)
    adminsWho may sign in as an admin: see the table above. At least one entry
    groups_claimgroupsThe ID token claim the groups are read from (for example roles)
    passwordoffallowed also accepts the page's password (when one is set) on this address
    session_lifetime1hHow long a sign-in lasts, 5m to 12h
    self_viewoffon lets people see their own usage: see below
    peopleEmail to person id, for the self view

    Google #

    1. In the Google Cloud console, APIs & Services > Credentials > Create credentials > OAuth client ID, type Web application. Add your redirect_url under Authorized redirect URIs.
    2. issuer: https://accounts.google.com, and the client id and secret it shows.
    3. Admins: emails or domains. For a domain, the account must be a Google Workspace account of that domain (its hd claim), not just any Google account with an address there; the same holds for an email in your company's domain. Google's ID tokens carry no groups.

    Microsoft Entra ID #

    1. App registrations > New registration: supported account types this organizational directory only, redirect URI of type Web = your redirect_url. Then Certificates & secrets > New client secret.
    2. issuer: https://login.microsoftonline.com/<tenant-id>/v2.0 with your directory (tenant) id. The common and organizations issuers are refused: one tenant per proxy.
    3. Admins by group (recommended): Token configuration > Add groups claim, security groups, ID token. The claim holds group object ids: put those in admins.groups. With app roles instead, set groups_claim: roles and list the role values.
    4. Admins by email: Token configuration > Add optional claim, ID token, email and xms_edov. Entra sends no email_verified, so an email counts only when xms_edov says its domain's owner verified it. A user in more than 200 groups gets no groups claim at all: use app roles for them.

    Okta #

    1. Applications > Create App Integration > OIDC - OpenID Connect > Web Application. Sign-in redirect URI = your redirect_url.
    2. issuer: https://<your-org>.okta.com (the org authorization server) or https://<your-org>.okta.com/oauth2/default (a custom one).
    3. Admins by group: on the org server, the app's Sign On > OpenID Connect ID Token > Groups claim filter; on a custom server, a groups claim in the ID token under Security > API > Authorization Servers > Claims, and scopes: [groups] if you tied the claim to that scope. Then list the group names in admins.groups.

    GitHub #

    GitHub has no OpenID Connect sign-in for people, so Maple uses a GitHub OAuth app with PKCE and then asks GitHub for the account's verified email addresses and, when admins.groups is set, its organisations and teams.

    1. Settings > Developer settings > OAuth Apps > New OAuth App; Authorization callback URL = your redirect_url.
    2. provider: github (no issuer), the client id and a client secret.
    3. Admins: groups as my-org or my-org/my-team (recommended; an organisation that restricts OAuth apps must approve this one, or its teams are not visible), or subjects (numeric user ids). emails works with verified addresses, but an address stays verified on GitHub after its owner leaves your company, so prefer groups; domains is refused for GitHub.
    4. GitHub Enterprise Server: github_url: https://github.example.com.

    Other OpenID Connect providers #

    Keycloak, Auth0, Authentik, Dex and others work the same way: register a confidential web client, set issuer to the address whose /.well-known/openid-configuration names that same issuer, and use emails, domains, groups or subjects. The provider must support the authorization code flow with PKCE (S256). Only an email_verified: true address counts as verified.

    On Kubernetes #

    Run the proxy's single sign-on address beside the setup page, and route your admin host name to it:

    # config.yaml (ConfigMap)
setup_page:
  sso:
    enabled: true
    issuer: https://login.microsoftonline.com/<tenant-id>/v2.0
    client_id: <application id>
    client_secret: ${secret:sso/client_secret}     # the Secret's key sso.client_secret
    redirect_url: https://maple-admin.example.com/sso/callback
    listen: 0.0.0.0:11547
    tls_cert_file: /run/tls/tls.crt                # or insecure_backend: true inside a network you trust
    tls_key_file: /run/tls/tls.key
    admins:
      groups: [<group object id>]

    Expose port 11547 with a Service, and an Ingress (or a Gateway route) for maple-admin.example.com with TLS that sends that host to it (with tls_cert_file set, tell your ingress the backend speaks HTTPS). Keep the Host header as the browser sent it. To have the throttles and the audit log count each browser rather than the ingress, list the ingress in server.trusted_proxies. With several replicas (storage.mode: central), sign-ins and sessions are kept in Redis, sealed with storage.encryption_key, so any replica serves any admin, and a sign-out ends their live views on every replica. See Run the proxy on Kubernetes.

    People see their own usage #

    With self_view: on, someone who is not an admin but whose verified email is one of your people's sees that person's own usage (the last 30 days, by day and by model) at /sso/me, and nothing else. Map emails to person ids under people (ana@example.com: ana), or give a person their email as their id. Off by default; the token-based self view (people_self_view) is unchanged. See Teams.

    What is not verified #

    Tested against a stand-in OpenID Connect provider and a stand-in GitHub, and in Chromium through a TLS front like a load balancer. Not yet run against real Google, Microsoft Entra ID, Okta or GitHub accounts, real ingress controllers, or Firefox and Safari.
