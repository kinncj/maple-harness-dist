herdr hosts terminal sessions for coding agents and shows, for each pane, whether the agent in it is working, waiting for you, or idle. Maple Harness works with it without any setup.

The short version

In plain words #

  • What it is. herdr shows, for each terminal pane, whether the agent in it is working, waiting for you, or idle. Maple also tells herdr when it is done (with the answer's first line), notifies you when you are looking at another pane, and can talk to the other agents on your machine: send them messages, read what they said, wait for them, and take messages from them.
  • Panes beside it. The agent can open terminals and tabs next to itself, run a server or a long build there, and start other agents (another Maple session, Claude Code, Codex) in a tab of their own. You can do the same with /tab, /pane, /panes and /worktree. The same works in tmux, WezTerm and kitty (Use it with tmux).
  • What to do. Nothing: start Maple inside a herdr pane. Other agents reach it with maple-harness agents send.

What you need to do #

Nothing. Start maple-harness (or mpl) inside a herdr pane and the pane labels itself maple-harness and shows its state as it changes:

StateWhat it means
workinga turn is running
blockedit is waiting for you to approve a tool call
idleit is waiting for your next message

The harness tells herdr itself, over herdr's local socket, and clears the label when it exits, so a pane is never left labelled by an agent that has gone. On a machine without herdr nothing happens and nothing is printed.

Next to the state it shows a short line: done: <the first line of the answer>, failed: …, or waiting for approval: bash. When a turn ends or an approval waits while you are looking at another pane, herdr shows a notification (with its "done" or "request" sound). herdr is also told which conversation runs in the pane and how to resume it (maple-harness --session <name>), and shows the session's name, its model and its permission mode beside the pane.

Talking to other agents #

Maple Harness sessions on the same machine, and the agents in your herdr panes (Claude Code, Codex and others), can talk to each other.

From a Maple session. The agent has four tools for this. Like any tool, each asks before it runs, unless you allow it or run in auto mode:

ToolWhat it does
agents_listthe other Maple sessions and herdr agents, and what each is doing (working, idle, blocked)
agent_messagesends a message: a Maple session gets it marked as coming from this one; a herdr agent gets it typed into its prompt
agent_reada Maple session's last answer, or the recent output of a herdr agent's pane
agent_waitwaits until the other agent stops working, then says whether it is done, idle or blocked

What another agent says comes back to the model marked as information from that agent, not as instructions. agent_message asks even in auto or yolo mode, because it acts outside this session and its sandbox (the agent it types into may run with no sandbox, or in yolo); an allow rule you write for it still applies. A session never messages itself, and a name two agents share is refused rather than guessed.

Into a Maple session. Any program you run, any agent in herdr included, can message a Maple session:

Shell
maple-harness agents                                  # the sessions on this machine
maple-harness agents send fix-parser "please also run go vet"
maple-harness agents send w1:p3 "review parser.go when you are free" --mode queue
maple-harness agents state fix-parser
maple-harness agents last fix-parser                  # its last answer

In the session, /inbox lists the recent messages other agents sent it and the ones it sent, and the agents tray lists the agents it talks to with what each is doing now (the agents tray).

A session is named by its session name, its herdr pane id, or its process id. The message shows in that session as ↘ from <sender> (the herdr pane it came from, or --from NAME), never as your own words. While the session works, a message steers its turn or queues for after it, by the same rules as typing (--mode steer or --mode queue decide it). The model is told it comes from another agent.

A turn that another agent's message started or steered is held: auto and yolo mode do not answer its tool calls, which ask you instead, because you did not ask for that work (your own allow rules still apply). Every message that comes in is recorded in agents-audit.log in the Maple Harness settings folder: who sent it, when, what became of it, and its first line. Turn incoming messages off with harness.agents.listen: off. That closes the socket; it cannot stop a program from typing into the pane through herdr (herdr agent prompt), which is like typing at the keyboard. A Maple session never types into another Maple session that way.

Answering approvals for a session. With harness.agents.approvals: on in that session's settings, another program can see the approvals it is waiting on and answer one, for example a reviewing agent or a script:

Shell
maple-harness agents approvals fix-parser             # ID, tool and what it would do
maple-harness agents answer fix-parser a3-5f0c2e9b17d4 allow   # or deny, with an ID from the list

The first answer wins, from the terminal or from here; a key you press in the terminal is taken the moment you press it. One given here leaves the terminal, with the answer and who gave it on the call's line, and is recorded in agents-audit.log with the tool and what it would do. Some questions are only ever answered by you in the terminal, and are listed with the reason: "always" (answer allow or deny here), a command run outside the sandbox, the cost confirmation, typing into another agent or pane, and anything asked in a turn another agent's message started. A project's own settings cannot turn this on, and it is only available on Linux for now.

It is off by default: any program of yours that reaches the socket could then allow a call. Commands the agent runs inside the sandbox cannot reach it; a command run outside the sandbox, or with the sandbox off, can.

Answering the model's questions. With harness.agents.questions: on (off by default, Linux only for now, not settable from a project's config), another program can also answer the questions the model asks you:

Shell
maple-harness agents questions fix-parser                      # ids, questions and options
maple-harness agents reply fix-parser q-7 Redis --note "we already run it"
maple-harness agents reply fix-parser q-7 --other "the company's SSO"
maple-harness agents reply fix-parser q-7 --answers '[{"id":"storage","selected":["Redis"]}]'   # several questions
maple-harness agents reply fix-parser q-7 --decline            # skip: the model decides

The first answer wins, from the terminal, a phone or here. The model is told such an answer came from another program, never from you, and it approves no tool call. It is off by default for the same reason as approvals: any program of yours that reaches the socket could answer for you.

Only your own sessions on this machine can be reached: each session listens on a local socket in a folder only you can open, and on Linux the sender's user is checked too. Nothing is reachable from the network, and commands in the sandbox cannot reach these sockets or herdr's. Not available on Windows yet.

Tested with herdr 0.9.0 (states) and herdr 0.9.5 (2026-11-19: opening a split and a tab in the session's own workspace, typing a command and reading what it printed, listing and closing panes, against a private herdr; and 2026-11-18, in a real herdr workspace: the pane's states, done after a turn, a message in through maple-harness agents send starting a turn and its answer read back with agents last and herdr agent read; the agent opening a pane beside it, running a command there after asking, and reading the result). herdr 0.9.5 accepts the session and resume details but does not show them anywhere yet, and it types into (herdr agent prompt) only agents it recognises itself, such as Claude Code and Codex: a Maple session takes messages through maple-harness agents send instead. Other versions should work, because it only uses herdr's public socket, but they haven't been tried.

For an orchestrator: the control socket #

In plain words:

  • What it is. Every interactive Maple session on your machine listens on a small local socket. A program that coordinates several agents (an orchestrator, a script, an editor plugin) can find the sessions, send one a message, read its state and last answer, and (where you allowed it) answer its approvals and its model's questions, without typing into its pane.
  • Why you want it. It is the reliable path: no screen scraping, no keystrokes into a terminal, and a session you started yourself keeps its full-screen interface.
  • What to do. Use maple-harness agents … --json from your program, or speak the socket's one-line JSON protocol below directly. Nothing has to be turned on except, for approvals, harness.agents.approvals: on, and for questions, harness.agents.questions: on.

Technical details:

Finding sessions. maple-harness agents --json prints the live sessions as a JSON array, one object each:

FieldMeaning
pidthe session's process id
socketthe path of its control socket
sessionits session name, when it has one
paneits herdr pane id, when it runs in herdr
term, term_id, term_panethe terminal workspace it runs in (tmux, wezterm or kitty), which one (tmux's server socket, WezTerm's socket, kitty's socket or process id), and its pane id there, when it runs in one
dirthe folder it works in
startedwhen it started (RFC 3339, UTC)

The sockets live in $XDG_RUNTIME_DIR/maple-harness/ (or, without XDG_RUNTIME_DIR, a folder named maple-harness-<your uid> in the temporary folder), each beside a <pid>.json file holding the same object. The folder is yours alone (0700), each socket 0600, and on Linux the connecting program's user is checked as well.

The protocol. Connect to the socket (a Unix stream socket), write one JSON object per line, and read one JSON object per line back. Several requests can go over one connection, which closes after 30 seconds.

RequestAnswer
{"cmd":"hello"}{"ok":true,"protocol":1,"commands":["hello","send","state","last",…]}: the protocol version and the commands this session takes (approvals and answer, questions and answer_question, only where they are on)
{"cmd":"send","text":"…","from":"reviewer","mode":"auto"}{"ok":true,"disposition":"delivered","busy":true}: mode is auto (the words decide), steer or queue; busy says a turn was running. from (at most 64 characters) is how the message is labelled in the session
{"cmd":"state"}{"ok":true,"state":{"session":"…","pane":"…","dir":"…","model":"…","status":"working"}}: status is working, idle or blocked (waiting for an approval)
{"cmd":"last"}{"ok":true,"text":"…"}: its last answer, at most 64 KB
{"cmd":"notice","text":"…","from":"…"}{"ok":true}: shows the text to the session's person, as a line in its window and a desktop notification, labelled with from. Only text of the form <session> changed <setting> to <value> (a setting's dotted name, a short plain value) is taken; anything else is refused. Never a turn, never words for its model
{"cmd":"approvals"}{"ok":true,"approvals":[{"id":"…","tool":"bash","what":"…","subagent":"…","terminal_only":"…"}]}: only with harness.agents.approvals: on. terminal_only, when set, says why that one can only be answered in the terminal
{"cmd":"answer","id":"…","allow":true,"from":"reviewer"}{"ok":true}: the first answer wins. "always":true is refused here, as above
{"cmd":"questions"}{"ok":true,"questions":[{"id":"…","agent":"…","questions":[…]}]}: the questions its model is waiting on, each with its questions and options as the model asked them. Only with harness.agents.questions: on
{"cmd":"answer_question","id":"…","answers":[{"id":"storage","selected":["Redis"],"other":"","note":""}],"from":"reviewer"}{"ok":true}: one answer per question, by option label; "decline":true instead of answers skips the dialog. The first answer wins, and an answer that does not fit the questions is refused. The model is told it came from another program (agent:<from>), never from the person

A request that fails answers {"ok":false,"error":"…"} with one line saying why. A message's text is at most 64 KB; at most 16 connections are served at once per session. protocol goes up only when a command changes in a way an existing client would notice; new commands and new fields can be added without it, so ignore what you do not know.

Shell
# the same, from a shell
echo '{"cmd":"state"}' | socat - UNIX-CONNECT:"$(maple-harness agents --json | jq -r '.[0].socket')"

A message that arrives this way is treated as another agent's, never as yours: it is shown as coming from the sender, and the turn it starts or steers is held, as described in Talking to other agents. There is no network or token mode: only programs running as you, on this machine, can reach a session. For a session you start from your program instead, maple-harness --rpc is the other way (Drive it from another program).

Panes, tabs and agents beside the session #

Inside herdr the agent can open terminals beside it, to run a server, a watcher or a long build while it keeps working, and start other agents there. In tmux, WezTerm and kitty the same tools work (Use it with tmux).

ToolWhat it doesAsks you
pane_opena split to the right or below this session, or a new tab, in this session's folder (or one inside it, or a worktree it made); your view does not move to it. Its shell starts there, outside the sandboxevery time
pane_runtypes one command line into a pane it opened, and presses Enterevery time (and for a pane whose program it does not know, see below)
pane_readthe recent output of a pane it openedlike any tool
pane_closecloses a pane it openedlike any tool
worktree_opena git worktree for a branch, where your setting puts worktrees (Worktrees), open in a workspace of its ownevery time
agent_startanother agent in a new tab or split: a new Maple Harness session given a task, or another agent's command line (claude "…", codex "…")every time

"Every time" means even in auto or yolo mode, and "always" is not offered for these: each call is its own question. An allow rule you write for that tool still applies, and a deny rule always wins. Your deny rules for bash refuse the same command in a pane too, and a message typed into an agent's pane. These questions are answered in the terminal only, never from the phone or by another agent.

Agents in panes. agent_start with a Maple session opens it with this session's settings file and folders, and sends it the task as a message from this session (never as your words), so that session asks before every tool in that turn, whatever its mode. It is always a new session: the name of one of your saved sessions is refused, so an agent never continues one of your conversations. With another agent's command line, the task is part of the command you approve. Either way the agent is listed in the agents tray with what it is doing, and agent_message, agent_read and agent_wait reach it by the name the tool answers with. herdr says whether a Claude Code or Codex pane is working or done; in tmux, WezTerm and kitty only a Maple session says so, and other agents are read from their pane. When the agent in a pane has exited and a shell runs there, messages are no longer typed into it; where the workspace cannot say what runs in a pane (herdr for agents it does not recognise, WezTerm, kitty), agent_message does not type there at all, and the agent uses pane_run, which shows you the line.

Never typing into a Maple session. Keys typed into a pane where a Maple session runs would drive it as your keyboard does: its message box, but also its menus, /settings and the answer to an approval. So nothing is ever typed into one: not by pane_run, not by agent_message, not by your own /pane run. Every Maple session writes which pane it runs in when it starts, however it was started (by agent_start, by hand, through a shell or a wrapper) and whether it takes messages or not: its herdr pane, or its tmux server and pane (the inner one in a nested tmux), its kitty window and kitty's socket, or its WezTerm pane and socket. A pane counts as a Maple session's when one says it is there, when this session started one there, when herdr reports a Maple agent there, or when the workspace says the program running there is maple-harness or mpl. agent_message reaches such a session through its control socket instead: there it is a message from this session, shown and handed to its model as another agent's words, and only ever a message (a /settings in it is text, never a command); a Maple session that does not listen (harness.agents.listen: off) is not messaged at all.

Which panes pane_run asks about. In plain words: Maple asks about a pane only when it does not know what is running there. A pane the agent opened itself is known: pane_open and worktree_open start a shell there, and agent_start the program of its command line (claude for claude "…"). While the pane runs that (or a shell), or while the workspace does not say what runs in it (herdr, WezTerm), pane_run types into it like any call, under your rules (it asks every time unless you wrote an allow rule for pane_run). In herdr, an agent it reports in the pane that the agent did not start there makes the pane unknown.

A pane is unknown when the workspace names another program running there (you started psql, vim or ssh in it, or the agent it started handed over to something else). Then pane_run types only when the call names that program (confirm_program), and:

  • While you watch (ask mode, in the terminal), you are asked, even if a rule allows pane_run, and the question starts with the program the keys go to. Once you allow it, the pane stays allowed for that program for the rest of the session: later calls into it are like calls into a pane the agent opened. The allowance is forgotten when the pane closes, when the workspace gives its id to another pane, or when another program runs there (the session says so, and asks again).
  • While nobody watches (auto or yolo mode, a --prompt, --rpc or A2A run), nothing waits for an answer. The program the agent names is its claim, not a fact, so it counts only for an allow rule written for pane_run with that program: pane_run(*psql*) exactly, or pane_run(*"confirm_program":"psql"*); in auto or yolo mode, where you chose to accept, an allow rule for pane_run does too. Without one the call is refused, the reason goes to the agent and the transcript, and the run carries on. A pane typed into this way keeps the name the agent gave it for this session only (never saved, never shared with another session): /panes shows it as "named psql by the agent", each later call names it again, and it is dropped when the pane closes or its program changes. A shell named for a pane is read as unknown.
  • Never, in any mode: typing into a pane that runs a Maple session; typing a program your bash deny rules refuse (bash(psql*) refuses a pane named psql); answering an approval: nothing is typed into a pane whose agent herdr reports waiting for its person's approval unless you were asked about that very call.
  • A pane running something that hides what runs inside it (another tmux or screen, ssh, a container, sudo), or one agent_start started such a program in (also behind env, nice, exec, timeout or sh -c), is never known and never remembered: every call names it, and is asked about or weighed by your rules again.

agent_message does not type into a pane running something a session cannot see into.

A started session says when its safety settings change. A Maple session agent_start started says, in its own window and in the window of the session that started it, each change to one of its safety settings, whoever made it: the permission mode or rules, the sandbox, which files its tools may touch, the memory limits, what other agents may answer, and what it runs (hooks, MCP and language servers, notification commands). Each is a line and a desktop notification, such as Maple Harness session review changed permission.mode to yolo; nothing reaches either model. A value is shown only when it is one of the words or numbers these settings take (yolo, off, 4GiB), a list says how many entries it has, and anything else (a folder, a command, an address) is said as "a new value". The session that started it is found by its process id and the time it started, so a later program given the same id is never told.

Your own commands. Typed by you, so they run without asking. The panes they open are yours: the agent's tools never type into them.

CommandWhat it does
/tab new [name]a tab beside this session, and moves you to it
/pane split [right|down] [command]a split beside this session, with the command running in it
/pane run <command>the command in the last pane you opened (a new split if there is none)
/pane file <path>the file in your editor ($VISUAL, $EDITOR, or less) beside the session
/pane diff [args], /pane loggit diff or git log beside the session
/pane close [pane]closes the last pane you opened, or one this session opened
/panesevery pane of the workspace, with this session's own, yours and the agent's marked
/worktree <branch> [base]a git worktree for the branch in a new tab (in herdr, a workspace of its own), with a new Maple session in it

harness.workspace picks the terminal workspace: auto (the default: herdr when the session runs in one of its panes, else tmux, WezTerm or kitty, else a herdr running on this machine, for tabs only), one of herdr, tmux, wezterm, kitty, or off.

What runs outside the sandbox #

The agent's own commands (bash) run in its sandbox. A pane is an ordinary terminal of yours: what runs in it runs as you, with no sandbox. That is why pane_run and agent_start ask you every time, show you the exact command line, and are refused when your bash deny rules refuse that command.

Runs outside the sandboxAsks you
the shell pane_open starts in a new pane (with that folder's shell and git settings)every time
a command pane_run types into a paneevery time
an agent agent_start starts, and what that agent then does (under its own settings)every time
a message agent_message types into another agent's promptevery time
git making a worktree (worktree_open, /worktree), with the repository's hooks turned off, and only from a main checkout whose .git folder is its ownworktree_open every time
your own /tab, /pane and /worktree commandsno: you typed them

The agent's tools act only on panes this session opened: never on your panes, panes you opened with /pane, or another agent's, and not on a later pane that was given the same id. Commands in the sandbox cannot reach herdr's, tmux's, WezTerm's or kitty's socket (see the sandbox), so they cannot open a pane themselves. A Maple session started in a pane has its own sandbox and permission mode, from your settings.

If the pane does not pick it up #

  1. Check that you started the harness from a shell inside the herdr pane (not a separate terminal window).
  2. If herdr uses a non-default socket, make sure HERDR_SOCKET_PATH points at it in the environment the harness inherits. By default it looks in ~/.config/herdr/herdr.sock.
  3. Run maple-harness version to confirm you are on a current build, then start a new session.

The terminal signals, with or without herdr #

Independently of herdr, the harness sets the window title and the terminal's progress indicator on every change of state, and sends a notification when a turn finishes or needs a decision. Terminals that do not support one of these ignore it.

StateWindow titleProgress indicator
idle● MapleHarnesscleared
working✳ MapleHarness — workingbusy
needs approval⏸ MapleHarness — needs approvalwarning
done✓ MapleHarness — donecleared
failed✗ MapleHarness — failederror

WezTerm, Ghostty and Windows Terminal show the progress indicator on the tab. Any terminal shows the title.

The detection manifest (advanced) #

herdr can also classify a pane from a detection manifest. Most people do not need this, because the harness reports its own state. If you want the manifest anyway, maple-harness herdr-manifest prints it, and maple-harness herdr-manifest --id <name> writes a different agent id into it. Whether your herdr version loads manifests for agents it does not ship with depends on the version, and this path has not been tested beyond herdr 0.7 and 0.9.

Turning the installer's herdr step off #

The installer needs to install nothing for herdr. --no-herdr is accepted and ignored, so older install commands keep working.
