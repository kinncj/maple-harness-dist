Background commands and monitors #

The agent can start a long command (a test suite, a build, a server) in the background and keep working while it runs. When that command ends, the agent is told: its exit code, how long it ran and the last lines it printed, so it never has to keep checking. It can also watch a command's output, such as a log or a CI run, and be told about the lines that matter as they come.

The short version

In plain words #

  • What it is. Commands that run while the agent does something else. When one ends, a line appears in the conversation and the agent reads the result. If the agent was idle, it wakes up and carries on.
  • Why you want it. A ten-minute test run no longer holds up the work, and nothing waits on the agent polling for a result: it hears the moment the run ends, pass or fail.
  • What to do. Nothing. To see what is running, press Ctrl+T (the agents tray) or type /jobs. To stop one, select it in the tray and press x, then y.
  • What stays the same. A background command runs under the same rules as any other: your permission rules, the sandbox and the memory caps.

When a background command ends #

In the conversation, one line:

$ bg_1 finished · exit 3 after 2s · go test ./internal/orders/...

When nothing else is going on, the agent starts a turn to read it, and the line says so:

$ bg_1 finished · exit 0 after 3m 12s · go test ./...  ↳ wakes the agent

While a turn is running, the result reaches the model at its next step instead; nothing is interrupted. When the terminal is not in front, a desktop notification says which command finished.

Not every end is announced:

How it endedWhat you and the agent hear
On its own (passed, failed, or stopped by a cap)The line above, and the agent reads the result
You stopped it (in the tray)The same, saying stopped by the person after …
The agent stopped it itself (kill_shell)Nothing: it already knows
Maple Harness was closingNothing

What happens: wake, next or off #

harness.job_notices decides:

ValueWhat it does
wake (default)The agent is told at once: during a turn at its next step, and when idle a turn starts for it
nextThe agent is told at its next step, or with your next message. It never starts a turn by itself
offNothing is said. The agent can still read a command's output with bash_output

A turn you did not ask for asks first

A turn a notice starts is not one you asked for, and it carries a command's output, so its tools ask before they run, even in auto or yolo mode, as in a turn another agent's message starts. The output itself reaches the model marked as the command's text: information, not instructions.

Only the terminal starts a turn by itself. A session driven another way (--rpc, maple-harness serve, -p) hands the result to the model at its next step or its next turn.

Watching a command: monitors #

A monitor runs a command and tells the agent about its output line by line: tail -f on a log, a CI run that prints as it goes, a test watcher. The agent can ask to hear every line, or only lines that match a pattern (for example FAIL|panic), and to stop at a line that says the work is over (for example ^ok|DONE).

Lines reach the agent in batches, at most one batch every 5 seconds, so a chatty log does not flood the conversation. Each batch shows as one line, ~ mon_1 · 3 new lines · <the last one>. A monitor wakes an idle agent at most twice, for its first lines and for its end (by harness.job_notices); the batches between reach it at its next step. One batch carries at most 16 KB; the rest is said to be left out, and bash_output reads it.

A monitor stops by itself:

  • when a line matches its until pattern (that line is the last one reported);
  • after its time limit: 5 minutes unless the agent asks for longer, 30 minutes at most;
  • after it has reported its number of lines: 50 unless the agent asks for another, 200 at most;
  • when the command it watches ends.

When it stops, the agent is told why and how many lines it reported in all. The agent can stop it sooner with kill_shell; you can stop it from the tray.

A monitor asks first #

Important

A monitor keeps running and feeds what it reads to the model unasked, so it always asks before it starts, in every mode, auto and yolo included, unless a permission rule allows it.

Rules match the command, like rules for bash. To let the agent tail logs without asking each time:

YAML
harness:
  permission:
    rules:
      - {decision: allow, pattern: "monitor(tail -f *)"}

A command your rules deny as bash is refused as a monitor too, whatever a monitor rule says, and so is a shell write under harness.bash_file_writes: deny. A hook that guards Bash sees monitors too. A subagent working in its own copy of the project runs its monitors there. Monitors are not offered in plan mode.

Seeing and stopping them #

In the agents tray (Ctrl+T, or ↓ from an empty message box), after the subagents, there is a row for each command or monitor that is running, or that finished in the last 20 seconds:

$ bg_1   go test ./...                    3m 12s
~ mon_1  watching tail -f ci.log          4 events · ends in 26m

$ is a command, ~ a monitor; the mark's colour says whether it is running, waiting for a heavy-run slot, passed, or failed or was stopped. With a row selected:

  • ↑/↓ move between rows;
  • Enter shows the last 40 lines it printed, in the conversation, for you only (the agent reads output with bash_output or agent_read);
  • x, then y, stops it, and the agent is told that you stopped it.

With the tray folded (c), the status line counts running commands and monitors as N jobs. /jobs lists this session's commands and monitors as a table, with their state.

Its whole output, in a file #

Every background command and monitor also writes everything it prints to a file of its own, so a long test run can be looked back through later. The file is kept small enough to be harmless: past 16 MB the oldest half is dropped, and the file says so at its top. The files are in a private temporary folder (only you can read it) that the harness removes when it exits. The message the agent gets when the command starts names the file; agent_read with the job's id (bg_1) and up to 400 lines reads its end.

A command that runs past its timeout #

A command the agent runs in the foreground is stopped when it reaches its timeout (2 minutes unless the agent asks for more). With harness.bash.background_on_timeout: on, it moves to the background instead: it keeps running as bg_N, with what it printed so far and everything after, the same caps and heavy-run slot, and you and the agent are told when it ends, as for any background command. Off by default.

SettingDefaultWhat it does
harness.bash.background_on_timeoutoffon: a foreground command past its timeout moves to the background instead of being stopped

For the curious

Technical details #

The tools. bash with run_in_background: true starts a command and answers at once with its id (bg_1, bg_2, …). bash_output reads what it printed since the last read, and kill_shell (or agent_stop) stops it and everything it started. agent_read reads its last lines and agent_wait waits for it to end. monitor starts a watch (mon_1, mon_2, …) and takes:

ArgumentMeaningDefaultLimit
commandThe shell command whose output to watchrequired
matchA regular expression: only lines matching it are reportedevery line500 characters
untilA regular expression: the first line matching it is reported, then the watch endsnone500 characters
timeout_secondsStop watching after this long3001800
max_eventsStop after reporting this many lines50200

A reported line longer than 2,000 characters is cut. The figures are chosen limits, not measurements.

What the model reads. A finished command:

[background command bg_1 finished: exit 3 after 2s] go test ./internal/orders/...
Last lines of its output (bash_output(job_id="bg_1") reads the rest):
--- FAIL: TestEmptyCart (0.00s)
…

That is the last 40 lines it printed, at most 8 KB, with a note when earlier lines were left out, or (it printed nothing). A monitor's batch starts [monitor mon_1: 3 new lines from <command>], and its end [monitor mon_1 ended: <why>; 4 events in all]. These notes go at the end of the conversation, after what is already there, so they do not disturb what came before.

The same rules as bash. A monitor's command runs exactly as a background bash command does: in the sandbox when the sandbox applies, under the per-command and per-session memory caps, and, when it is a heavy run such as a test suite, in a heavy-run slot (it waits for one like any other heavy run, and gives it back when it ends).

Tested on Linux. macOS and Windows have not been tried.
