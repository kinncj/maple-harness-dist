Maple Harness 3.0 is a big one, eh: agents that keep working while you talk, an agent that asks before it guesses, a terminal with a fresh coat of paint, and a proxy that can run a whole organization's model traffic, LiteLLM included. On one computer it asks nothing of you: update, restart the proxy and carry on. Everything new stays out of the way until you set it up. This page is the tour; each card opens the guide.

The short version

In plain words #

  • Nothing to do on one computer. Your settings, sign-ins, sessions and usage history keep working. See Upgrading to 3.0.
  • The agent does more on its own. Helpers keep working after the turn ends and report back by themselves; long test runs tell the agent when they finish; and when a decision is yours, the agent asks you a short question instead of guessing.
  • You can steer it. Type while it works and your correction reaches it mid-turn.
  • The terminal looks better. Framed dialogs, tinted diffs, a mode chip, themes you try live, and a first screen reader mode.
  • The proxy does more. Model groups, capacity it learns, guardrails, a cache that answers by meaning, scheduled investigations, and more of the OpenAI and Anthropic APIs.
  • One proxy for a whole organization. Organizations, roles, rules per access token, budgets per end user, lifetime budgets, rate limits and LiteLLM's management API. All opt-in.
  • Every setting on the setup page. The settings that used to be config.yaml only now have forms.
  • Ready-made deployment. A published container image, a Helm chart and Compose quick starts.

Updating from 2.x?

Read Upgrading to 3.0 first: what keeps working, what behaves differently, the one question that may come back, and how to go back to 2.x.

The agent #

Helpers that stay out on the ice while you talk, and a lineup you can watch.

  • When a limit runs out Out of a provider's limit with no fallback left? The session and its agents pause until the reset the proxy says, and carry on, sooner if you add a fallback or switch model.
  • Background agents Agents that keep working after the turn ends; each report lands and wakes the session. Talk to a running one, resume a finished one, or keep them working after you quit.
  • The lineup The task list the agents share, live with /tasks or Alt+T: who has what, what waits for what, and checks that must pass before a task is done.
  • Questions the agent asks you ask_person puts one to four short questions to you, with options, your own answer and a note, in the terminal, on your phone, over --rpc or A2A.
  • Background commands and monitors Long commands tell the agent when they end, and monitors report the log lines that matter as they come.
  • Memory caps and heavy runs Every command the agent runs has a memory cap, and test suites and builds take turns across all your sessions.
  • Subagents in their own copy A writing background agent works in its own git copy, and its changes are applied only when you agree.
  • Notes of its own An agent file with memory: keeps notes between its runs; permissions and limits give an agent its own rules and budget.

Steering and the terminal #

  • Steer a turn while it works A correction typed mid-turn reaches the model at its next step; Ctrl+G, /steer and /queue decide it yourself.
  • How the interface looks Framed dialogs, tinted diffs, a mode chip, /theme to try every theme live, three themes from home (birch, northern-lights, toque) and screen reader mode.
  • Commands and keys The key map (?), the palette (Ctrl+P), the session switcher (Ctrl+S), /settings, the sidebar, @ for files and Ctrl+R for what you sent.
  • Language servers Compile errors after every edit, now listed in the sidebar too.
  • Use it with herdr Sessions and agents that message each other, and panes beside the session in herdr, tmux, WezTerm and kitty.
  • Drive it from another program sessions list --json, --rpc with send, questions and approvals for scripts and editors.

Screen reader mode is a first version

It has not been checked with a real screen reader yet. Dialogs, tints and the theme picker are not yet verified on macOS and Windows terminals.

Agents that call agents #

  • Maple Harness as an A2A agent maple-harness a2a serve takes tasks from other agents over A2A 1.0 and 0.3; tool calls still wait for approval.
  • The proxy as an A2A gateway Several agents at one address, with access per person and team, each agent's own credentials, loop limits and a record of every call.
  • Find an agent GET /v1/agents?query= finds the gateway's agents by what they do, by meaning when the built-in model is installed.

The proxy: routing and capacity #

  • Model groups One model name served by several accounts, regions or servers, with retries and a conversation kept on the deployment that answered it.
  • Capacity, in three layers The proxy asks your model server how many requests it takes at once, learns it from busy answers otherwise, and always obeys what you set. Interactive requests go first.
  • Your own rules for auto Words in a message that set its weight, and several models for one weight.
  • Content-policy fallbacks Models to try only when a provider refuses a request for its content.
  • The semantic cache A question already answered, worded differently, answered again without asking the provider. Off unless you turn it on.
  • More API routes The OpenAI Responses API (Codex CLI works through the proxy), rerank, moderations, images, audio, files, batches, legacy completions and pass-through routes.

The proxy: control and insight #

  • Guardrails Block, mask or log secrets, personal data, banned terms and your own patterns, before a request is sent, on the answer and around MCP tool calls.
  • Investigations Scheduled checks over the usage log for recurring errors, loops, cost spikes, cache regressions and providers that fail or slow.
  • Content export and callbacks Prompts and answers of the people you name to Langfuse, Phoenix or OpenTelemetry, and usage lines to a webhook, Datadog or storage.
  • Request tags Label requests with X-Maple-Tags (or --tag in the harness) and sum usage by story, feature or job.

One proxy for an organization #

Everything here is opt-in: a single-user setup is unchanged.

  • Organizations and roles One budget and model list over several teams, and roles for the people who manage the proxy.
  • Rules per access token A budget, a model list and the addresses a token may be used from.
  • Budgets per end user A spending limit for each customer of your own application.
  • Lifetime budgets A budget that never resets, for a contractor or a trial.
  • Rate limits Requests a minute, input tokens a minute and requests at once, for people and teams.
  • Rotate or revoke a token Block, expire and rotate tokens, with a grace period for the old secret.

LiteLLM, both ways #

  • Maple in front of LiteLLM A litellm provider type; Detect models lists what the key may use.
  • LiteLLM in front of Maple Your LiteLLM serves some models from a Maple proxy, a GitHub Copilot seat for example.
  • LiteLLM's management API Scripts written for /key, /user, /team and spend keep working against Maple.
  • Move a LiteLLM config to Maple maple-proxy import litellm, from a file or a running LiteLLM; nothing changes without --write.

The MCP hub, ready for teams #

No longer experimental. A 2.x mcp_hub section works unchanged; everything new is opt-in.

  • Servers that ask you to sign in One sign-in for everyone, each person their own, or the hub as an app.
  • Acting for each person without a browser Token exchange: each person's calls reach the server as them, and nobody opens a browser.
  • Who may use which tools Lists per team, per token and named groups; the most restrictive wins.
  • Pinning tools Tools, prompts and resources that changed are held back until you accept them.
  • The tool loop A chat request names hub servers, and the proxy runs their tools for it.

The setup page #

  • Every setting on the page Access control, routing rules, concurrency, the semantic cache, cloud accounts, pass-through routes, callbacks, the MCP hub and the A2A gateway have forms; a secret typed there is write-only.
  • The setup page, card by card What each card shows and does, Findings and Guardrails included.

Deployment #

  • The published image A container image for every release, for Intel/AMD and ARM, with Compose quick starts.
  • With Helm A Helm chart, beside the Kustomize samples, from one pod to several replicas.
  • Codex CLI A tested Codex CLI setup through the proxy's Responses API.
  • Install With GitHub's gh installed, the installers and update check that a release came from the public release workflow.

Not verified yet #

Note

Some of 3.0 was checked against stand-ins rather than the real thing: the provider guardrail services, the semantic cache with real traffic, token exchange with Keycloak, Okta or Entra, and the container image and Helm chart in a real cluster. macOS and Windows were not run for most of the agent features, and the WezTerm and kitty panes were checked against their command lines only. Each page says what was and was not tried.

Upgrading #

  • Upgrading to 3.0 What keeps working, what behaves differently, the question that may come back, and how to go back to 2.x.
  • Install maple-harness update, or the installer again, then restart the proxy.
